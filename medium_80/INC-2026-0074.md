## Symptom
The incident began with reports of object replication lag exceeding the SLA threshold in our distributed filesystem. Monitoring alerts indicated a growing delay in data replication across nodes, prompting an immediate investigation. As the lag continued to increase, it became clear that this was not a transient issue but a persistent problem affecting data consistency and availability.

Further analysis revealed that the replication lag was not uniform across all nodes, suggesting a potential issue with the metadata server or the network connections between nodes. The s3-style CLI tool was used to inspect the bucket's replication status, and `rsync --dry-run` was employed to simulate data transfers and identify any bottlenecks. However, these initial checks did not reveal the root cause of the lag.

The impact of the growing replication lag was significant, as it threatened the integrity and availability of data stored in the distributed filesystem. This prompted a swift escalation of the incident to ensure timely resolution and minimize potential data loss or corruption.

As the incident progressed, the focus remained on understanding and addressing the cause of the replication lag, with an emphasis on the distributed filesystem's metadata server and its role in managing data replication across nodes.

## Diagnosis steps and hypotheses
Initial hypotheses focused on network connectivity issues or node performance problems. However, as the investigation deepened, attention turned to the metadata server and its configuration. One key diagnostic step involved examining the health of the storage paths using the command:
```
multipath -ll | grep -c active
```
This helped assess whether there were issues with the multipathing setup that could contribute to the replication lag.

Despite these efforts, the root cause remained elusive until the focus shifted to the replication factor and its potential impact on the metadata server's ability to manage data replication efficiently. It became clear that a misconfigured replication factor could lead to a split-brain scenario, severely impacting the distributed filesystem's performance and data consistency.

## Resolution steps
1. Restart metadata server on node 3
2. Set replication_factor to 3 in /etc/distributed-fs.conf
3. Run s3-style CLI command with --repair flag on bucket mydata
4. Verify multipath -ll output shows healthy paths to storage devices

## Post-mortem note
The distributed filesystem metadata server experienced a split brain scenario due to a misconfigured replication factor. This incident highlights the importance of regularly reviewing configuration settings, especially those critical to data replication and consistency, to prevent similar issues in the future.
