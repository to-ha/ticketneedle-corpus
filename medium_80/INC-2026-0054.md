## Symptom
The application connection pool reported periodic spikes of dropped connections, with the pattern recurring every 30-45 minutes and clearing within a minute. This symptom was observed by monitoring tools and reported by users experiencing transient errors. The dropped connections seemed to happen without any explicit error messages from the database, making it challenging to pinpoint the cause.

Further investigation revealed that autovacuum was canceling under sustained write load, which might have contributed to the connection drops. However, the direct link between autovacuum cancellation and connection drops was not immediately clear. The team decided to monitor the situation more closely, focusing on database performance metrics and connection pool behavior.

The observable pattern of dropped connections, combined with the autovacuum behavior, suggested that there might be an issue with how the database was handling connections under load. This led to a deeper investigation into the database's connection management and pooling mechanisms.

## Diagnosis steps and hypotheses
Initial hypotheses focused on database configuration and resource utilization. The team considered the possibility of inadequate connection pooling settings or insufficient database resources (e.g., CPU, memory) to handle the load. To investigate further, the team used tools like `iostat` and `pidstat` to monitor system resources and database performance.

A key diagnostic step involved checking the current database activity, particularly focusing on idle connections, using the command:
```
psql -c 'SELECT * FROM pg_stat_activity WHERE state = idle'
```
This helped in understanding the connection pool's behavior and identifying if there were any issues with idle connections being improperly managed.

## Resolution steps
1. Set pool_health_check_kill_idle to false
2. Add 60s grace window to pool resize eviction
3. Restart pooler service with new config
4. Verify idle connections are not terminated mid-transaction

## Post-mortem note
Pooler health-check killed idle backends mid-transaction during a graceful pool resize. This root cause explained the periodic spikes of dropped connections observed by the application. Adjusting the pool health check and adding a grace window to the pool resize eviction resolved the issue, ensuring that idle connections are managed properly without being terminated mid-transaction.
