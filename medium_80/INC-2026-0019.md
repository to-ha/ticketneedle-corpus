## Symptom
The incident began with reports of pods failing to become Ready despite the Horizontal Pod Autoscaler (HPA) scaling up. This symptom was consistently observed across multiple deployments, suggesting a deeper issue within the cluster. Further investigation revealed that the affected pods were stuck in the Pending state, indicating a potential problem with resource allocation or cluster management.

As the issue persisted, monitoring tools began to show an increase in errors related to etcd communication, hinting at a possible problem with the etcd cluster's health. The symptom complex pointed towards an etcd-related issue affecting pod scheduling and deployment.

## Diagnosis steps and hypotheses
Initial hypotheses centered around network connectivity issues or misconfigurations within the etcd cluster. To investigate these hypotheses, the team ran several diagnostic commands, including:
```
k9s get etcdcluster --namespace=kube-system -o yaml
```
This command provided valuable insights into the etcd cluster's current state and helped rule out certain hypotheses. However, it became clear that the root cause was more complex and related to the etcd cluster's quorum state.

## Resolution steps
1. Restart etcd node 2 with --listen-peer-urls=http://10.0.0.2:2380
2. Set etcd cluster quorum to 3 using etcdctl member add
3. Verify cluster health with k9s get etcdcluster --namespace=kube-system
4. Remove failed etcd node 1 from cluster with etcdctl member remove
5. Update etcd configuration to use --heartbeat-interval=100ms

## Post-mortem note
etcd cluster lost quorum due to node failure. This incident highlights the importance of monitoring etcd cluster health and having robust recovery procedures in place to quickly address quorum losses and prevent prolonged service disruptions.
