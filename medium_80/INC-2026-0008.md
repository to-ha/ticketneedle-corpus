## Symptom
The incident began with reports of a DNS resolution latency spike to 5-10 seconds, affecting multiple services across the network. This increase in latency was first observed by monitoring tools and subsequently confirmed by user reports. The symptom presented as a uniform delay in name resolution, regardless of the destination domain or the user's location within the network. Initial observations suggested that the issue was not limited to a specific segment of the network but was rather a widespread problem.

Further investigation revealed that the latency spike was consistent across different types of DNS queries, indicating that the issue was likely related to the underlying network infrastructure rather than a specific DNS server or service. The uniform nature of the delay pointed towards a routing or network configuration issue, as application-level problems would likely have shown more variability in their impact.

Given the critical nature of DNS for service discovery and accessibility, even a short-lived increase in resolution latency can significantly impact user experience and service availability. Thus, understanding and resolving the root cause of this symptom was of paramount importance.

As the incident unfolded, it became clear that the impact was not confined to user-facing services but also affected internal tools and automation scripts that relied on timely DNS resolution. This broad impact underscored the need for a swift and comprehensive diagnosis to identify and rectify the underlying cause.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential issues with DNS server configuration or reachability. However, as evidence mounted, attention shifted towards the network infrastructure, particularly the OSPF protocol, which is crucial for dynamic routing within the network. One of the key diagnostic steps involved capturing network traffic to analyze OSPF messages:
```
tcpdump -i eth0 -n -v -s 0 -c 100 'ospf'
```
This command helped in understanding the OSPF protocol's behavior and identifying any anomalies in neighbor discovery or route advertisement. The output provided valuable insights into the protocol's operation, although it did not directly point to the root cause without further analysis of the network configuration.

Other hypotheses considered included issues with link quality or congestion, which could affect routing protocol performance. However, these were ruled out based on monitoring data showing stable link utilization and no significant increases in error rates. The focus then narrowed down to the configuration of the OSPF backbone area, given its central role in the network's routing stability.

## Resolution steps
1. Set ospf backbone area to 0.0.0.0
2. Restart ospfd on router 10.1.1.1
3. Adjust hello interval to 10 seconds
4. Verify neighbor count on router 10.1.1.2

## Post-mortem note
The ospf backbone area was misconfigured, causing routing instability. This misconfiguration led to the observed DNS resolution latency spike, as stable routing is a prerequisite for efficient name resolution. The swift identification and correction of this issue prevented further escalation and minimized the impact on services and users. The incident highlights the importance of meticulous network configuration and the value of thorough diagnostic procedures in identifying and resolving complex network issues.
