## Symptom
The incident began with reports of authentication failures across multiple services that rely on the SAML federation gateway. Users were unable to log in, receiving an error message indicating that their credentials were invalid. Initial observations suggested a directory sync lag might be causing stale group membership information, which in turn could lead to authentication issues due to outdated user data. However, as the incident progressed, it became clear that the problem was more specific to the SAML authentication flow rather than a general issue with user data synchronization.

Further investigation into the symptom revealed that the error messages were not consistent across all affected services, suggesting that the issue might be related to how each service configured its SAML settings rather than a uniform problem with the directory sync. Despite this variability, all errors pointed towards a failure in the authentication process at the SAML gateway level. The impact was significant, with a substantial portion of users unable to access critical applications and services.

Monitoring tools indicated a spike in authentication attempts around the time the incident started, followed by a sharp increase in error rates for SAML-based logins. This pattern suggested that the issue was not with the volume of requests but rather with the processing of those requests by the SAML gateway. The lack of successful authentications during this period further supported the hypothesis that the problem lay within the SAML authentication mechanism.

As the situation evolved, it became apparent that resolving the incident would require a deep dive into the SAML configuration and the interaction between the SAML gateway and the services relying on it for authentication. Given the complexity of SAML and its dependency on correctly configured metadata and certificates, the potential causes were numerous, and a systematic approach to diagnosis would be necessary.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential issues with the directory sync and group membership updates, given the initial symptom of stale user data. However, as more evidence was collected, attention shifted towards the SAML gateway and its configuration. One hypothesis considered was that the SAML metadata might be outdated or incorrectly configured, leading to authentication failures. To investigate this, the team used a `jwt.io equivalent decoder to inspect SAMLResponse`

Another hypothesis explored was the possibility of network connectivity issues between the SAML gateway and the identity provider (IdP) or service providers (SPs), which could prevent successful authentication. However, network checks and traceroutes did not reveal any issues that would support this hypothesis.

## Resolution steps
1. Restart SAML gateway service on port 8443
2. Set IdP entityID to https://idp.example.org/idp/shibboleth
3. Update SP metadata at /etc/saml/sp-metadata.xml
4. Verify LDAP connection with ldapsearch -H ldap://ldap.example.org:389
5. Test authentication with pam-test -a saml

## Post-mortem note
The SAML gateway's IdP entityID was misconfigured, causing authentication failures. This issue highlights the importance of regularly reviewing and validating SAML configurations to prevent such incidents. The resolution steps effectively addressed the problem, and implementing a more robust validation process for SAML metadata updates will help mitigate similar risks in the future.
