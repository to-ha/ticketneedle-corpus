# Major Incident — INC-2026-0058
* **Ticket ID:** INC-2026-0058
* **Reported:** 2026-02-28 07:08 UTC
* **Priority:** P1
* **Domain:** Network
* **Status:** Resolved

## Symptom
The incident began with reports of intermittent delays in outbound API calls, which were taking 5-10 seconds to complete due to DNS resolution stalls. This issue would temporarily resolve itself after a resolver cache flush, only to reappear minutes later. The pattern observed was that of asymmetric routing after a config push, where the return path for packets did not match the outbound path, causing confusion among routers and leading to these delays. Further investigation revealed that the DNS resolution was indeed the bottleneck, as flushing the resolver cache would immediately alleviate the symptoms, albeit temporarily.

Upon closer inspection, it became clear that the DNS resolution issue was not a simple matter of cache size or expiration but rather a more complex problem involving the interaction between the resolver and the upstream DNS servers. The fact that flushing the cache provided temporary relief suggested that the issue might be related to how the resolver was handling certain types of queries or how it was interacting with its upstream providers.

The impact of this incident was significant, as it affected the performance and reliability of critical API calls, potentially leading to timeouts, errors, and a poor user experience. Given the nature of the symptom, which involved DNS resolution and asymmetric routing, tools like Wireshark for packet capture and analysis, nft for firewall rule inspection, and MTR for tracing network paths were considered essential for diagnosing the root cause.

## Diagnosis steps and hypotheses
Initially, it was hypothesized that the issue might be due to a misconfiguration in the MPLS L3VPN setup, leading to incorrect routing decisions. However, after reviewing the config push history and verifying the VPN settings, this hypothesis was ruled out due to lack of evidence supporting any recent changes that could cause such behavior.

Another hypothesis considered was that the problem lay with the firewall rules, possibly blocking or incorrectly routing DNS traffic. This led to an inspection of the firewall configurations using nft, but no issues were found that could explain the DNS resolution stalls.

Further investigation involved looking into the DNS resolver's performance and its interaction with upstream servers. A key command used in this diagnosis was:
```
dig +trace example.com @192.0.2.1
```
This command helped in tracing the path of a DNS query and identifying any potential bottlenecks or misconfigurations in the resolution process.

## Resolution steps
1. Set negative-TTL to 60s in /etc/resolv.conf
2. Add secondary resolver at 192.0.2.53
3. Configure failover with timeout of 30s
4. Verify resolver cache size is at least 10000
5. Restart resolver service

## Post-mortem note
The root cause of the incident was determined to be: Recursive resolver hit upstream rate limit on example.com zone. This issue highlighted the importance of closely monitoring DNS resolution performance and having robust failover mechanisms in place to prevent such incidents from impacting service reliability. Following the implementation of the resolution steps, the DNS resolution times returned to normal, and the intermittent delays in outbound API calls were resolved.
