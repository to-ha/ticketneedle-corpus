# Major Incident — INC-2026-0063
- **Ticket ID:** INC-2026-0063
- **Reported:** 2026-03-26 00:45 UTC
- **Priority:** P1
- **Domain:** Database
- **Status:** Resolved

## Symptom
The primary SQL replica began experiencing replication lag that grew unbounded after the midnight cron job ran. This issue was first observed by monitoring tools, which alerted on the increasing lag time. As the lag continued to grow, database performance started to degrade, leading to slower query times and eventually causing errors for users attempting to write to the database.

Further investigation revealed that the replication lag was directly related to the number of connections being made to the primary SQL replica. It appeared that the connection limit had been reached, preventing new connections from being established and thus halting replication.

This symptom complex pointed towards a configuration issue with the primary SQL replica, specifically related to connection management.

## Escalation timeline
- 00:52 — L1 Database operator: Leila: She immediately began investigating the monitoring alerts and attempted to restart the replica to clear any temporary issues.
- 01:13 — L2 Database engineer: Hana: Hana took over the investigation, focusing on the database configuration and connection settings to identify the root cause of the replication lag.

## Diagnosis steps and hypotheses
Initial hypotheses centered around resource utilization and potential network issues. However, upon closer inspection using tools like `pidstat` to monitor process activity, it became clear that the issue was more related to how the database was handling connections. A key command used in diagnosis was:
```
pidstat -p 1234 -u 10
```
This helped in understanding the process-level resource utilization but did not directly point to the connection limit issue. It wasn't until a review of the database configuration files and connection settings that the true cause began to emerge.

## Resolution steps
1. Restart primary SQL replica on node 3
2. Set max_connections to 500 in postgresql.conf
3. Adjust pgbouncer.ini to use 4 worker processes
4. Raise shared_buffers to 2GB in postgresql.conf

## Post-mortem note
The primary SQL replica exceeded its connection limit due to misconfigured parameters. This incident highlights the importance of regularly reviewing database configuration settings, especially in environments where usage patterns can change significantly over time, such as after cron jobs that may temporarily increase database load.
