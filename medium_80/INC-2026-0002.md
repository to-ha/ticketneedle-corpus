## Symptom
The incident began with the observation that the Horizontal Pod Autoscaler (HPA) was scaling up the ingress controller deployment, but the pods never became Ready. This behavior was first noticed by the monitoring system, which alerted the team to investigate further. Upon closer inspection, it was found that a specific deployment was entering CrashLoopBackOff within 30 seconds of pod start. The pod logs showed a single line and then the container exited with code 137, indicating an out-of-memory (OOM) kill. This pattern suggested that the ingress controller was experiencing memory issues, causing the pods to crash and restart repeatedly.

As the team dug deeper, they noticed that the HPA was trying to scale up the deployment to meet the increasing load, but the pods were not becoming Ready due to the OOM kills. This created a cycle where the HPA would scale up, the pods would crash, and then the HPA would scale down, only to repeat the process again. The team realized that they needed to investigate the memory usage of the ingress controller to understand the root cause of the issue.

The monitoring system showed that the memory usage of the ingress controller was increasing steadily over time, with spikes in usage corresponding to the OOM kills. This suggested that the ingress controller was experiencing memory pressure, which was causing the pods to crash. The team decided to investigate further to determine the cause of the memory issues.

The team also noticed that the ingress controller was not responding to requests during the periods of high memory usage, resulting in errors for users trying to access the application. This highlighted the need to resolve the issue quickly to minimize the impact on users.

## Diagnosis steps and hypotheses
The team considered several hypotheses to explain the memory issues with the ingress controller. One hypothesis was that the Java Virtual Machine (JVM) was not configured correctly, leading to memory leaks. Another hypothesis was that the ingress controller was experiencing an unusual load pattern, causing the memory usage to spike. The team used various tools, including `helm` and `stern`, to investigate the issue.

To investigate the OOM kills, the team used the following command:
```
stern -n ingress-controller | grep OOMKill
```
This command showed that the OOM kills were indeed caused by memory issues, but it did not reveal the underlying cause. The team decided to investigate the JVM configuration and the memory limits set for the ingress controller.

## Resolution steps
1. Raise memory limit to 2 GiB in deployment config
2. Set -Xmx to 1500m for JVM headroom
3. Apply updated config with helm upgrade
4. Verify pod memory allocation with etcdctl

## Post-mortem note
Memory limit was reduced causing JVM OOMKill. The team realized that the memory limit for the ingress controller had been reduced, causing the JVM to run out of memory and resulting in OOM kills. By increasing the memory limit and configuring the JVM correctly, the team was able to resolve the issue and prevent future occurrences.
