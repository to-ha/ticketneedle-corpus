## Symptom
The incident began with reports of MFA push notifications being delivered but never accepted, resulting in failed authentication attempts for users trying to access protected resources. This symptom was first observed by the security operations team, who noticed an increase in authentication failure rates starting at 17:30 UTC. As the issue persisted, it became clear that the problem was not limited to a specific group of users or geographic location, but rather a widespread issue affecting all users relying on MFA push notifications for authentication. The security information and event management (SIEM) system detected an unusual spike in authentication failures, which triggered an alert to the L1 Security operations team. Further investigation revealed that users were receiving the push notifications, but the acceptance of these notifications was not being registered by the SAML federation gateway, leading to authentication failures.

As the incident evolved, the impact on business operations became more significant, with users unable to access critical applications and services. The support team started receiving a high volume of calls from frustrated users, which added to the urgency of resolving the issue quickly. The monitoring system, which tracks authentication metrics, showed a sharp increase in failed authentication attempts, confirming the widespread nature of the problem. However, the initial monitoring did not catch the root cause of the issue, requiring further in-depth analysis.

The user impact was substantial, with many users locked out of essential systems and unable to perform their duties. The business relied heavily on the seamless operation of the SAML federation gateway for secure access to its applications, making this incident particularly disruptive. As the hours passed, the pressure to resolve the issue grew, given the significant business impact and the number of affected users.

Given the complexity of the authentication flow and the involvement of multiple components, pinpointing the exact cause required a meticulous approach. The initial focus was on the MFA service itself, considering possibilities such as issues with the push notification delivery or problems with the user's device. However, as these potential causes were investigated and ruled out, the attention shifted towards the SAML federation gateway, given its critical role in the authentication process.

The investigation into the symptom involved reviewing logs from the SAML federation gateway, analyzing network traffic captures, and inspecting the configuration files for any recent changes or anomalies. These efforts aimed to identify any patterns or clues that could explain why the MFA push notifications were not being accepted, despite being delivered successfully to the users' devices.

## Diagnosis steps and hypotheses
Initial suspicions pointed towards a potential issue with the MFA service itself, such as a problem with push notification delivery or an error in the user's device configuration. To investigate this hypothesis, the team attempted to reproduce the issue using test accounts and monitored the network traffic to see if there were any anomalies in the communication between the user's device and the MFA service.

Another hypothesis considered was that there might be a misconfiguration in the SAML federation gateway that was preventing it from properly handling the MFA push notifications. This led to a review of the gateway's configuration files and logs to identify any recent changes or errors that could be contributing to the issue.

The team also suspected that there could be an issue with the clock skew between the SAML federation gateway and the MFA service, potentially causing the push notifications to expire before they could be accepted. To diagnose this, they checked the system clocks on both services to ensure they were synchronized.

As part of the diagnostic process, the following command was executed to query the LDAP directory for any synchronization issues:
```
ldapsearch -x -H ldap://localhost:389 -b dc=example,dc=com
```
This helped in verifying if there were any user synchronization problems that could be affecting the authentication process.

Further investigation involved using tools like `jwt.io` equivalent decoder to inspect the SAML assertions for any anomalies and `session-trace` to follow the authentication flow step by step. These tools provided valuable insights into how the authentication requests were being processed and helped in identifying where the issue was occurring.

Despite these efforts, the root cause remained elusive until a closer examination of the SAML federation gateway's configuration revealed a critical setting that was causing the timeouts. The actual root cause emerged after a thorough review of the gateway's logs and configuration files, which pointed towards an issue with the `idp_ttl` setting being too low.

## Resolution steps
1. Set idp_ttl to 3600 in /etc/saml/gateway.conf
2. Restart saml-gateway service with --debug flag
3. Update entity_id in metadata.xml to https://sso.example.com/idp
4. Run ldapsearch with -D cn=admin,dc=example,dc=com to verify user sync
5. Adjust clock skew tolerance to 300 seconds in /etc/saml/gateway.conf

## Post-mortem note
The SAML federation gateway's idp_ttl was set too low, causing frequent timeouts. This issue was initially missed due to the focus on the MFA service and the complexity of the authentication flow. The resolution steps corrected the `idp_ttl` setting, ensured proper synchronization with the LDAP directory, and adjusted the clock skew tolerance, ultimately resolving the incident. To prevent similar issues in the future, the team plans to conduct regular reviews of the SAML federation gateway's configuration and implement additional monitoring to catch any potential problems before they affect users. Furthermore, enhancing the documentation of the authentication flow and the dependencies between different components will aid in faster diagnosis and resolution of future incidents.
