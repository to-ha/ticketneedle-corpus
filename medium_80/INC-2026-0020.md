## Symptom
The incident began with reports of object replication lag exceeding the SLA threshold. This was initially observed by the monitoring team, who noticed a significant increase in latency for write operations on the storage cluster. As the issue persisted, users began to report errors when attempting to access or update objects, indicating a potential problem with data consistency.

Further investigation revealed that the replication lag was not uniform across all nodes, suggesting a possible issue with the underlying storage infrastructure. The team used tools like `iostat` to analyze disk utilization and throughput, which showed elevated wait times and reduced throughput on affected nodes. This evidence pointed towards a performance bottleneck, potentially related to the SAN multipath driver configuration.

The monitoring dashboard displayed a clear spike in replication lag, with some nodes showing delays of over 30 minutes. This not only affected the availability of data but also raised concerns about data integrity, as updates were not being propagated in a timely manner. The impact was significant, with several critical applications relying on the storage cluster for their operations.

As the incident progressed, the team worked to isolate the cause and mitigate the effects. They applied temporary workarounds to reduce the load on the affected nodes and prioritized traffic to minimize the impact on users. Despite these efforts, the root cause remained elusive, necessitating a deeper dive into the configuration and performance of the SAN multipath driver.

## Diagnosis steps and hypotheses
Initial hypotheses centered around issues with disk performance, network connectivity, and configuration errors in the storage cluster. The team used `multipath -ll` to verify the multipath configuration and check for any issues with path prioritization or failover.
```
multipath -ll
```
This command provided valuable insights into the current state of the multipath setup but did not immediately reveal the root cause. Further investigation involved running `fio` benchmarks to assess storage performance under load and using `iostat` to monitor disk statistics in real-time.

One hypothesis considered was that the issue might be related to inadequate queue depth settings, leading to inefficient handling of I/O requests. Another possibility was that the polling interval for path checking was too low, causing unnecessary overhead and contributing to the bottleneck. However, each of these hypotheses required specific evidence to support or refute them, leading to a trial-and-error approach with configuration adjustments and performance testing.

## Resolution steps
1. Restart multipathd service with -v flag
2. Set max_queue_depth to 64 in /etc/multipath.conf
3. Increase polling_interval to 5 seconds
4. Run fio with --numjobs=16 and --size=10G
5. Verify path priority with multipath -ll

## Post-mortem note
The SAN multipath driver was misconfigured, causing I/O bottlenecks. This incident highlighted the importance of regularly reviewing and optimizing storage configurations to prevent performance issues. The resolution steps implemented not only resolved the immediate problem but also provided a basis for future improvements in storage cluster efficiency and reliability.
