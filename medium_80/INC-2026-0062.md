## Symptom
During the release window, the database experienced a significant spike in deadlocks. This was first observed by monitoring tools, which alerted on an unusual increase in wait events related to locks. Upon further investigation, it became clear that the issue was impacting user transactions, leading to errors and timeouts. The deadlocks seemed to be concentrated around specific tables, suggesting a potential issue with data maintenance or concurrent access patterns.

The spike in deadlocks was sudden and unexpected, occurring right after a deployment that included changes to database schema and queries. Initial thoughts pointed towards the new code as the culprit, but it was crucial to understand the underlying cause to apply the correct fix. Deadlocks of this nature can be complex, involving multiple factors such as transaction duration, lock contention, and system resources.

Further analysis using pidstat and views similar to pg_stat_activity revealed high CPU usage by the database processes and an increase in disk I/O wait times, indicating that the system was under stress. This information hinted at a resource bottleneck but didn't directly point to the root cause of the deadlocks.

## Diagnosis steps and hypotheses
Initial hypotheses centered around the recent code changes causing inefficient queries or transactions that led to lock contention. However, upon reviewing the changes and running tests, it became apparent that the code itself wasn't the primary cause. Another hypothesis considered was disk space or resource limitations leading to slower transaction times and thus more opportunities for deadlocks. To investigate further, the team executed a command to check for any ongoing VACUUM operations:
```
psql -c 'SELECT * FROM pg_stat_activity WHERE query LIKE "%VACUUM%"'
```
This revealed that autovacuum was not running as expected, hinting at a maintenance issue rather than a code or resource problem.

## Resolution steps
1. Set autovacuum_vacuum_scale_factor to 0.1
2. Restart autovacuum daemon with -d option
3. Run VACUUM on tables with bloat factor over 2
4. Adjust maintenance_work_mem to 128MB

## Post-mortem note
The autovacuum daemon failed to run due to insufficient memory. This oversight led to significant table bloat, which in turn caused the deadlocks during the release window when transactional load was high. Adjusting the autovacuum settings and manually running VACUUM on affected tables resolved the issue, highlighting the importance of regular database maintenance and monitoring of autovacuum performance.
