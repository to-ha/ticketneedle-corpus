## Symptom
The incident began with reports of increased write latency on one of the volumes in the distributed filesystem. Specifically, users noticed that after a snapshot was taken, the write latency would jump significantly, causing delays in their workflows. This increase in latency was first observed by monitoring tools, which triggered an alert to the on-call team. Upon further investigation, it became clear that this issue was not limited to a specific user or application but was rather a widespread problem affecting all writes to that particular volume.

Initial observations suggested that the issue might be related to the snapshot process itself, possibly due to the way metadata was being handled during and after the snapshot. However, as more data was collected, it became apparent that the root cause might be more complex and related to the underlying storage infrastructure. The symptom complex revolved around the abnormal increase in write latency post-snapshot, with no immediate indication of hardware failure or software misconfiguration.

The impact of this increased latency was significant, affecting not just the performance of applications relying on this volume but also causing frustration among users who experienced delays. Given the critical nature of storage performance for ongoing operations, resolving this issue quickly was of the utmost importance. The on-call team immediately began digging deeper into the storage layer to identify any anomalies or potential bottlenecks that could explain the sudden increase in write latency.

As the investigation continued, focus shifted towards understanding the behavior of the distributed filesystem metadata server, given its central role in managing data across the storage infrastructure. It was crucial to determine if the metadata server was functioning correctly and if there were any issues with how it was handling metadata updates, especially in the context of snapshots.

## Diagnosis steps and hypotheses
Diagnosing the issue involved considering several hypotheses, each of which was tested and eventually ruled out based on the evidence collected. One initial hypothesis was that the problem lay with the physical disks themselves, possibly due to a hardware failure or impending failure. To investigate this, the team used `smartctl` to check the health of the disks, as shown in the command:
```
smartctl -H /dev/sda
```
This command provided insights into the disk's health but did not reveal any critical issues that would explain the write latency problem.

Another hypothesis considered was that the multipathing configuration might be faulty, leading to inefficient use of available paths and thus increased latency. The `multipath -ll` command was used to verify the WWID and ensure that multipathing was correctly configured. However, this also did not yield any evidence pointing to a misconfiguration as the root cause.

The team also explored the possibility of issues with the snapshot process itself, potentially causing metadata inconsistencies or locks that could lead to increased latency. This involved running `rsync --dry-run -avz /mnt/data/` to test the sync process and ensure that data was being correctly replicated across the distributed filesystem.

## Resolution steps
1. Restart metadata server on node3 with -f flag
2. Set max_elevations to 10 in /etc/metadata.conf
3. Run smartctl -H /dev/sda to check disk health
4. Verify multipath -ll output for correct WWID
5. Run rsync --dry-run -avz /mnt/data/ to test sync

## Post-mortem note
The distributed filesystem metadata server failed due to disk errors on node3. This failure led to a cascade of issues, including the increased write latency observed after a snapshot was taken. The resolution steps taken not only addressed the immediate symptom by restarting the metadata server and adjusting configuration settings but also ensured that the underlying disk health issue was identified and could be properly mitigated to prevent future occurrences.
