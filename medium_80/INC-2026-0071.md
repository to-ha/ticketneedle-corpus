## Symptom
The incident began with reports from real users experiencing errors while interacting with the application, despite synthetic probes indicating that everything was functioning correctly. This discrepancy between synthetic and real-user experiences suggested an issue that wasn't immediately apparent through automated monitoring. Further investigation revealed that the errors were related to tracing data not being collected properly, which hinted at a problem with the tracing collector. The fact that synthetic probes were reporting green suggested that the basic functionality of the application was intact, but there was a deeper issue affecting real users.

As the incident progressed, it became clear that the tracing collector was not sending data as expected, leading to gaps in the tracing information available for debugging and performance analysis. This made it challenging to diagnose the root cause of the errors experienced by real users, as the usual detailed tracing data was not available. The impact was significant because without this data, the engineering team was flying blind, trying to identify and fix issues based on limited information.

The observation that synthetic probes were unaffected while real users suffered errors pointed towards an issue that was specific to the production environment or user interactions that synthetic tests did not replicate. This symptom complex indicated a need to dive deeper into the tracing collector's configuration and performance to understand why it was failing to collect and send tracing data for real user interactions.

Given the critical nature of tracing data for both debugging and performance optimization, the lack of this data significantly hindered the team's ability to respond effectively to the incident. It underscored the importance of ensuring that monitoring tools, including the tracing collector, are functioning correctly to provide comprehensive insights into system behavior.

## Diagnosis steps and hypotheses
Initial hypotheses included issues with network connectivity affecting the tracing collector's ability to send data, problems with the tracing collector's configuration that might prevent it from collecting data correctly, or even resource constraints on the server hosting the tracing collector. To investigate these hypotheses, the team used various tools, including `tsdb-cli` and `trace-query`, to examine the state of the tracing collector and its interactions with the application.

One key diagnostic step involved running the command:
```
tsdb-cli diagnose --config /etc/tracing/config.yaml
```
This command provided insights into the tracing collector's configuration and any potential issues that might be affecting its operation. However, despite these efforts, the initial hypotheses did not yield a clear root cause, suggesting that the issue was more complex than initially thought.

Further investigation focused on the tracing collector's performance under load and its memory usage patterns, considering whether excessive memory usage could lead to failures in data collection. This line of inquiry ultimately proved fruitful, as it highlighted the critical role of memory management in the tracing collector's operation.

## Resolution steps
1. Restart tracing collector on port 55678
2. Set max_span_age to 30m in /etc/tracing/config.yaml
3. Increase cache_size to 1024MB for tsdb-cli queries
4. Run trace-query with --verbose flag for detailed logs

## Post-mortem note
The tracing collector failed to flush spans due to excessive memory usage. This root cause explained why real users were experiencing errors while synthetic probes, which typically exert less load on the system, continued to report green. The resolution steps effectively addressed this issue by ensuring the tracing collector had sufficient resources and was properly configured to handle the load, thereby restoring the collection of vital tracing data.
