## Symptom
The distributed filesystem metadata server was observed to fail over every few hours, causing brief disruptions to storage services. This pattern was consistently noted by the monitoring system and reported by users attempting to access stored data during these failovers. The failovers themselves were automatic, but the frequency at which they occurred indicated an underlying issue that needed to be addressed.

- 10:16 — L2 Platform engineer: Kai began reviewing the metadata server logs for any error patterns.
- 11:01 — L3 Platform lead: Kenji took over the investigation, focusing on potential configuration issues.
- 11:45 — Engineering manager: Ines oversaw the escalation and ensured resources were allocated for a swift resolution.

## Diagnosis steps and hypotheses
Initial hypotheses focused on network connectivity issues and metadata server configuration errors. However, upon further investigation using tools like `fio` and `multipath -ll`, it became clear that the issue was more related to the server's performance under load. A key diagnostic step involved running 
```
fio --filename=/mnt/data --size=1G --rw=read
```
to simulate read workload on the metadata server, which helped in understanding the server's behavior under stress.

## Resolution steps
1. Restart metadata server on node 3
2. Set journal_size to 1024M in /etc/metadata.conf
3. Run fio --filename=/mnt/data --size=1G --rw=read
4. Verify multipath -ll shows all 4 paths online

## Post-mortem note
The distributed filesystem metadata server crashed due to insufficient journal space. This incident highlights the importance of regularly reviewing configuration settings and performance metrics to prevent such crashes. Future preventative measures will include more frequent checks on journal space and automated alerts for low disk space conditions.
