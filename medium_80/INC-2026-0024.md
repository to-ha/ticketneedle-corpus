## Symptom
The incident began with reports of DNS resolution latency spikes, where queries would take 5-10 seconds to resolve. This slowdown was observed in outbound API calls, which would intermittently stall due to delayed DNS resolution. The issue seemed to temporarily resolve itself after a resolver cache flush, only to reappear later.

Further investigation revealed that the affected systems were experiencing these delays consistently, with no clear pattern of affected domains or query types. The symptom complex suggested a potential issue with the DNS resolution process itself, rather than a specific domain or service being unavailable.

Monitoring data confirmed the spike in DNS resolution latency, with some queries taking up to 10 seconds to complete. This was significantly higher than the expected resolution time of milliseconds.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential network congestion or packet loss causing the DNS resolution delays. However, analysis of network logs and traffic patterns did not support this hypothesis. 
```
mtr --show-ips example.com
```
was used to investigate potential issues with DNS query routing, but it did not reveal any obvious problems.

## Resolution steps
1. Edit /etc/resolv.conf to include edns-buffer-size=1232
2. Set max_udp_size to 1232 in /etc/nft/nftables.conf
3. Restart the resolver daemon with systemctl restart nft
4. Verify resolver cache with nft -s list ruleset

## Post-mortem note
EDNS0 buffer-size mismatch caused fragmentation that the upstream resolver dropped silently. This incident highlights the importance of ensuring consistent EDNS0 buffer sizes across all DNS resolvers and upstream servers to prevent similar issues in the future.
