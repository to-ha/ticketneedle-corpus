# Major Incident — INC-2026-0048
* **Ticket ID:** INC-2026-0048

* **Priority:** P2
* **Domain:** Database
* **Status:** Resolved

## Symptom
The primary SQL replica experienced a significant slowdown under sustained write load, causing autovacuum to cancel repeatedly. This led to a buildup of dead tuples, further exacerbating the performance issue. Monitoring alerted on elevated query latency, prompting investigation.

Initial observations suggested that the replica was struggling to keep up with the write workload, resulting in canceled autovacuum processes. This pattern was consistent across multiple monitoring cycles, indicating a persistent issue rather than a transient anomaly.

Further examination of the SQL replica's metrics revealed a correlation between the canceled autovacuum processes and spikes in write traffic. This correlation hinted at a potential connection between the write load and the autovacuum cancellations.

## Diagnosis steps and hypotheses
Initial hypotheses centered around resource contention and query optimization issues. To better understand the system's behavior, the `pidstat` command was used to monitor process-level metrics:
```
pidstat -p $(pg_ctl get pid) 1
```
This revealed significant wait times on disk I/O, pointing towards a potential bottleneck in storage performance. However, further analysis using `explain analyze` and `pg_stat_activity` views suggested that the issue was more closely related to connection management and database configuration.

## Resolution steps
1. Restart primary SQL replica with max_connections set to 500
2. Set shared_buffers to 2GB in postgresql.conf
3. Run VACUUM on tables with bloat factor over 1.5
4. Adjust checkpoint_timeout to 30 minutes

## Post-mortem note
The primary SQL replica ran out of connections due to excessive query load. This incident highlights the importance of regularly reviewing database configuration and adjusting parameters to match changing workload demands.
