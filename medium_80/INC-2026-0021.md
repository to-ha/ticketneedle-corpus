# Major Incident — INC-2026-0021
* **Ticket ID:** INC-2026-0021
* **Reported:** 2026-03-21 21:22 UTC
* **Priority:** P1
* **Domain:** Containers / Kubernetes
* **Status:** Resolved

## Symptom
The incident began with reports of pods stuck in CrashLoopBackOff after a node reboot. This pattern was consistently observed across multiple deployments, indicating a widespread issue rather than an isolated problem. Upon further investigation, it became clear that the affected pods were all utilizing the same container runtime, suggesting that the root cause might be related to this component. The symptom manifested as repeated crashes of the pods, with the container runtime failing to properly manage the pod lifecycle. As a result, the pods were unable to achieve a running state, leading to service disruptions.

The impact of this symptom was significant, as it affected multiple services that relied on the Kubernetes cluster for deployment and management. Users reported errors and timeouts when attempting to access these services, highlighting the need for swift resolution. The operations team was alerted to the issue through monitoring alerts, which detected the abnormal pod behavior and triggered notifications.

Initial observations suggested that the issue might be related to resource allocation or configuration problems within the container runtime. However, without further diagnosis, it was unclear whether this was indeed the root cause or merely a symptom of a deeper problem. The team decided to escalate the issue to gather more expertise and resources to tackle the problem.

As the investigation progressed, it became apparent that the container runtime was experiencing difficulties managing memory allocation for the pods. This led to speculation about potential memory leaks or misconfigurations that could be causing the pods to crash. Despite these hypotheses, the actual root cause remained elusive, requiring further diagnostic efforts to uncover.

## Diagnosis steps and hypotheses
The diagnosis process involved several hypotheses, each of which was tested and eventually ruled out. One of the initial hypotheses was that the issue stemmed from a misconfiguration in the kustomize settings, potentially leading to incorrect image versions being deployed. However, upon reviewing the kustomize config, no such misconfigurations were found. Another hypothesis suggested that etcd might be experiencing issues, affecting the Kubernetes cluster's ability to manage pod states accurately. While etcdctl checks were performed, they did not reveal any inconsistencies that could explain the observed behavior.

To further investigate the memory allocation issue, the team executed the following command to check for out-of-memory errors:
```
stern -n default --since 1h | grep 'out of memory'
```
This command provided insight into whether memory constraints were indeed contributing to the pod crashes. Although it offered valuable information on recent errors, it did not directly point to the root cause, necessitating additional investigation.

## Resolution steps
1. Restart container runtime with --log-level=debug flag
2. Set /etc/container/runtime.conf max_memory to 4096
3. Update kustomize config to use image version 1.21.0
4. Run etcdctl to check for inconsistent container state

## Post-mortem note
Container runtime failed due to insufficient memory allocation. This root cause was ultimately identified through a combination of log analysis, configuration reviews, and targeted diagnostic commands. The resolution steps effectively addressed the issue by adjusting memory settings and ensuring the container runtime was properly configured. The incident highlighted the importance of closely monitoring resource allocation within container runtimes to prevent similar disruptions in the future.
