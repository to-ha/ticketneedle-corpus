# Major Incident — INC-2026-0050
* **Ticket ID:** INC-2026-0050
* **Reported:** 2026-04-13 14:54 UTC
* **Priority:** P2
* **Domain:** Containers / Kubernetes
* **Status:** Resolved

## Symptom
The incident began with reports of a Persistent Volume Claim (PVC) stuck in the Pending state after a storage class migration. This issue was observed by users attempting to deploy new pods, which were unable to start due to the unavailability of the requested storage. Monitoring tools also picked up on this anomaly, triggering alerts for the on-call team.

Further investigation revealed that the affected PVCs were all associated with a specific node, suggesting a node-level issue rather than a cluster-wide problem. The symptom was consistent across multiple deployments, indicating a systemic problem rather than an isolated incident.

* 15:43 — L2 Platform engineer: Mark took over the investigation, focusing on node-level configurations and storage class settings.
* 16:31 — L3 Platform lead: Sven was engaged to provide deeper technical insight into the Kubernetes storage subsystem and potential interactions with the migrated storage class.

## Diagnosis steps and hypotheses
Initial hypotheses centered around issues with the storage class migration itself or potential misconfigurations in the Kubernetes cluster. However, upon further investigation, including running `kubectl describe node node-3` to inspect the node's configuration and status, it became clear that the problem was more localized.
``` 
kubectl describe node node-3
```
This command provided crucial insights into the node's current state and helped narrow down the potential causes.

## Resolution steps
1. Restart kubelet on node 3
2. Set --kubeconfig to /etc/kubernetes/admin.conf
3. Update node 3 config with kustomize build /path/to/config
4. Verify node 3 status with stern -n default

## Post-mortem note
The kubelet on node 3 was not configured correctly. This oversight led to the PVCs being stuck in the Pending state, as the node was unable to properly manage storage requests. Thankfully, the resolution steps were effective in correcting the configuration and restoring normal operation to the affected node.
