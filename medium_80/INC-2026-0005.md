## Symptom
The incident began with reports of asymmetric routing after a configuration push to the OSPF backbone area. This resulted in packets taking different paths for incoming and outgoing traffic, causing latency and packet loss. The issue was first observed by monitoring tools, which detected an increase in latency and packet loss on certain routes. As the incident progressed, users began to report connectivity issues and slow network performance.

Further investigation revealed that the asymmetric routing was caused by a mismatch in the OSPF area 0 network type configuration. The incorrect configuration led to the OSPF routers not forming the expected adjacencies, resulting in the asymmetric routing patterns. The monitoring tools were able to detect the issue due to the increased latency and packet loss, but the root cause of the problem was not immediately apparent.

The user impact of the incident was significant, with many users experiencing slow network performance and connectivity issues. The business impact was also notable, as the incident affected critical network services and applications. The incident highlighted the importance of careful configuration management and monitoring in preventing and detecting network issues.

The monitoring tools used to detect the issue included the metrics platform, which provided real-time visibility into network performance and latency. The SIEM also played a crucial role in detecting and alerting on the issue, allowing the network operations team to respond quickly and effectively. However, despite the best efforts of the monitoring tools, the root cause of the issue was not immediately apparent, and further investigation was required.

As the incident progressed, the network operations team worked to gather more information and troubleshoot the issue. They used tools such as `tcpdump` and `nft` to analyze network traffic and configuration, but the root cause of the problem remained elusive. It wasn't until the team dug deeper into the OSPF configuration that they began to suspect the issue was related to the area 0 network type.

## Diagnosis steps and hypotheses
The team considered several hypotheses to explain the asymmetric routing issue. One initial hypothesis was that the issue was caused by a problem with the OSPF hello packets not being sent correctly. To investigate this, the team used the command ```tcpdump -i eth0 -n -vv -s 0 -c 100 port 89``` to capture and analyze the OSPF packets on the network. However, the output of this command did not show any issues with the hello packets, ruling out this hypothesis.

Another hypothesis was that the issue was caused by a problem with the OSPF adjacency formation. The team investigated this by checking the OSPF adjacency tables and looking for any signs of adjacency formation issues. However, the tables showed that the adjacencies were forming correctly, ruling out this hypothesis.

The team also considered the possibility that the issue was caused by a problem with the network topology or the OSPF area configuration. They used `dig` to check the network topology and verify that the OSPF areas were configured correctly. However, the output of `dig` did not show any issues with the network topology or OSPF area configuration, ruling out this hypothesis.

As the team continued to investigate, they began to suspect that the issue was related to the OSPF area 0 network type configuration. They checked the configuration and found that it was set to broadcast, which was incorrect for the network topology. This led them to suspect that the issue was caused by the incorrect OSPF area 0 network type configuration.

The team then considered the hypothesis that the issue was caused by a problem with the nft rules not allowing OSPF packets on the interface. They investigated this by checking the nft rules and looking for any signs of issues with the OSPF packet filtering. However, the rules showed that the OSPF packets were being allowed correctly, ruling out this hypothesis.

Finally, after ruling out the other hypotheses, the team discovered that the root cause of the issue was indeed related to the OSPF area 0 network type configuration. The incorrect configuration led to the asymmetric routing patterns and the resulting network issues.

## Resolution steps
1. Set ospf area 0 network type to point-to-point
2. Restart ospfd service on router 10.1.1.1
3. Update nft rule 100 to allow ospf packets on interface eth0
4. Adjust ospf hello interval to 10 seconds on all backbone routers

## Post-mortem note
The ospf area 0 network type was incorrectly set to broadcast. This incorrect configuration led to the asymmetric routing patterns and the resulting network issues. The root cause of the issue was missed initially due to the complexity of the OSPF configuration and the network topology. In the future, the team will work to improve the monitoring and configuration management processes to prevent similar issues from occurring. Additionally, the team will provide training on OSPF configuration and troubleshooting to ensure that all team members have a thorough understanding of the protocol and its potential issues.
