# Major Incident — INC-2026-0072

* **Reported:** 2026-03-03 13:56 UTC
* **Priority:** P3
* **Domain:** Storage
* **Status:** Resolved

## Symptom
The filesystem metadata server was observed to fail over every few hours, causing disruptions to object storage bucket replication. This issue was first noticed by the monitoring team, who reported seeing errors in the metadata server logs indicating a loss of connectivity to the storage nodes. As the failover occurred, users attempting to access or upload data to the object storage buckets would experience timeouts or receive error messages. The frequency of these failovers increased over the course of several hours, leading to a significant impact on the overall availability of the storage service.

Further investigation revealed that the failovers were not due to hardware issues, as the servers themselves remained operational and responsive. However, the metadata server's inability to maintain a stable connection to the storage nodes was causing a ripple effect, leading to the observed replication issues. The monitoring team also noticed that the disk usage on the storage nodes was higher than usual, which might have contributed to the instability of the connections.

Given the nature of the symptom, it seemed likely that the issue was related to either a configuration problem or a resource constraint affecting the metadata server or the storage nodes. The fact that the failovers were recurring suggested a periodic or threshold-based trigger, possibly tied to the load or usage patterns of the object storage service.

The impact of this issue was significant, as it affected not only the availability of data within the object storage buckets but also the overall performance of applications relying on these buckets for their operation. Users were unable to upload new data, and in some cases, they were unable to retrieve existing data due to the replication failures.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential network connectivity issues or hardware failures affecting the storage nodes. However, as more data was collected, it became clear that the problem was more likely related to the configuration or resource allocation of the object storage service itself. One of the key commands used during the diagnosis was:
```
s3cmd ls -v s3://bucket1
```
This command helped in understanding the current state of the bucket and identifying any inconsistencies in the replication status.

Another hypothesis considered was that the issue might be due to disk health problems on the storage nodes, given the higher-than-usual disk usage observed. However, preliminary checks using tools like `iostat` and `smartctl` did not reveal any immediate issues with the disks themselves.

## Resolution steps
1. Restart object storage service on node3
2. Set replication_factor to 3 in /etc/object_storage.conf
3. Run s3cmd sync --delete-removed /data/bucket1/
4. Check disk health with smartctl -H /dev/sda

## Post-mortem note
Object storage bucket replication failed due to incorrect configuration. This incident highlights the importance of regularly reviewing and validating the configuration settings for critical services like object storage to prevent such issues. The resolution steps taken not only addressed the immediate problem but also ensured that the service was more resilient against similar failures in the future by adjusting the replication factor and verifying the health of the underlying storage.
