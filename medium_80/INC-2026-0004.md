- **Reported:** 2026-03-19 10:01 UTC
- **Priority:** P3
- **Domain:** Platform infrastructure
- **Status:** Resolved

## Symptom
The incident began with a noticeable increase in the message broker queue depth, which grew unbounded over time. This symptom was first observed by the monitoring system at 10:01 UTC, triggering an alert that was immediately escalated to the L1 Platform support team. As the queue depth continued to rise, it started to impact service discovery, causing delays and timeouts for dependent services. The growth of the queue depth was steady and relentless, indicating a potential issue with the internal DNS resolution that the message broker relies on for service discovery.

Further investigation into the monitoring data revealed that the issue was not limited to a single service but was affecting multiple services across the platform. This suggested a systemic problem rather than an isolated issue with a particular service. The metrics platform showed a significant spike in DNS query failures around the time the queue depth began to increase, further supporting the hypothesis that DNS resolution was at the heart of the problem.

The user and business impact of this incident was substantial. As services began to timeout and fail, users experienced errors and delays when attempting to access various platform features. The business impact included not only the immediate loss of functionality but also the potential long-term effects on user trust and satisfaction. The operations team worked closely with the development teams to understand the dependencies between services and how the DNS issue was cascading through the system.

The monitoring system played a critical role in identifying the issue early on, but it became clear that additional tools and insights were needed to diagnose the root cause of the problem. Tools like `registry-gc`, `broker-admin`, and `runner-logs` were utilized to gather more information about the state of the message broker, service registrations, and the runtime environment of the affected services.

As the incident progressed, it became evident that a deeper dive into the DNS resolution process was necessary. This involved analyzing DNS query logs, inspecting the configuration of the DNS servers, and verifying the health of the DNS infrastructure. The focus on internal DNS for service discovery helped to narrow down the potential causes and guided the investigation towards issues related to DNS caching, query timeouts, and service registration.

## Diagnosis steps and hypotheses
The team initially suspected that the issue might be related to a recent change in the service registration process. To investigate this hypothesis, they reviewed the commit history and deployment logs but found no evidence supporting this theory. They then moved on to consider whether the problem could be due to a network connectivity issue between the message broker and the DNS servers. Diagnostic steps included running `tcpdump` on the network interfaces of both the message broker and the DNS servers to capture and analyze DNS traffic. However, the captured traffic did not show any signs of network-level issues.

Another hypothesis considered was that the DNS servers themselves might be experiencing performance issues or were under heavy load, leading to query timeouts. To test this, the team used `dig` to manually query the DNS servers from different locations within the infrastructure. The results showed consistent response times, ruling out server overload as a cause.

The team also explored the possibility of a misconfiguration in the message broker's DNS client settings. They inspected the configuration files and compared them against known good configurations but found no discrepancies.

To further diagnose the issue, the team executed the following command to query the DNS server directly:
```
dig +short example.service @10.0.1.5
```
This test was designed to check if the DNS server was correctly resolving the service name. The results from this test helped to narrow down the potential causes but still did not point to a specific root cause.

As the investigation continued, the team considered the hypothesis that there might be an issue with the DNS cache expiration timer, potentially causing stale records to be served. However, without direct evidence, this remained a speculative cause. It wasn't until later, after reviewing the DNS server logs and configuration more closely, that the team began to suspect an issue related to DNS caching.

After ruling out several hypotheses and gathering more evidence, the team finally began to focus on the DNS cache expiration timer as the potential root cause. This was based on a combination of the symptoms observed, the results from diagnostic tests, and a deeper review of the DNS server configuration.

## Resolution steps
1. Restart dns-cache service on node 10.0.1.5
2. Set dns_cache_ttl to 300 in /etc/dns/config.yaml
3. Run registry-gc with --dns-cache flag to clean up stale records
4. Verify dns record consistency using dig +short example.service

## Post-mortem note
The dns cache expiration timer was set too low, causing service discovery failures. This root cause was initially missed because the team focused on more obvious potential issues such as network connectivity and server performance. In retrospect, a closer examination of the DNS configuration and cache behavior earlier in the investigation might have led to a quicker resolution. Following this incident, the team has planned to review and adjust the DNS cache expiration timer settings across all DNS servers to prevent similar issues in the future. Additionally, there will be an emphasis on enhancing the monitoring system to include more specific checks for DNS cache health and performance.
