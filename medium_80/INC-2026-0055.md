# Major Incident — INC-2026-0055
- **Ticket ID:** INC-2026-0055
- **Reported:** 2026-01-25 10:48 UTC
- **Priority:** P2
- **Domain:** Database
- **Status:** Resolved

## Symptom
The application threads were blocked due to a saturated connection pool, causing delays in query execution. This symptom was first observed by the monitoring system, which alerted the team to a potential issue with the database connection pooler. Further investigation revealed that the connection pool was indeed full, and no new connections could be established.

As the incident progressed, users began to report timeouts and errors when attempting to access the application. The error messages indicated that the database was unavailable, which suggested a problem with the connection pooler. The team focused on resolving the connection pool issue to restore application functionality.

The monitoring system provided valuable insights into the connection pool utilization, showing a steady increase in usage leading up to the saturation point. This data helped the team understand the scope of the issue and plan their response accordingly.

## Diagnosis steps and hypotheses
The team considered several hypotheses, including a misconfigured connection pooler and an unexpected increase in application traffic. To investigate these hypotheses, the team used various diagnostic tools, including `pidstat` to monitor system resources. Specifically, they ran the following command to monitor the connection pooler process:
```
pidstat -p $(pgrep pgbouncer) 1 10
```
This command provided valuable insights into the connection pooler's resource utilization, helping the team rule out some of the initial hypotheses.

## Resolution steps
1. Restart connection pooler with max_client_conn set to 500
2. Set pool_mode to transaction in /etc/pgbouncer.ini
3. Increase server_idle_timeout to 60 seconds
4. Reduce max_db_connections to 200 in pgbouncer logs

## Post-mortem note
The connection pooler exceeded its maximum client connections. This root cause was identified through a combination of monitoring data and diagnostic investigations, which revealed the need for adjustments to the connection pooler configuration to prevent similar incidents in the future.
