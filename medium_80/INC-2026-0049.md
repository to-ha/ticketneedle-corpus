## Symptom
The CI pipelines began to stall consistently on the same stage across all repositories, indicating a potential issue with the secrets manager. This symptom was first observed by the development team and reported to the support team. Upon further investigation, it became clear that the stalling pipelines were all waiting for secrets to be rotated, suggesting a problem with the secrets manager's ability to handle connections.

The stalling of CI pipelines on the same stage across different repositories pointed towards a common dependency or service that was failing. Given that secrets rotation is a critical step in many CI/CD processes, the focus naturally turned to the secrets manager as the potential source of the issue.

Initial observations from monitoring tools showed an increase in error rates related to connection timeouts when attempting to access or rotate secrets. This observation further supported the hypothesis that the secrets manager was at the heart of the problem.

## Diagnosis steps and hypotheses
Initial hypotheses included issues with network connectivity to the secrets manager or problems with the underlying database. However, upon reviewing logs and running diagnostic commands such as 
```
kubectl logs secrets-manager -c debug
```
it became clear that the connections to the secrets manager were being exhausted, leading to the stalling of pipelines. The team considered hypotheses related to configuration issues or external factors causing the connection exhaustion but focused on direct evidence pointing to the secrets manager's performance under load.

## Resolution steps
1. Restart secrets manager with --debug-log flag
2. Set max_connections to 50 in /etc/secrets/config.yaml
3. Run registry-gc with --dry-run flag to identify stale secrets
4. Delete expired secrets older than 90 days using broker-admin

## Post-mortem note
The secrets manager failed to rotate certificates due to exhausted connections. This root cause was addressed through the resolution steps taken, ensuring that the secrets manager could handle the required number of connections and rotate certificates as needed. The incident highlighted the importance of monitoring connection usage and regularly cleaning up stale or expired secrets to prevent similar issues in the future.
