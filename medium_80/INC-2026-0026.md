# Major Incident — INC-2026-0026

## Symptom
The incident began with a noticeable increase in write latency on one of the object storage volumes, specifically after a snapshot was taken. This latency spike was observed by the monitoring system and reported by users attempting to upload data to the affected bucket. Initially, the issue seemed isolated to this single volume, but as the incident progressed, it became clear that the replication process for the entire object storage bucket was impacted.

Further investigation revealed that the increased latency was not solely due to the snapshot process itself but was exacerbated by an underlying issue with how data was being replicated across nodes. The symptom complex revolved around this replication issue, which manifested as delayed writes and eventual failures in synchronizing data across the storage cluster.

The monitoring system alerted on high latency thresholds, prompting an initial response from the on-call team. As users began to experience errors when trying to upload files, it became apparent that the issue was not just a transient problem but a significant incident affecting the availability and integrity of the object storage service.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential issues with the storage hardware or network connectivity between nodes. However, as diagnosis progressed, it became clear that these were not the primary causes. One key command used in the diagnosis was:
```
rsync --dry-run -avz /data/bucket/
```
This helped in understanding the replication process without actually transferring data, which assisted in pinpointing configuration issues rather than problems with the data transfer process itself.

## Resolution steps
1. Restart rsync on node 1 with --bwlimit=100
2. Set replication.factor to 3 in /etc/object-storage.conf
3. Run multipath -ll on node 2 to verify path status
4. Execute smartctl -H /dev/sda to check disk health

## Post-mortem note
Object storage bucket replication failed due to incorrect configuration. This incident highlights the importance of regularly reviewing and testing configuration settings, especially after updates or changes to the storage environment, to prevent such failures. The swift escalation and collaborative effort among the teams ensured that the issue was resolved promptly, minimizing the impact on users.
