## Symptom
The incident began with reports of ingress returning 502 errors for a single backend service. This symptom was first observed by monitoring tools, which alerted the on-call team to a spike in error rates. As the team investigated, it became clear that the issue was not limited to a single ingress controller, but was instead a cluster-wide problem affecting all incoming traffic to the specified backend service. Users attempting to access the service via the ingress resource were consistently receiving 502 errors, indicating a failure in the communication between the ingress controller and the backend pods.

Further investigation revealed that the backend pods themselves were healthy and responding correctly to direct requests, suggesting that the issue lay with the ingress configuration or the networking setup within the cluster. The error rates remained steady over time, with no signs of fluctuation or intermittent recovery, pointing towards a persistent configuration issue rather than a transient problem.

The impact of this symptom was significant, as the affected backend service is critical for the platform's functionality. The error rate of 100% for incoming requests via ingress meant that no users could access the service, leading to a complete loss of functionality for this component of the platform. This had cascading effects on dependent services and overall user experience.

Given the nature of the error (502 Bad Gateway), the initial focus was on the networking and ingress components, looking for any misconfigurations or issues that could prevent the ingress controller from successfully proxying requests to the backend pods. The fact that direct requests to the backend pods were successful suggested that the problem was likely related to the CNI plugin or the ingress controller's configuration.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential issues with the ingress controller itself, such as incorrect annotations or misconfigured paths. However, as the investigation progressed, attention shifted towards the CNI plugin due to its critical role in networking within the Kubernetes environment. The team considered the possibility of a version mismatch or an incorrect configuration that could prevent proper communication between pods and the ingress controller.

One key diagnostic step involved checking the etcd configuration for any inconsistencies or misconfigurations related to the network settings. This led to the execution of the following command to inspect the current etcd settings:
```
etcdctl get /registry/network/config --prefix=true
```
The output from this command provided valuable insights into the current state of the network configuration, helping to narrow down the potential causes.

Despite these efforts, the initial hypotheses did not yield a clear root cause, necessitating a deeper dive into the CNI plugin's behavior and configuration. It was only after considering the plugin's settings and how they interacted with the etcd configuration that the team began to form a clearer picture of the issue.

## Resolution steps
1. Restart CNI plugin with --cni-conf-dir=/etc/cni/net.d
2. Set etcd key /registry/network/config to {'bridge': 'br0'}
3. Apply kustomize overlay with stern logging level set to 3
4. Update cni-plugin config map with bridge-mtu: 1500
5. Validate CNI plugin version is 1.0.0 or higher

## Post-mortem note
The CNI plugin was misconfigured with an incorrect bridge interface. This root cause, once identified and addressed through the resolution steps, fully restored the functionality of the ingress resource and the affected backend service. The experience highlighted the importance of thorough configuration validation, especially for critical components like the CNI plugin, and underscored the value of systematic troubleshooting in identifying and resolving complex issues within Kubernetes environments.
