## Symptom
The incident began with reports of pods failing to become Ready after being scaled up by HPA. Further investigation revealed that a specific deployment was entering CrashLoopBackOff within 30 seconds of pod start. Pod logs showed a single line and then the container would exit with code 137, indicating an unexpected termination. This pattern was consistent across multiple attempts to start the pods.

The symptom was first observed by monitoring tools, which alerted on the high rate of pod failures. The team then used `kubectl` and `stern` to investigate the pod logs and understand the cause of the failures.

## Diagnosis steps and hypotheses
Initial hypotheses focused on issues with the node's networking configuration, given the pods' inability to become Ready. The team used `crictl` to inspect the pod's configuration and check for any errors. One key command used was:
```
crictl inspect --output json pod-id
```
This helped to rule out issues with the pod's configuration and pointed towards a problem with the node's CNI bridge.

## Resolution steps
1. Drain node with kubectl drain --delete-local-data --force node-name
2. Restart CNI daemon with systemctl restart cni-plugin
3. Verify CNI bridge config at /etc/cni/net.d/10-bridge.conf
4. Re-add node to pool with kubectl uncordon node-name

## Post-mortem note
Node had a stale CNI bridge after a kernel upgrade, causing new pods to timeout. This incident highlights the importance of regularly checking and updating node configurations after upgrades to prevent similar issues in the future.
