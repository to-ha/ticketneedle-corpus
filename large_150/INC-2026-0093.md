## Symptom
The incident began with reports of feature flag evaluation latency spikes during peak hours. Users noticed that the application was taking longer than usual to respond, and in some cases, the flags were not being evaluated correctly. This resulted in inconsistent behavior across the platform, causing frustration for users and impacting business operations. The monitoring system caught the latency spikes, but initially, it was unclear what was causing them. As the incident evolved, the latency spikes became more frequent and prolonged, affecting a larger number of users.

The symptoms were first observed during a period of high traffic, which made it challenging to determine the root cause. The team initially thought that the issue might be related to the increased load, but as they dug deeper, they realized that the problem was more complex. The feature flag evaluation latency spikes were not only affecting user experience but also causing issues with downstream services that relied on the flags.

Further investigation revealed that the latency spikes were correlated with a specific set of feature flags, which were being evaluated more frequently than others. This led the team to suspect that there might be an issue with the message broker, which was responsible for handling the feature flag evaluations. However, at this point, it was still unclear what was causing the problem, and the team needed to gather more information.

The monitoring system provided valuable insights into the issue, showing that the latency spikes were not uniform and were affecting specific parts of the application more than others. This suggested that the problem might be related to the way the feature flags were being evaluated or the underlying infrastructure. The team decided to investigate further, using tools like vault-style CLI, flag-history, and runner-logs to gather more information.

As the incident continued to evolve, the team realized that the latency spikes were not just affecting user experience but also causing issues with the overall stability of the platform. The inconsistent behavior caused by the feature flag evaluation latency spikes was making it challenging to identify the root cause, and the team needed to think creatively to resolve the issue.

## Diagnosis steps and hypotheses
The team considered several hypotheses to explain the feature flag evaluation latency spikes. One of the initial suspicions was that the issue might be related to the increased load on the platform. To investigate this, they checked the metrics for the message broker, looking for any signs of overload. However, the metrics showed that the broker was handling the load without issues, which ruled out this hypothesis.

Another hypothesis was that there might be a problem with the feature flag evaluation logic itself. The team reviewed the code and tested it using flag-history and runner-logs, but they did not find any issues. This led them to suspect that the problem might be related to the underlying infrastructure, specifically the message broker.

To investigate this further, the team used the vault-style CLI to check the configuration of the message broker. They ran the following command to check the connection limits:
```
vault read /config/broker | grep max_connections
```
The output showed that the connection limits were set too low, which could cause latency spikes during peak hours. This was a promising lead, and the team decided to investigate further.

The team also considered the possibility that the issue might be related to the way the feature flags were being stored and retrieved. They checked the vault configuration and found that it was set up correctly, but they did realize that the connection limits were not being updated dynamically. This meant that during peak hours, the message broker might become overwhelmed, causing latency spikes.

As the team continued to investigate, they realized that the root cause of the issue was more complex than initially thought. They had to consider multiple factors, including the feature flag evaluation logic, the message broker configuration, and the underlying infrastructure. It was not until they took a step back and looked at the bigger picture that they were able to identify the root cause.

The team's investigation eventually led them to suspect that the message broker was overwhelmed due to exceeded connection limits. This hypothesis was supported by the evidence from the vault configuration and the metrics for the message broker. The team realized that they needed to update the connection limits and adjust the configuration to prevent similar issues in the future.

## Resolution steps
1. Restart message broker with --max-connections 500
2. Set broker.config.max_message_size to 10240
3. Update vault at path /config/broker with new connection limits
4. Clear flag --enable-flow-control to prevent further backpressure

## Post-mortem note
The root cause of the incident was Message broker overwhelmed due to exceeded connection limits. This issue was missed initially because the team was focused on the feature flag evaluation logic and did not consider the message broker configuration as a potential culprit. In hindsight, it is clear that the connection limits were set too low, and the team should have caught this earlier. To prevent similar issues in the future, the team will review the message broker configuration and adjust the connection limits dynamically based on traffic. Additionally, the team will implement more robust monitoring and alerting to catch potential issues before they become incidents.
