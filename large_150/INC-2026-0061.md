## Symptom
The incident began with reports of intermittent connectivity issues between two sites, characterized by an MTU black hole. This meant that packets larger than a certain size were being dropped, causing disruptions to various services relying on DNS resolution. Initially, the symptoms seemed sporadic and were not consistently reproducible, making it challenging to pinpoint the exact cause. As the issue persisted, it became clear that the problem was related to the recursive DNS resolver cluster, which was failing to resolve hostnames for certain domains. The monitoring system caught occasional spikes in DNS resolution latency, but these were not immediately alarming, as they were within the expected range for a busy network. However, as the day progressed, the frequency and duration of these spikes increased, indicating a worsening problem.

The user impact was significant, with many services relying on the affected DNS resolver cluster becoming unavailable or sluggish. This included internal web applications, email services, and even some external services that depended on the organization's DNS infrastructure. The business impact was substantial, as critical operations were hindered by the inability to access necessary resources. Despite the monitoring system's initial failure to raise a significant alarm, the sheer volume of user complaints and service disruptions eventually led to the incident being escalated.

Further investigation into the symptom revealed that the issue was not limited to a specific set of domains or services but was rather widespread, affecting any service that relied on the recursive DNS resolver cluster for name resolution. This suggested a problem with the DNS infrastructure itself rather than with individual services or applications. The MTU black hole phenomenon was observed consistently across different sites and networks, pointing towards a deeper issue within the network or DNS configuration.

As the incident continued to affect operations, the focus shifted towards identifying the root cause and implementing a solution as quickly as possible. The intermittent nature of the issue made it challenging, but the consistent impact on DNS resolution services kept the investigation centered on the recursive DNS resolver cluster.

The initial observable pattern of MTU black holes between two sites was just the tip of the iceberg, revealing a more complex issue with the DNS infrastructure. The fact that monitoring initially missed the severity of the issue highlighted the need for more sensitive alerts and better monitoring of critical DNS services.

## Diagnosis steps and hypotheses
Initially, the team suspected a network configuration issue, possibly related to MTU settings on routers or switches, which could cause the observed black holes. To investigate this, they used `iperf3` to test network throughput and `nft` to inspect firewall rules for any potential packet filtering issues. However, these tests did not reveal any obvious configuration problems that would explain the widespread DNS resolution failures.

Another hypothesis considered was a problem with the DNS resolver software itself, potentially a bug or an incompatibility issue with recent updates. The team attempted to reproduce the issue in a controlled environment but was unable to do so, which made this hypothesis less likely.

The team also explored the possibility of a DDoS attack targeting the DNS infrastructure, which could overwhelm the recursive DNS resolver cluster and cause resolution failures. However, analysis of traffic patterns and volumes did not support this hypothesis, as there was no evidence of abnormal traffic that would indicate a targeted attack.

To further diagnose the issue, the team used various network diagnostic tools, including:
```
mtr --tcp --report -c 10 10.0.1.5
```
This helped in understanding the network path and identifying any potential bottlenecks or issues along the way, though it did not directly point to the root cause of the DNS resolution problem.

Another considered hypothesis was a resource constraint issue with the DNS resolver cluster, such as insufficient memory or CPU resources, which could lead to failed resolutions under load. While this seemed plausible, initial checks on resource utilization did not indicate any shortages that would explain the severity of the observed issues.

As the investigation continued, the focus narrowed down to issues directly related to the recursive DNS resolver cluster's configuration and performance. It became clear that the root cause was more nuanced than initially thought and required a deeper understanding of the DNS infrastructure and its current state.

The actual root cause emerged after a thorough review of the DNS resolver cluster's configuration files and performance metrics, indicating an issue with how the cluster was handling concurrent requests and resource allocation.

## Resolution steps
1. Restart dns-resolver service on node 10.0.1.5
2. Set max_concurrent_requests to 500 in /etc/dns/config.yaml
3. Increase cache_size to 1024MB in /etc/dns/config.yaml
4. Run iperf3 -c 10.0.1.5 -u -b 100M to test UDP throughput

## Post-mortem note
The recursive DNS resolver cluster was overwhelmed by excessive concurrent requests. This root cause was initially missed due to the complexity of the issue and the lack of clear indicators in the monitoring data. The resolution steps, including restarting the dns-resolver service, adjusting max_concurrent_requests, increasing cache_size, and testing UDP throughput, effectively addressed the problem and restored normal operation to the DNS infrastructure. In retrospect, more detailed monitoring of the DNS resolver cluster's performance and resource utilization could have led to a quicker identification of the root cause. Follow-up actions include reviewing and enhancing the monitoring setup for critical DNS services to prevent similar incidents in the future. Additionally, the organization will conduct regular stress tests on the DNS infrastructure to ensure it can handle peak loads without failing.
