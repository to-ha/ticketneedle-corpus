## Symptom
The incident began with reports of pods not becoming Ready after the Horizontal Pod Autoscaler (HPA) had scaled up the number of replicas. This issue was first noticed by monitoring tools, which alerted on the discrepancy between the expected and actual number of Ready pods. As the day progressed, the problem became more pronounced, leading to increased latency and error rates for users. The symptom complex revolved around this single observable pattern: HPA scales up but pods never become Ready. This led to a significant impact on service availability and performance.

Further investigation revealed that the cluster was experiencing issues with pod scheduling, which seemed to be related to the autoscaling mechanism. The lack of Ready pods despite sufficient resources being available pointed towards an issue with either the pod lifecycle management or the scaling logic itself. The monitoring data showed a clear correlation between the scaling events and the onset of the problem, suggesting that the root cause might be linked to how the cluster was handling the scaled-up replicas.

The operations team started receiving alerts around the same time, indicating a rise in errors related to pod creation and scheduling. This prompted an immediate response to understand and rectify the situation. Given the nature of the issue, it was clear that the problem was not with the application code itself but rather with how the Kubernetes cluster was managing resources and scaling.

As the incident unfolded, it became apparent that the focus needed to be on the interaction between the HPA, the cluster autoscaler, and the pod scheduling mechanism. The fact that pods were being created but not becoming Ready suggested a potential issue with resource allocation or with the health checks configured for the pods. However, since the pods were not even reaching a Running state where they could be health-checked, the issue seemed more fundamental, likely related to how the cluster was scaling and managing its resources.

## Diagnosis steps and hypotheses
Initial hypotheses included issues with the HPA configuration, problems with the pod scheduling algorithm, or even network connectivity issues preventing pods from becoming Ready. However, as the team dug deeper, they realized that the cluster autoscaler might be at the heart of the problem, possibly due to a misconfiguration or a logical error in its scaling decisions.

One of the key diagnostic steps involved checking the logs of the cluster autoscaler and the HPA to see if there were any error messages or unusual patterns. This led to running commands like:
```
stern -n default cluster-autoscaler
```
to get real-time logs from the cluster autoscaler, which provided crucial insights into its decision-making process.

The team considered several hypotheses, including a faulty HPA scaling policy, issues with node resource allocation, or even a bug in the Kubernetes version being used. However, each of these was systematically ruled out through a combination of log analysis, configuration reviews, and experimental scaling tests.

## Resolution steps
1. Restart cluster autoscaler with --v=4 flag
2. Set scale-down-unneeded-time to 10m in cluster autoscaler config
3. Update kustomize configuration to include autoscaler max-node-count: 10
4. Run crictl to verify pod eviction policy
5. Check stern logs for autoscaler error messages

## Post-mortem note
Cluster autoscaler was not scaling down due to misconfigured timeout. This root cause explained the observed behavior of pods not becoming Ready after scaling up, as the cluster was essentially stuck in an inappropriate scaling state. The resolution steps directly addressed this issue by adjusting the autoscaler's configuration and ensuring it could properly scale down when needed, thereby resolving the incident and restoring normal service operation.
