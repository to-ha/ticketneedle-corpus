- **Ticket ID:** INC-2026-0099

- **Status:** Resolved

## Symptom
The incident began with a noticeable increase in write latency on one of the storage volumes, specifically after a snapshot was taken. This increase in latency was observed through monitoring tools and reported by users attempting to write data to the affected volume. Further investigation showed that the latency spike was consistent and directly impacted the performance of applications relying on this storage volume.

## Escalation timeline
- 00:47 — L1 Platform support: Maya immediately started reviewing the system logs to identify any errors or warnings related to the storage volume.
- 01:27 — L2 Platform engineer: Imani took over the investigation, focusing on the network and storage configuration to find any potential bottlenecks or misconfigurations.

## Diagnosis steps and hypotheses
Initial hypotheses included a potential issue with the storage node's configuration or a problem with the network connectivity affecting the volume. To investigate these hypotheses, the `multipath -ll` command was used to verify path redundancy:
```
multipath -ll
```
This helped rule out issues with the multipathing configuration. Further diagnosis involved checking disk utilization and verifying bucket replication.

## Resolution steps
1. Restart storage node 3
2. Set replication_factor to 3 in /etc/storage/config.yaml
3. Run multipath -ll to verify path redundancy
4. Check iostat -x for disk utilization above 80%
5. Verify bucket replication with s3cmd sync --stat

## Post-mortem note
The object storage bucket replication failed due to insufficient redundancy. This incident highlights the importance of regularly reviewing storage configurations to ensure they meet the required levels of redundancy and performance.
