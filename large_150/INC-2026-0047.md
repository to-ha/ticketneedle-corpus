## Symptom
The object replication lag began to grow past the SLA threshold, indicating a potential issue with the storage system. This growth was observed by the monitoring tools and reported by users who rely on real-time data replication. The replication lag is a critical metric, as it directly affects the availability and consistency of data across the system.

As the incident unfolded, it became clear that the replication lag was not a transient issue but rather a persistent problem that required immediate attention. The growth rate of the lag suggested that the underlying cause was related to the storage subsystem, possibly involving the SAN multipath driver.

Further investigation revealed that the issue was not limited to a specific subset of users or data but was instead a system-wide problem. This suggested that the root cause was likely related to a configuration or operational issue rather than a hardware failure or software bug affecting a particular component.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential issues with the storage hardware or network connectivity. However, as diagnostic efforts progressed, attention turned to the SAN multipath driver configuration. A key command used in the diagnosis was:
```
iostat -x /dev/mapper/mpath0
```
This command provided insight into the I/O statistics for the multipath device, helping to rule out hardware issues and pointing towards a configuration problem.

## Resolution steps
1. Restart multipathd service with debug flag
2. Set max_fds to 1024 in /etc/multipath.conf
3. Reload multipath configuration with iostat -x
4. Verify path priority with fio --filename=/dev/mapper/mpath0

## Post-mortem note
The SAN multipath driver was misconfigured, causing I/O errors. This issue highlights the importance of regularly reviewing and updating configuration settings for critical system components to prevent similar incidents in the future.
