# Major Incident — INC-2026-0026
* **Ticket ID:** INC-2026-0026
* **Reported:** 2026-03-10 19:27 UTC
* **Priority:** P2
* **Domain:** Storage
* **Status:** Resolved

## Symptom
The incident began with a noticeable increase in write latency on one of the object storage volumes, specifically after a snapshot was taken. This latency spike was first observed by the monitoring system, which triggered an alert due to the deviation from the expected baseline performance. As the issue evolved, it became clear that the increased latency was not only affecting the performance of applications relying on this volume but also causing delays in data replication across the storage cluster. Users reported slower than usual response times when attempting to upload or access data, indicating a direct business impact. The monitoring system caught the initial symptom through its real-time metrics collection, specifically highlighting an unusual pattern in disk I/O wait times. However, it initially missed the root cause of the issue, which was more nuanced and related to the configuration of the object storage service rather than a simple resource utilization problem.

Further investigation into the symptom revealed that the write latency was consistently higher on this particular volume compared to others, even after the snapshot process had completed. This suggested that the issue might not be transient or related solely to the snapshot process but could be indicative of a more persistent problem with the storage configuration or the underlying hardware. The team observed that the affected volume was part of a larger storage pool that was designed for high availability and redundancy, which made the performance discrepancy even more puzzling. Given the complexity of the storage system and the potential for cascading failures, it was crucial to identify and address the root cause promptly to prevent further degradation of service.

The initial hypothesis was that the issue might be related to hardware performance or a misconfiguration at the disk level, given the focus on write latency. The team considered the possibility of faulty disks or incorrect settings that could impede optimal performance. To explore this hypothesis, engineers began by examining the health of the disks using `smartctl` and checking for any signs of failure or suboptimal performance. They also reviewed the configuration settings for the storage pool to ensure that everything was set up as intended for high-performance writing.

As the investigation continued, it became apparent that the problem was not solely related to disk health or basic configuration settings. The team then shifted its focus towards the object storage service itself, considering factors such as replication settings, network connectivity, and the overall architecture of the storage system. This involved a deeper dive into the logs and metrics of the object storage service to identify any anomalies or patterns that could point towards the root cause.

The monitoring system played a critical role in identifying the initial symptom but was less effective in pinpointing the exact cause. It highlighted the increased latency and provided some insights into system resource utilization but did not offer a clear indication of what was driving the problem. This underscored the importance of having a robust monitoring setup that can not only detect performance issues but also provide actionable insights into their causes.

## Diagnosis steps and hypotheses
The team initially suspected a hardware failure or a disk configuration issue due to the write latency symptom. To diagnose this, they ran `smartctl` checks on the affected disks and reviewed disk settings for any potential misconfigurations. However, these checks did not reveal any issues, ruling out the initial hypothesis.

Next, the team considered network connectivity problems as a potential cause, given the distributed nature of the storage system. They used tools like `ping` and `traceroute` to test connectivity between nodes but found no issues, which led them to rule out network problems as the root cause.

Another hypothesis was that the object storage service's replication factor might be misconfigured, leading to inefficient data distribution across the cluster. To investigate this, the team examined the configuration files for the object storage service. Before diving into the specifics of the replication settings, they decided to check the health of the storage paths on all nodes using the following command:
```
multipath -ll
```
This step provided valuable insights into the state of the storage infrastructure but did not directly point to a misconfigured replication factor as the cause.

The team also explored the possibility of issues with the snapshot process itself, considering whether it might be locking resources or causing contention on the affected volume. They reviewed snapshot logs and timing but found that the snapshot had completed without errors and was not a contributing factor to the ongoing latency issue.

As the diagnosis progressed, the team began to suspect that the root cause might be more complex and related to how data was being managed within the object storage service. They started to investigate settings related to data replication and distribution across the cluster, looking for any configuration that might lead to inefficient use of resources or bottlenecks in data processing.

## Resolution steps
1. Restart object storage service on node 3 with --force flag
2. Set replication factor to 3 in /etc/objectstorage/config.yaml
3. Run rsync --dry-run -avz /mnt/data/ to test replication sync
4. Verify multipath -ll output for healthy storage paths on all nodes
5. Adjust smartctl -a /dev/sdb settings to optimize disk performance

## Post-mortem note
The object storage bucket replication failed due to a misconfigured replication factor. This root cause was initially missed because the focus was on symptoms related to hardware performance and network connectivity rather than the configuration of the object storage service itself. In retrospect, a more detailed examination of the service's configuration settings earlier in the investigation could have led to a quicker resolution. Following this incident, the team has planned a review of the object storage service's configuration to ensure that all settings are optimized for performance and redundancy, and to implement additional monitoring that can detect similar configuration issues before they cause significant impact. The experience highlighted the importance of considering all potential causes of an issue, including those related to service configuration, and of having a structured approach to diagnosis that systematically rules out hypotheses based on evidence.
