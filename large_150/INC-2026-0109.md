# Major Incident — INC-2026-0109
- **Ticket ID:** INC-2026-0109
- **Reported:** 2026-05-03 04:10 UTC
- **Priority:** P3
- **Domain:** Storage
- **Status:** Resolved

## Symptom
The backup job for the distributed filesystem completed successfully, but the verification step failed, indicating data inconsistencies. This issue was first noticed by the monitoring system, which triggered an alert due to the failure of the verification process. Further investigation revealed that the backup job itself had run without errors, suggesting the problem lay in the verification or the data integrity post-backup.

The symptom complex revolved around this singular observable pattern, with no other related issues such as performance degradation or access problems reported at the time. The focus, therefore, remained on understanding why the verification of the backup was failing given the successful completion of the backup job.

Given the nature of the issue, tools like `fio` for testing disk I/O, `rsync --dry-run` for checking data consistency without modifying the destination, and `iostat` for monitoring system input/output statistics were considered for diagnosing the problem.

## Escalation timeline
- 04:14 — L1 Platform support: Imani began reviewing the backup logs to identify any potential issues or errors that might have been overlooked.
- 04:31 — L2 Platform engineer: Mark started analyzing the system's performance metrics around the time of the backup and verification processes to see if there were any resource bottlenecks or unusual activity.
- 05:27 — L3 Platform lead: Lukas took over the investigation, focusing on the distributed filesystem's metadata server, suspecting that the issue might be related to data consistency or replication.

## Diagnosis steps and hypotheses
Initial hypotheses included the possibility of a transient network issue affecting data transfer during the verification step or a problem with the backup target itself. However, these were ruled out after reviewing network logs and performing a dry run of the backup process to a different target, which succeeded. Another hypothesis considered was that the load on the system was too high during the backup, causing the verification to fail due to inconsistent data access. To test this, the command ```
fio --readwrite=randrw --size=1G /mnt/data
``` was executed to simulate heavy I/O load and observe if it could induce similar verification failures.

## Resolution steps
1. Restart metadata server on node 3
2. Set fs.metadata.replica.count to 5
3. Run fio with --numjobs=10 on /mnt/data
4. Verify disk usage with iostat -x on /dev/sda1

## Post-mortem note
Metadata server failed to replicate due to insufficient replicas. This root cause explanation aligns with the resolution steps taken, particularly adjusting the replica count and verifying system performance post-adjustment. The incident highlighted the importance of regularly reviewing configuration settings for critical components like the metadata server in a distributed filesystem environment.
