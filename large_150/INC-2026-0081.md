# Major Incident — INC-2026-0081

* **Status:** Resolved

## Symptom
The incident began with reports of PVCs stuck in the Pending state after a storage class migration. This issue was first noticed by the monitoring team, who alerted the on-call engineer. Further investigation revealed that the pods associated with these PVCs were unable to connect to the network.

The pods were scheduled and running, but they could not reach external services or other pods within the cluster. This symptom suggested a networking issue, possibly related to the CNI plugin configuration.

As the incident progressed, more pods began to exhibit the same behavior, indicating a widespread problem with the networking setup.

## Diagnosis steps and hypotheses
Initial hypotheses focused on issues with the storage class migration itself or problems with the nodes' connectivity. However, as more information became available, the focus shifted towards the CNI plugin. A key command used in the diagnosis was:
```
kubectl get pods -o yaml | grep -i cni
```
This helped in understanding the current state of the CNI configuration across the pods.

## Resolution steps
1. Restart CNI plugin with --cni-conf-dir=/etc/cni/net.d
2. Set bridge.batch.size to 32 in /etc/cni/net.d/10-mynet.conf
3. Apply new config with kustomize build /path/to/config
4. Verify pods can connect using crictl exec -it <pod_id> ping 8.8.8.8

## Post-mortem note
CNI plugin misconfiguration caused network instability. This incident highlights the importance of thoroughly testing configuration changes, especially those affecting critical components like networking. The root cause was identified and resolved through a combination of diagnostic efforts and knowledge of the CNI plugin's behavior.
