## Symptom
The incident began with reports of stale group membership, where users were unable to access resources they should have been granted access to due to directory sync lag. This issue was first noticed by the security team during a routine audit, where they found discrepancies between the expected and actual group memberships of several users. As the day progressed, more users reported issues, and the problem was escalated to the security operations team. The monitoring system caught the issue through alerts on directory replication delays, which initially seemed like a minor glitch but quickly escalated into a major incident. The symptoms were widespread, affecting multiple departments and causing significant disruptions to business operations.

The security team tried to troubleshoot the issue by checking the directory replication logs, but they didn't find any obvious errors. They then tried to verify the group memberships manually, which confirmed the sync lag. The team also checked the system metrics, which showed a significant increase in latency and error rates for directory replication requests. This information helped the team to focus their investigation on the directory replication process.

As the incident continued, the security team worked with the IT department to gather more information about the issue. They collected logs from the directory servers, which showed that the replication process was indeed delayed, but the cause was not immediately clear. The team also tried to reproduce the issue in a test environment, but they were unable to do so, which made it harder to diagnose the problem.

The monitoring system played a crucial role in detecting the issue, as it alerted the security team to the directory replication delays. However, the system did not provide enough information to diagnose the root cause of the problem, which made it necessary for the team to conduct a thorough investigation. The team used tools like pam-test and session-trace to gather more information about the issue, but they still couldn't find the root cause.

The incident had a significant impact on business operations, as many users were unable to access the resources they needed to do their jobs. The security team worked closely with the IT department to resolve the issue as quickly as possible, but it took several hours to find and fix the root cause. During this time, the team had to implement temporary workarounds to mitigate the impact of the incident, which added to the complexity of the situation.

## Diagnosis steps and hypotheses
The team initially suspected that the issue might be related to network connectivity problems, as they had experienced similar issues in the past. They tried to ping the directory servers and check the network latency, but everything seemed normal. They then suspected that the problem might be related to the directory server configuration, so they checked the server settings and compared them to the documentation, but they didn't find any discrepancies.

Another hypothesis was that the issue might be related to the authentication protocol, as it had been updated recently. The team tried to verify the authentication configuration using pam-test, but it didn't reveal any issues. They also suspected that the problem might be related to the session management, so they used session-trace to analyze the session logs, but they didn't find any errors.

The team then tried to investigate the directory replication process more deeply, by checking the replication logs and verifying the replication interval. They used the following command to check the SSL certificates:
```
openssl s_client -connect dirsync-server:636 -showcerts
```
This command helped them to identify a potential issue with the SSL certificates, which they had not considered before.

As they dug deeper, they found that the directory replication failed due to misconfigured SSL certificates, which was not immediately apparent from the symptoms. The team had to try several different approaches before they were able to identify the root cause of the problem.

## Resolution steps
1. Restart directory replication service on node 3
2. Set replication interval to 300 seconds in /etc/dirsync.conf
3. Increase debug log level to 5 in /etc/dirsync.conf
4. Run pam-test with --verbose flag to verify auth config

## Post-mortem note
Directory replication failed due to misconfigured SSL certificates. This issue was missed initially because the symptoms were not immediately obvious, and the team had to try several different approaches before they were able to identify the root cause. In hindsight, the team should have checked the SSL certificates earlier, as this would have revealed the issue more quickly. To prevent similar incidents in the future, the team will review the directory replication configuration and update the monitoring system to include checks for SSL certificate issues. Additionally, the team will provide training to the security operations team on how to troubleshoot directory replication issues, including how to use tools like openssl s_client to verify SSL certificates.
