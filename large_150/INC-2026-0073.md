## Symptom
The incident began with reports of slow query performance on the read-replica pair, which was causing delays in data processing. Further investigation revealed that autovacuum was canceling under sustained write load, leading to an accumulation of dead tuples and increased disk usage. This, in turn, was causing queries to take longer to complete, resulting in a backlog of pending requests. As the issue persisted, monitoring alerts began to trigger, indicating a rise in latency and error rates.

The symptom complex was characterized by a significant increase in query execution times, often exceeding the expected thresholds. This was accompanied by a notable rise in disk usage, which was attributed to the accumulation of dead tuples. The affected read-replica pair was responsible for serving a substantial portion of the database workload, making the incident particularly impactful.

Upon closer inspection, it became apparent that the autovacuum cancelation was not an isolated event but rather a recurring issue. The database logs showed multiple instances of autovacuum being canceled due to the sustained write load, suggesting a deeper underlying problem. This observation helped focus the investigation on the interactions between the write load, autovacuum, and the read-replica pair's performance.

Given the specific nature of the symptom, the primary tools used for diagnosis included the psql equivalent client for executing queries and examining database state, explain analyze for understanding query performance, and pg_stat_activity-style views for monitoring current database activity. These tools provided valuable insights into the database's behavior and helped guide the diagnostic process.

## Diagnosis steps and hypotheses
Initial hypotheses focused on the possibility of inadequate database resources (e.g., insufficient RAM or CPU) leading to performance degradation under load. However, examination of the system metrics did not support this hypothesis, as resource utilization was within expected bounds. Another considered hypothesis was that the write load was exceptionally high, overwhelming the database's ability to process transactions efficiently. While the write load was indeed high, it was not unprecedented, and previous experience suggested that the database should have been able to handle it without such severe performance impacts.

Further investigation involved analyzing query plans using `EXPLAIN ANALYZE` to identify any inefficient queries that might be contributing to the problem. A key command used in this process was:
```
psql -c 'EXPLAIN ANALYZE SELECT * FROM large_table'
```
This helped in understanding the query execution plans and identifying potential bottlenecks. However, the queries themselves did not appear to be the primary cause of the issue, as they had not changed recently and were previously performing adequately.

## Resolution steps
1. Restart replica on host 10.1.2.3
2. Set max_connections to 100 in postgresql.conf
3. Run ANALYZE on tables with high row count
4. Adjust wal_sender_timeout to 60 seconds
5. Verify replica lag with pg_stat_replication

## Post-mortem note
The read-replica pair experienced excessive lag due to insufficient connections. This root cause was addressed through the resolution steps, which included adjusting database settings and ensuring that the replica was properly synchronized. The incident highlighted the importance of regularly reviewing database configuration and performance metrics to prevent similar issues in the future.
