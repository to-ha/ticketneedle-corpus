# Major Incident — INC-2026-0052
- **Ticket ID:** INC-2026-0052
- **Reported:** 2026-01-24 11:09 UTC
- **Priority:** P3
- **Domain:** Containers / Kubernetes
- **Status:** Resolved

## Symptom
The incident began with reports of Persistent Volume Claims (PVCs) being stuck in a Pending state after a recent storage class migration. This issue was first identified by the monitoring system, which alerted the on-call team to an unusual increase in the number of pending PVCs. Further investigation revealed that the affected PVCs were all associated with pods running in the cluster, and the pods were unable to start due to the lack of available persistent storage.

As the incident progressed, it became clear that the problem was not limited to a single namespace or application, but rather was a cluster-wide issue affecting multiple teams and services. The on-call team worked to gather more information about the affected PVCs and the storage classes they were associated with, in an effort to identify the root cause of the problem.

The stuck PVCs had a significant impact on the availability of applications running in the cluster, as many of them rely on persistent storage to function correctly. The incident resulted in errors and timeouts for users attempting to access these applications, leading to a degradation in overall service quality.

The monitoring system provided valuable insights into the issue, highlighting the rapid increase in pending PVCs and the corresponding decrease in available storage capacity. This data suggested that the cluster's storage resources were being overwhelmed, but did not provide a clear indication of the underlying cause.

## Diagnosis steps and hypotheses
Initial hypotheses focused on issues with the storage class migration, such as incorrect configuration or insufficient resources. However, as the investigation progressed, it became clear that the problem was more complex and likely related to the cluster autoscaler.

One potential cause considered was a misconfiguration of the cluster autoscaler, which could be preventing it from scaling properly in response to changes in storage demand. To investigate this further, the following command was used:
```
kubectl describe deployment cluster-autoscaler --namespace kube-system
```
This provided valuable information about the current state of the cluster autoscaler and its configuration, but did not reveal any obvious issues.

Another hypothesis was that the cluster autoscaler was not receiving accurate information about the available storage resources, which could be causing it to make incorrect scaling decisions. However, after reviewing the logs and configuration, it appeared that this was not the case.

## Resolution steps
1. Scale cluster autoscaler deployment to 3 replicas
2. Set maxNodesTotal to 10 in cluster autoscaler configmap
3. Update helm chart with autoscaler version 1.20.0
4. Restart cluster autoscaler pods with kubectl rollout restart
5. Verify autoscaler logs for scale up events with crictl logs

## Post-mortem note
The cluster autoscaler was not scaling properly due to outdated configuration. This issue highlights the importance of regularly reviewing and updating the cluster's configuration to ensure it remains aligned with changing requirements and resources. In this case, the outdated configuration prevented the cluster autoscaler from functioning correctly, leading to a cascade of issues that ultimately resulted in the stuck PVCs and degraded service quality.
