* **Domain:** Containers / Kubernetes
* **Status:** Resolved

## Symptom
During a rolling kernel upgrade, several nodes entered a NotReady state, prompting an alert from our monitoring system. The first sign of trouble was when the node-local DNS cache began to exhibit erratic behavior, causing pods to fail with DNS resolution errors. As the upgrade progressed, more nodes became affected, leading to a significant increase in error rates for services relying on these nodes.

Further investigation revealed that the issue was not directly related to the kernel upgrade itself but rather to how the node-local DNS cache handled the transient network disruptions that occurred during the upgrade process. The cache's inability to properly resolve hostnames resulted in a cascade of failures, ultimately leading to the nodes being marked as NotReady.

The impact was noticeable, with several critical services experiencing downtime. The operations team was alerted, and an initial assessment was conducted to determine the cause and potential remedies. Given the nature of the issue, it was clear that a deeper dive into the DNS caching mechanism and its configuration was necessary.

The symptom complex revolved around DNS resolution failures in the context of node-local caching during infrastructure maintenance. This specific scenario highlighted the importance of ensuring that all components of the Kubernetes cluster, including those responsible for DNS resolution, are resilient to transient disruptions and properly configured for optimal performance.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential misconfigurations in the Kubernetes setup or issues with the rolling upgrade process itself. However, as more data was collected, attention turned to the node-local DNS cache as a primary point of failure. 

One of the key diagnostic steps involved examining the current state of the node-local DNS deployment using the command:
```
k9s get deploy/node-local-dns -o yaml
```
This provided insights into the deployment's configuration and any recent changes that might have contributed to the issue.

Further investigation considered hypotheses around network connectivity issues, resource constraints on the nodes, and potential bugs in the DNS caching software. Each of these was explored through a combination of log analysis, network testing, and resource monitoring, but none proved to be the root cause.

## Resolution steps
1. Restart cache with --max-ttl 300
2. Set dns-cache-size to 1000 in /etc/kubernetes/node-local-dns.conf
3. Verify cache hit ratio with stern -n kube-system node-local-dns
4. Adjust --cache-max-concurrent 5 for better performance

## Post-mortem note
The node-local DNS cache was not properly configured and timed out frequently. This realization underscores the need for periodic reviews of critical component configurations to ensure they are optimized for the current operational demands. Following this incident, a review of our configuration management processes is planned to prevent similar issues in the future.
