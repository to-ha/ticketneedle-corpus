# Major Incident — INC-2026-0144
- **Ticket ID:** INC-2026-0144
- **Reported:** 2026-05-05 15:47 UTC
- **Priority:** P3
- **Domain:** Containers / Kubernetes
- **Status:** Resolved

## Symptom
The incident began with reports of ingress returning 502 errors for a single backend service. This symptom was consistent across multiple user requests, indicating a potential issue with the service's deployment or the underlying node infrastructure. Further investigation revealed that the affected service was running on node-1, which had been experiencing high pod allocation recently.

## Escalation timeline
- 15:56 — L1 Platform support: Jonas alerted the team to the growing number of user complaints about the 502 errors.
- 16:12 — L2 Platform engineer: Imani started reviewing the node's logs and metrics to identify any resource constraints or errors.
- 16:33 — L3 Platform lead: Tomas joined the investigation, focusing on the kubelet service's performance and configuration.

## Diagnosis steps and hypotheses
Initial hypotheses included a resource exhaustion scenario or a misconfiguration in the deployment. To investigate, the team used `stern` to inspect container logs, as seen in the command:
```
stern -n default --kubelet-port 10250
```
This helped in identifying stopped containers that could be contributing to the issue but did not directly point to the root cause.

## Resolution steps
1. Restart kubelet on node-1
2. Set --max-pods to 100 in /etc/kubernetes/kubelet.conf
3. Run crictl delete --force all stopped containers

## Post-mortem note
The node's kubelet service had crashed due to excessive pod allocation. This incident highlights the importance of monitoring pod allocation and adjusting resource limits accordingly to prevent similar crashes in the future.
