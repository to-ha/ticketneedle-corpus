## Symptom
The database team noticed a growing replication lag after the midnight cron job. This lag was causing delays in data consistency across the cluster. Upon further investigation, it became apparent that the connection pooler was struggling to manage the load. The replication lag was increasing unbounded, indicating a potential issue with the database's ability to handle concurrent connections.

The team observed that the lag started to grow significantly after a large batch of transactions were executed during the cron job. This suggested that the connection pooler might be overwhelmed by the sudden increase in database activity. The symptom was consistent across multiple nodes in the cluster, pointing towards a configuration or resource limitation issue rather than a node-specific problem.

Initial observations from `pg_stat_activity` views showed an unusually high number of idle transactions, which could be contributing to the connection pooler's struggles. However, without further diagnosis, it was unclear if this was the root cause or merely a symptom of a deeper issue.

## Diagnosis steps and hypotheses
The team considered several hypotheses, including a potential misconfiguration of the connection pooler, insufficient database resources, or issues with the cron job itself. To investigate these hypotheses, the team used various diagnostic tools, including `explain analyze` for query performance and `iostat` for disk usage patterns. A key command used in the diagnosis was:
```
psql -c 'SELECT * FROM pg_stat_activity WHERE state = "idle";'
```
This helped identify a large number of idle transactions that were holding onto connections, potentially causing the connection pooler to exhaust its available connections.

## Resolution steps
1. Restart connection pooler with max_connections=100
2. Set pool_mode to transaction in postgresql.conf
3. Increase shared_buffers to 512MB in postgresql.conf
4. Run VACUUM on idle_in_transaction_sessions table

## Post-mortem note
The connection pooler exhausted its available connections due to idle transactions. This incident highlights the importance of regularly reviewing database configurations and monitoring for potential bottlenecks, especially in high-transaction environments.
