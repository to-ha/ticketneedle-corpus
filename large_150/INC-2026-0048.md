* **Domain:** Containers / Kubernetes
* **Status:** Resolved

## Symptom
The incident began with reports of a specific deployment entering CrashLoopBackOff within 30 seconds of pod start. Further investigation revealed that pod logs showed a single line and then the container exited with code 137. This pattern was consistent across multiple attempts to restart the pods, indicating a deeper issue with the node's configuration or the deployment itself. The PVCs for these pods were also stuck in a Pending state after a recent storageclass migration, which might have contributed to the problem. However, the primary observable symptom remained the consistent failure of the containers to start properly.

As the issue persisted, it became clear that the problem was not limited to a single pod or deployment but was rather a node-wide issue affecting multiple workloads. The node's kubelet was identified as the potential culprit, given its role in managing pod lifecycles and interacting with the container runtime. The focus then shifted towards diagnosing the kubelet's behavior and identifying any configuration issues or errors that could be causing the CrashLoopBackOff.

The symptom complex pointed towards a communication or configuration issue between the kubelet and either the container runtime or the network components, given the DNS timeout errors observed in some of the pod logs. This hinted at a potential problem with the node's network setup or the CNI (Container Network Interface) configuration, which could be preventing containers from resolving necessary hostnames and thus causing them to exit prematurely.

Given the recent storageclass migration, there was also consideration of whether the changes might have indirectly affected network policies or CNI configurations. However, the direct symptom of containers failing to start and the associated DNS timeout errors kept the focus on the node's network and kubelet configuration.

## Diagnosis steps and hypotheses
Initial hypotheses included issues with the container runtime, problems with the node's network configuration, or conflicts arising from the recent storageclass migration. The team attempted to verify the CNI bridge status and inspect container configurations using `crictl` for more insights into the container runtime environment. A key command used during this phase was:
```
crictl inspect --output json
```
This helped in understanding the container's configuration and runtime environment but did not directly point to the root cause. The investigation also involved checking kubelet logs for any errors or warnings related to network setup or container management.

Given the DNS timeout errors, there was a strong suspicion of a network configuration issue, potentially related to the CNI setup. However, initial checks did not reveal any obvious misconfigurations, leading the team to consider other hypotheses, including potential issues with the node's kernel after a recent upgrade and how it might interact with the CNI bridge.

## Resolution steps
1. Drain node with kubectl drain --delete-local-data --force --ignore-daemonsets
2. Restart CNI daemon with systemctl restart cni
3. Verify CNI bridge with ip link show cni0
4. Re-add node to pool with kubectl uncordon

## Post-mortem note
The root cause of the incident was identified as a stale CNI bridge after a kernel upgrade, causing DNS timeout. Node had a stale CNI bridge after kernel upgrade, causing DNS timeout. This highlighted the importance of verifying network configurations after significant system changes, such as kernel upgrades, and ensuring that all components, including the CNI setup, are properly updated and restarted as necessary. The resolution steps effectively addressed the issue by refreshing the node's configuration and ensuring the CNI bridge was properly set up, allowing containers to start correctly and resolving the CrashLoopBackOff issue.
