- **Status:** Resolved

## Symptom
The incident began with reports of SAML assertions being rejected as expired, despite the clocks on all relevant systems being in sync. This issue was first observed by users attempting to access protected resources, who were met with error messages indicating that their session had expired. Further investigation revealed that the problem was not limited to a specific group of users or a particular resource, but rather seemed to be affecting all users who had authenticated via SAML within a certain time frame.

As the issue persisted, monitoring tools began to pick up on the pattern, with error rates for SAML authentication spiking significantly. The error messages themselves were consistent, citing an expired session as the reason for the failure. This suggested that the issue was related to the management of session tokens, rather than a problem with the SAML assertions themselves.

The impact of this issue was significant, as it effectively prevented users from accessing protected resources. This not only affected user productivity but also raised concerns about the security and reliability of the authentication system. Given the critical nature of this system, it was essential to resolve the issue as quickly as possible.

Initial observations pointed towards a potential issue with session token management, given the nature of the error messages and the fact that clock sync was confirmed to be correct. This focused the initial troubleshooting efforts on the components responsible for managing session tokens, including the session token cache.

## Diagnosis steps and hypotheses
Initial hypotheses included the possibility of a clock skew issue, despite initial reports suggesting that clocks were in sync. However, given the consistency of the error messages regarding expired sessions, attention turned towards the session token cache and its management. One of the key diagnostic steps involved using `session-trace` to monitor the session token cache behavior and identify any potential issues with how sessions were being managed.

Another hypothesis considered was a problem with the SSL/TLS handshake process, given the role of SAML assertions in authentication. To investigate this, the command ```
openssl s_client -connect localhost:443 -session_reused
``` was used to test the SSL/TLS connection and verify if session reuse was functioning correctly. However, this did not yield any evidence pointing towards an issue with the handshake process.

Further investigation into the session token cache behavior and its configuration led to a focus on the cache's timeout settings and how they might be contributing to the observed issue. This involved reviewing logs and metrics related to the cache's performance and looking for any indicators of misconfiguration or overload.

## Resolution steps
1. Clear session token cache at /var/lib/sessions
2. Set cache timeout to 3600 seconds in /etc/session.conf
3. Restart session service with --force-reload flag
4. Verify cache size with session-trace -c 10

## Post-mortem note
The session token cache became overloaded due to incorrect timeout settings. This issue highlights the importance of regularly reviewing and updating configuration settings, especially in critical systems like authentication. The resolution steps taken not only addressed the immediate problem but also ensured that the system was properly configured to prevent similar issues from arising in the future.
