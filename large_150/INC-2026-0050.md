## Symptom
The incident began with reports of autovacuum canceling under sustained write load on the primary SQL replica. Initially, this caused minimal disruption, but as the night progressed, the cancelations became more frequent, leading to increased latency and eventually errors for users attempting to query the database. Monitoring caught the initial spike in write load, but the subsequent autovacuum cancelations were not immediately flagged as critical, delaying the response. The user impact was significant, with several critical applications relying on the database for real-time data. As the issue persisted, the business impact grew, affecting operations and decision-making processes. Further investigation into pg_stat_activity views revealed an unusually high number of idle connections, which hinted at a potential configuration issue rather than a straightforward resource constraint problem.

The symptoms evolved over time, with the database showing signs of increased contention and decreased performance. The metrics platform indicated rising CPU usage and disk I/O wait times, suggesting that the database was struggling to keep up with the workload. However, these metrics alone did not point to a clear root cause, requiring deeper investigation into the database's configuration and current state. The focus on the primary SQL replica led the team to examine its settings and behavior closely, looking for any anomalies that could explain the autovacuum cancelations and performance degradation.

As the incident unfolded, it became clear that the monitoring setup, while alerting on some aspects of database performance, had not been configured to catch the specific combination of symptoms presented by this issue. This gap in monitoring meant that the initial response was reactive rather than proactive, highlighting the need for a review of alerting rules to prevent similar delays in the future. The team relied heavily on tools like `pidstat` to monitor CPU usage and `pgbouncer` logs to understand connection pooling behavior, which provided valuable insights into the database's state but required manual analysis to connect the dots between different metrics and logs.

Given the complexity of the issue and the evolving nature of the symptoms, it was challenging to pinpoint the exact cause without a thorough investigation. The team had to consider multiple factors, including recent changes to the database configuration, application behavior, and infrastructure performance. Each of these potential causes required careful examination, making the diagnosis phase both critical and time-consuming. The initial hypothesis focused on resource constraints, given the high write load and signs of contention. However, as more data was collected, it became apparent that the issue might be more nuanced, involving configuration settings and how they interacted with the workload.

The user and business impact continued to grow as the incident persisted, underscoring the need for a swift and accurate diagnosis. The team worked closely with stakeholders to understand the implications of the database performance issues, ensuring that everyone was aligned on the urgency and the steps being taken to resolve the issue. This collaboration was crucial in managing expectations and ensuring that the resolution efforts were properly prioritized. As the investigation deepened, the team remained focused on the primary SQL replica, recognizing that the root cause of the issue lay within its configuration or operation.

## Diagnosis steps and hypotheses
Initially, the team suspected that the issue might be related to insufficient resources (CPU, memory, or disk I/O) given the high write load. To investigate this hypothesis, they used `pidstat` to monitor CPU usage and checked disk I/O metrics, but these did not reveal any clear bottlenecks that would explain the autovacuum cancelations. The next hypothesis considered was that the database was experiencing contention due to locking or deadlocks, which could be causing the autovacuum to cancel. However, an examination of the database logs did not show significant evidence of locking issues.

Another hypothesis explored was that the connection pooling configuration might be inadequate, leading to inefficient use of database connections and potentially causing the observed issues. To investigate this, the team examined `pgbouncer` logs and considered adjusting the pool size. However, before making changes, they wanted to understand the current connection usage better. The team executed the following command to get more insights:
```
psql -c 'SELECT * FROM pg_stat_activity;'
```
This provided a snapshot of current database activity, which helped in understanding the connection usage patterns but did not directly point to the root cause.

The team also considered the possibility that the autovacuum settings themselves might be too aggressive, causing cancelations under load. They reviewed the autovacuum configuration but found no recent changes that would explain the sudden onset of the issue. As the investigation continued, the team remained open to revising their hypotheses based on new evidence. The actual root cause emerged after a detailed review of the database configuration files and logs, which revealed a misconfiguration that had been overlooked in the initial setup.

## Resolution steps
1. Set max_connections to 500 in postgresql.conf
2. Restart primary SQL replica on node1
3. Adjust pgbouncer.ini to increase pool_size to 200
4. Run pidstat -p 1234 to monitor CPU usage
5. Set statement_timeout to 30000 in postgresql.conf

## Post-mortem note
The primary SQL replica exceeded its connection limit due to a misconfigured max_connections setting. This issue was missed initially because the monitoring setup did not adequately cover this specific scenario, and the team's initial hypotheses focused on more common causes of database performance issues. The resolution required a combination of configuration adjustments and a better understanding of the database's workload and limitations. Following this incident, the team plans to review and enhance the monitoring setup to include more specific alerts for connection limit issues and to conduct regular audits of database configurations to prevent similar misconfigurations. Additionally, the experience highlighted the importance of thorough investigation and the value of considering a wide range of hypotheses when diagnosing complex database performance issues.
