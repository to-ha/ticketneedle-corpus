## Symptom
The incident began with reports of BGP session flapping every few minutes, which led to intermittent disruptions in network connectivity. This flapping caused outbound API calls to stall, resulting in delays of 5-10 seconds because DNS resolution would hang. The slowdown would temporarily disappear after a resolver cache flush, only to reappear a few minutes later. This pattern suggested that the issue was related to DNS resolution and the anycast VIP.

Further investigation revealed that the BGP session flapping was not an isolated event, but rather a symptom of a deeper issue. The flapping would cause the DNS resolver to timeout, leading to the delays in outbound API calls. This suggested that the problem was not solely with the BGP configuration, but also with the DNS resolution process.

The impact of this incident was significant, as it affected the ability of users to make outbound API calls. The intermittent nature of the issue made it challenging to diagnose and resolve. Monitoring tools detected the BGP session flapping and alerted the network operations team, who began investigating the cause of the issue.

As the investigation continued, it became clear that the issue was related to the anycast VIP and the DNS resolution process. The team used tools such as `traceroute`, `tcpdump`, and `dig` to gather more information about the issue. These tools provided valuable insights into the network traffic and DNS resolution process, which helped the team to narrow down the possible causes of the issue.

## Diagnosis steps and hypotheses
The team considered several hypotheses to explain the BGP session flapping and DNS resolution issues. One hypothesis was that the issue was caused by a misconfiguration of the BGP protocol. However, after reviewing the configuration, it was determined that it was correct. Another hypothesis was that the issue was related to the anycast VIP and the way it was handling DNS requests.

To investigate this hypothesis, the team used the `dig` command to test DNS resolution. For example, they ran the following command:
```
dig +ednsopt=4096 example.com
```
This command helped to determine if the issue was related to the EDNS0 buffer size. However, the results did not point to a clear cause of the issue.

The team also considered the possibility that the issue was caused by a problem with the upstream resolver. However, after investigating this hypothesis, it was determined that the upstream resolver was functioning correctly.

## Resolution steps
1. Set edns-buffer-size to 1232 in /etc/resolver.conf
2. Restart the resolver daemon with systemctl restart resolver
3. Verify new buffer size with dig +ednsopt=1232 example.com
4. Flush resolver cache with rndc flush

## Post-mortem note
EDNS0 buffer size mismatch caused fragmentation that the upstream resolver dropped silently. This issue was resolved by adjusting the EDNS0 buffer size to match the requirements of the upstream resolver. The resolution steps taken ensured that the DNS resolution process was functioning correctly, and the BGP session flapping was eliminated. The team will continue to monitor the network to ensure that this issue does not recur.
