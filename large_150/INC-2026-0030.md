# Major Incident — INC-2026-0030
* **Ticket ID:** INC-2026-0030
* **Reported:** 2026-02-09 06:16 UTC
* **Priority:** P3
* **Domain:** Containers / Kubernetes
* **Status:** Resolved

## Symptom
The incident began with reports of pods not scaling as expected, leading to increased latency and decreased responsiveness in the application. Upon initial investigation, it was observed that the horizontal pod autoscaler was not functioning correctly, resulting in insufficient replicas to handle the current workload. This issue manifested as a PVC stuck in the Pending state after a recent storage class migration, indicating a potential problem with the autoscaling configuration.

Further examination revealed that the symptoms were consistent across multiple deployments, suggesting a systemic issue rather than an isolated problem. The monitoring tools indicated a mismatch between the expected and actual number of replicas, pointing towards an autoscaling misconfiguration.

## Escalation timeline
* 06:31 — L1 Platform support: Ravi: Ravi initiated the incident response process by notifying the L2 team and gathering initial diagnostic data.
* 07:03 — L2 Platform engineer: Nora: Nora took over the investigation, focusing on the horizontal pod autoscaler configuration and its interaction with the storage class migration.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential issues with the storage class migration and its impact on PVC provisioning. However, upon further investigation using tools like k9s and kubectl, it became clear that the root cause lay elsewhere. 
```
kubectl describe hpa -n default
```
This command provided critical insights into the autoscaling configuration, revealing a misconfigured scale target as the likely culprit.

## Resolution steps
1. Set scale target to 50% CPU
2. Update deployment config with maxReplicas=10
3. Restart autoscaler with --v=5 flag
4. Verify hpa-metrics adapter is running on port 8443

## Post-mortem note
The horizontal pod autoscaler misconfigured scale target led to insufficient replicas. This incident highlights the importance of regularly reviewing and validating autoscaling configurations, especially after changes to underlying infrastructure components like storage classes.
