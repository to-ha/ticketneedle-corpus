## Symptom
The application threads were blocked due to a saturated connection pool, causing delays in query execution. This symptom was observed by the monitoring system, which triggered an alert when the connection pool utilization exceeded the threshold. Further investigation revealed that the database was experiencing a high volume of active connections, leading to resource contention.

The connection pool saturation was causing a ripple effect, impacting the overall performance of the application. Users were experiencing timeouts and errors when attempting to execute queries, resulting in a significant disruption to business operations. The monitoring system's alerts and metrics provided valuable insights into the symptom, allowing the team to focus on diagnosing the root cause.

## Diagnosis steps and hypotheses
Initial hypotheses suggested that the issue might be related to disk I/O bottlenecks or inadequate database configuration. However, upon further analysis, it became clear that the root cause was more complex. To better understand the situation, the team executed the following command:
```
psql -c 'SELECT * FROM pg_stat_activity WHERE state = "active"'
```
This query revealed a large number of active connections, which hinted at a potential issue with the WAL archive process.

## Resolution steps
1. Restart WAL archiver with --archive_timeout=60
2. Set wal_sender_timeout to 3000ms in postgresql.conf
3. Increase max_wal_senders to 5
4. Run VACUUM on pg_catalog tables

## Post-mortem note
The WAL archive process hung due to insufficient wal sender resources. This incident highlights the importance of monitoring database performance and configuring resources adequately to prevent similar issues in the future.
