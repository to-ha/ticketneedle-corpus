## Symptom
The incident began with reports of secret rotation breaking one downstream consumer, leading to authentication failures. This symptom was first observed through monitoring alerts and user complaints about failed logins. Further investigation revealed that the secrets manager was not properly updating secrets, causing the downstream consumer to fail.

As the issue persisted, the team noticed a pattern of frequent secret expirations, which seemed to be related to the problem. The frequency of these expirations was higher than expected, indicating a potential misconfiguration in the secrets manager. This observable pattern suggested that the issue might be related to the secrets rotation process.

The symptom complex was characterized by a high rate of authentication failures due to expired secrets, which pointed towards an issue with the secrets manager's ability to properly rotate and update secrets.

## Diagnosis steps and hypotheses
Initial hypotheses included a misconfiguration in the secrets manager or a problem with the downstream consumer's implementation. However, upon further investigation, these hypotheses were ruled out due to lack of evidence. 
```
vault read -field=tokens /secret/path
```
This command was used to verify the secret rotation process, but it did not reveal any obvious issues. The team then shifted their focus towards the secrets manager's configuration, suspecting that a parameter might be set incorrectly, leading to the frequent secret expirations.

## Resolution steps
1. Set max_ttl to 3600 in /etc/secrets.conf
2. Restart secrets manager service on node 10.1.1.5
3. Update flag --secrets-refresh-interval to 60 in runner-logs
4. Verify secrets rotation with vault-style CLI command

## Post-mortem note
The max_ttl value was set too low, causing frequent secret expiration. This issue highlights the importance of regularly reviewing configuration parameters to prevent similar problems in the future.
