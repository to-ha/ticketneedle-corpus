## Symptom
The recursive DNS resolver cluster began exhibiting asymmetric routing after a recent configuration push. This resulted in users experiencing intermittent DNS resolution failures, with some queries taking an abnormally long time to resolve or timing out altogether. The issue was first noticed by monitoring tools, which detected a spike in DNS query latency. As the incident progressed, users started reporting difficulties accessing certain websites and online services.

Upon further investigation, it became clear that the asymmetric routing was causing packets to take unexpected paths through the network, leading to increased latency and packet loss. This, in turn, was exacerbating the DNS resolution issues, creating a cascade of failures that affected a significant portion of users. The monitoring tools were able to provide detailed insights into the network traffic patterns, helping the engineers to narrow down the possible causes of the issue.

The symptom complex presented a challenging diagnostic scenario, as the intermittent nature of the failures made it difficult to pinpoint the exact cause. However, by analyzing the network traffic patterns and DNS query logs, the engineers were able to identify some key characteristics of the issue, including the asymmetric routing and increased latency. These findings would later prove crucial in guiding the diagnosis and resolution efforts.

As the incident continued to affect users, the engineering team worked to gather more data and refine their understanding of the symptom complex. They used tools like `tcpdump` to capture network traffic and `nslookup` to test DNS resolution, which provided valuable insights into the behavior of the recursive DNS resolver cluster. The data collected during this phase would eventually contribute to the development of a hypothesis about the root cause of the issue.

## Diagnosis steps and hypotheses
The diagnosis process involved considering several hypotheses about the root cause of the issue. One initial hypothesis was that the problem might be related to a recent change in the network topology, which could have introduced asymmetric routing. However, after analyzing the network traffic patterns and DNS query logs, this hypothesis was ruled out due to lack of evidence supporting such a change.

Another hypothesis considered was that the recursive DNS resolver cluster might be experiencing resource exhaustion, leading to delayed or failed DNS resolutions. While this hypothesis seemed plausible, further investigation using tools like `nslookup` and `tcpdump` did not reveal any signs of resource constraints that could explain the observed symptoms.

To further diagnose the issue, the following command was used:
```
nslookup -type=soa example.com 127.0.0.1
```
This test helped to isolate the problem to the recursive DNS resolver cluster, suggesting that the issue might be related to its configuration or operation. However, the exact cause remained unclear, necessitating further investigation.

## Resolution steps
1. Set max recursion depth to 10 in /etc/named.conf
2. Restart named service on all recursive DNS nodes
3. Update nftables rule 5 to allow UDP packets on port 53
4. Verify DNS query timeout is set to 2 seconds

## Post-mortem note
The recursive DNS resolver cluster was overwhelmed by excessive queries due to a misconfigured max recursion depth. This incident highlights the importance of carefully configuring and monitoring critical infrastructure components like the recursive DNS resolver cluster to prevent such issues. In the future, regular audits of configuration files and proactive monitoring of DNS query patterns could help mitigate similar problems.
