## Symptom
The incident began with reports of ingress returning 502 errors for a single backend service. This symptom was first observed by monitoring tools, which alerted the team to a spike in error rates. Upon further investigation, it became clear that the issue was not limited to a single ingress controller, but rather was a cluster-wide problem affecting all incoming traffic to the specified backend service. The error messages indicated a failure to establish a connection to the backend, suggesting a possible issue with service discovery or DNS resolution.

As the team dug deeper, they found that the affected backend service was properly configured and running as expected, with no issues reported by the service itself. This led to a focus on the ingress controllers and the node-local DNS cache, as these components are responsible for resolving service names to IP addresses. The fact that only a single backend service was affected suggested that the issue might be related to a specific DNS entry or cache entry.

The impact of the incident was significant, as the affected backend service is a critical component of the application. Users reported errors and timeouts when attempting to access the service, resulting in a loss of functionality and productivity. The team worked quickly to resolve the issue, recognizing the importance of prompt action to minimize downtime and restore service.

## Diagnosis steps and hypotheses
Initial hypotheses focused on possible misconfigurations of the ingress controllers or issues with the backend service itself. However, as the investigation progressed, attention turned to the node-local DNS cache, given the specific nature of the error and the fact that only one backend service was affected. The team considered the possibility of a cache overflow or corruption, which could lead to failed resolutions for specific services.

To explore this hypothesis further, the team used `helm` to inspect the configuration of the `coredns` component, which manages DNS services within the cluster. Specifically, they ran the following command to verify the configuration values:
```
helm get values coredns --show-values
```
This helped confirm that the `coredns` setup was as expected, but did not immediately reveal the root cause. Further diagnosis involved checking etcd for any issues with service registrations and using `stern` to monitor logs from `coredns` for any errors or warnings related to DNS resolution.

## Resolution steps
1. Restart coredns with --cache-size=1000
2. Set dns-cache-ttl to 300 in /etc/coredns/Corefile
3. Run etcdctl get /registry/services/local/dns --prefix
4. Verify cache metrics with stern -n kube-system coredns

## Post-mortem note
The node-local DNS cache became overloaded due to excessive queries. This overload led to a situation where the cache was unable to properly resolve the name of the affected backend service, resulting in the observed 502 errors. The resolution steps taken helped to alleviate the immediate issue by adjusting the cache size and TTL, ensuring that the DNS service could properly handle the query load. Further analysis and tuning may be necessary to prevent similar incidents in the future.
