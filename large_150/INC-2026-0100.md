# Major Incident — INC-2026-0100
* **Ticket ID:** INC-2026-0100
* **Reported:** 2026-04-29 00:59 UTC
* **Priority:** P1
* **Domain:** Containers / Kubernetes
* **Status:** Resolved

## Symptom
The incident began with reports of PVCs (Persistent Volume Claims) becoming stuck in the "Pending" state after a recent storage class migration. This issue was first observed by the monitoring team, who noticed a spike in error rates for pod deployments. As the issue persisted, it became clear that the problem was not limited to a single namespace or deployment, but rather was a cluster-wide problem. The error messages indicated that the ingress controller was unable to allocate the necessary storage resources, leading to a backlog of pending PVCs.

Further investigation revealed that the affected pods were all relying on the same storage class, which had been recently migrated to a new provisioner. However, the ingress controller configuration had not been updated to reflect this change, resulting in a mismatch between the expected and actual storage provisioning. This mismatch caused the ingress controller to become overloaded, leading to the observed symptoms.

The impact of this issue was significant, as it prevented new deployments from being created and caused existing pods to become unavailable. The development team was unable to push new code changes, and the operations team was unable to perform routine maintenance tasks. The issue required immediate attention to prevent further disruption to the cluster.

As the incident progressed, the team observed that the ingress controller was experiencing high CPU usage and memory utilization, which further exacerbated the problem. The team attempted to restart the ingress controller, but this did not resolve the issue. It became clear that a more thorough investigation and diagnosis were necessary to identify the root cause of the problem.

## Diagnosis steps and hypotheses
The team considered several hypotheses to explain the observed behavior, including issues with the storage provisioner, problems with the ingress controller configuration, and potential network connectivity issues. However, as they dug deeper, they found that the root cause was related to the ingress controller configuration. One of the key diagnostic steps involved running the following command to inspect the ingress controller logs:
```
stern -n ingress-namespace ingress-controller
```
This command provided valuable insights into the ingress controller's behavior and helped the team to identify the issue. The team also used tools like `kustomize` and `etcdctl` to investigate the configuration and state of the cluster.

## Resolution steps
1. Restart ingress controller with --v=5 flag
2. Set maxConnections to 1000 in /etc/ingress/config.yaml
3. Run etcdctl get /ingress/config --prefix --keys-only
4. Update kustomize config to include ingress patch

## Post-mortem note
Ingress controller misconfiguration caused connection overload. The team has updated the ingress controller configuration to reflect the changes made during the storage class migration, and the cluster is now stable. The incident highlighted the importance of ensuring that all components are properly configured and updated after changes to the cluster.
