# Major Incident — INC-2026-0069
* **Ticket ID:** INC-2026-0069
* **Reported:** 2026-03-12 20:34 UTC
* **Priority:** P3
* **Domain:** Containers / Kubernetes
* **Status:** Resolved

## Symptom
The incident began with reports of PVCs (Persistent Volumes) getting stuck in the "Pending" state after a recent storage class migration. This issue was first observed by the development team when they attempted to deploy new applications, and it quickly became apparent that the problem was not isolated to a single namespace or application. As the issue persisted, the monitoring system began to alert on an increasing number of failed pod creations due to the unavailability of persistent storage. The symptom complex revolved around the inability of the Kubernetes cluster to properly allocate storage resources, leading to a significant impact on service deployment and scalability.

Further investigation into the monitoring data revealed that the problem seemed to correlate with an increase in DNS query errors within the cluster. It appeared that the node-local DNS cache was experiencing difficulties in resolving the hostnames of the storage nodes, which in turn caused the PVC allocation process to fail. The user impact was substantial, as it prevented the deployment of new services and the scaling of existing ones, directly affecting the availability and performance of applications running on the cluster.

The evolution of the symptoms over time showed a gradual increase in the number of affected pods and namespaces, indicating a systemic issue rather than an isolated problem. Despite the monitoring system's alerts on pod creation failures, it initially missed the underlying DNS query issues, highlighting a gap in the current monitoring setup. As the incident progressed, the team focused on understanding the root cause of the DNS query failures, recognizing its critical role in resolving the PVC allocation problem.

The business impact of the incident was significant, with several critical services unable to scale or deploy new versions, leading to potential revenue loss and customer dissatisfaction. The operations team worked closely with the development teams to understand the scope of the issue and to find a temporary workaround, which involved manual intervention to allocate storage resources. However, this approach was not scalable and did not address the underlying problem.

The initial hypothesis based on the symptoms suggested a possible issue with the storage class configuration or the Kubernetes cluster's ability to communicate with the storage nodes. However, as more data became available, it became clear that the node-local DNS cache was at the heart of the problem, misbehaving in a way that affected the entire cluster's functionality.

## Diagnosis steps and hypotheses
The team initially suspected that the issue might be related to the storage class migration itself, possibly introducing a compatibility problem with the Kubernetes version in use. To diagnose this, they reviewed the storage class configurations and compared them against the recommended settings for their Kubernetes version. However, after verifying the configurations and finding no discrepancies, this hypothesis was ruled out.

Another hypothesis considered was that there might be a network connectivity issue between the Kubernetes nodes and the storage nodes, preventing the successful resolution of storage node hostnames. The team used `dig` and `tcpdump` to inspect DNS traffic and verify network connectivity, but these tests showed no issues with network connectivity or DNS resolution from the nodes to the storage nodes, thus ruling out this hypothesis as well.

The team also explored the possibility of a misconfiguration in the Kubernetes cluster's DNS settings, potentially causing the node-local DNS cache to malfunction. They inspected the CoreDNS configuration files and logs but found no obvious misconfigurations that would lead to the observed behavior. This led them to consider more complex issues with the DNS cache itself.

To further investigate the DNS cache, the team executed the following command to inspect the current CoreDNS configuration stored in etcd:
```
etcdctl get /coredns/config
```
This step provided valuable insight into how CoreDNS was currently configured and whether there were any recent changes that could have contributed to the issue. However, it did not immediately reveal the root cause, prompting further investigation.

As the diagnosis progressed, the team began to suspect that the node-local DNS cache might be experiencing performance issues or was misconfigured in a way that was not immediately apparent. They decided to monitor the CoreDNS logs more closely using `stern` to observe any patterns of failure or error messages that could indicate what was going wrong.

It wasn't until they dug deeper into the performance metrics of the node-local DNS cache that they started to see evidence pointing towards a memory limit issue. The cache seemed to be growing beyond its allocated limits, causing it to malfunction and fail to resolve hostnames correctly. This realization led to a final hypothesis that the root cause of the incident was related to the DNS cache's configuration and its inability to handle the current workload without exceeding its memory limits.

## Resolution steps
1. Restart coredns on node1 with --tls flag
2. Set cache size to 1000 in /etc/coredns/Corefile
3. Run stern -n default coredns to monitor logs
4. Update etcd cluster with new coredns config using etcdctl
5. Redeploy coredns helm chart with updated values

## Post-mortem note
The node-local DNS cache was misconfigured and exceeded its memory limit. This issue was missed initially because the monitoring setup did not adequately cover the performance metrics of the DNS cache, highlighting a need to expand the scope of metrics collection to include more detailed performance data on critical cluster components like CoreDNS. Following the incident, the team implemented additional monitoring for the DNS cache and scheduled a review of all cluster components to ensure similar issues are caught before they escalate into major incidents. The resolution steps taken not only fixed the immediate problem but also provided a basis for improving the cluster's resilience against similar issues in the future.
