# Major Incident — INC-2026-0015
* **Ticket ID:** INC-2026-0015
* **Reported:** 2026-04-18 22:14 UTC
* **Priority:** P2
* **Domain:** Database
* **Status:** Resolved

## Symptom
The database experienced intermittent failures under sustained write load, with autovacuum canceling repeatedly. This led to a buildup of dead tuples, causing disk space issues and eventually resulting in errors for users attempting to write to the database. Monitoring alerted on the rising disk usage and failure of autovacuum to complete, prompting an immediate investigation.

## Escalation timeline
* 22:29 — L1 Database operator: Zara notified the L2 team about the escalating issue after attempting basic troubleshooting steps.
* 23:02 — L2 Database engineer: Dmitri began a deeper dive into the database logs and configuration to identify the root cause.

## Diagnosis steps and hypotheses
Initial hypotheses focused on misconfiguration of autovacuum settings or inadequate resource allocation. However, upon further investigation, including running diagnostic queries like 
```
psql -c 'EXPLAIN ANALYZE SELECT * FROM orders'
```
it became clear that the issue was more complex, related to how data was being partitioned and managed within the database.

## Resolution steps
1. Set default_tablespace to 'main_ts' in postgresql.conf
2. Restart database service with systemctl restart db
3. Run VACUUM FULL on partitioned table 'orders_2022'
4. Adjust partitioning scheme with ALTER TABLE orders SET (autovacuum_enabled = on)

## Post-mortem note
The table partitioning scheme was not properly configured, leading to disk space issues. This incident highlights the importance of regularly reviewing database configurations, especially after significant changes or updates, to prevent such issues from arising in the future.
