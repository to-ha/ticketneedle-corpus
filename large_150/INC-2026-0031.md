## Symptom
The incident began with reports of feature flag evaluation latency spikes during peak hours. Users experienced delays in accessing updated features, which impacted the overall performance of the platform. Monitoring tools detected an increase in response times for feature flag evaluations, indicating a potential issue with the CI runner pool.

Further investigation revealed that the latency spikes were consistent across different regions and user groups, suggesting a systemic problem rather than an isolated issue. The symptoms were most pronounced during peak usage hours, when the CI runner pool was under the highest load.

The observable pattern of feature flag evaluation latency spikes served as the primary indicator of the incident, prompting further investigation into the root cause.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential misconfigurations or resource constraints within the CI runner pool. To investigate, the team used various tools, including a vault-style CLI to access sensitive configuration data. A key command used during diagnosis was:
```
vault read /secret/ci-config
```
This command provided insight into the current configuration and helped rule out certain hypotheses. Although the team considered several potential causes, including network connectivity issues and insufficient resources, the evidence ultimately pointed to an overwhelmed CI runner pool as the root cause.

## Resolution steps
1. Stop CI runner pool with --force flag
2. Clean /var/lib/ci-runners directory
3. Set max_concurrent_jobs to 5 in ci_config.yml
4. Restart CI runner service with --verbose flag

## Post-mortem note
The CI runner pool was overwhelmed by concurrent jobs. This incident highlights the importance of monitoring and adjusting the CI runner pool configuration to ensure optimal performance under varying loads. Future improvements will focus on implementing more robust scaling mechanisms and enhancing real-time monitoring capabilities to prevent similar incidents.
