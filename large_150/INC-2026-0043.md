## Symptom
The incident began with reports of intermittent packet loss on a single uplink of the stateful firewall pair, which led to noticeable delays in outbound API calls. Users experienced stalls in DNS resolution, resulting in 5-10 second delays for these calls. However, the slowdown would temporarily disappear after a resolver cache flush, only to return after a few minutes. This pattern suggested a periodic issue related to DNS resolution that was being mitigated by cache flushes but not permanently resolved.

Further investigation revealed that the affected uplink was responsible for a significant portion of the network's outbound traffic, including critical API calls to external services. The intermittent nature of the packet loss made it challenging to pinpoint the exact cause, as the network would appear to function normally for periods before the issue recurred.

Monitoring tools indicated spikes in latency and packet loss during the affected periods, aligning with user reports of delayed API calls. The fact that a resolver cache flush could temporarily alleviate the issue hinted at a DNS-related problem, possibly tied to the stateful firewall's configuration or its interaction with external DNS services.

Given the impact on critical API calls and the intermittent nature of the issue, it was crucial to identify and resolve the root cause promptly to prevent further disruptions to service.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential misconfigurations of the stateful firewall pair, including rules that might be inadvertently blocking or delaying DNS traffic. Another hypothesis considered was the possibility of the firewall's DNS resolution mechanism being overwhelmed, leading to intermittent failures.

To investigate these hypotheses, several diagnostic steps were taken, including analyzing network traffic captures with `tcpdump` and inspecting DNS resolution patterns with `nslookup`. A key command used in the diagnosis was:
```
nft list table inet filter | grep dnssec
```
This helped in understanding the current DNSSEC validation rules applied by the firewall. However, none of these initial hypotheses fully explained the observed behavior, prompting further investigation into DNSSEC validation and its potential impact on delegated zones.

## Resolution steps
1. Disable DNSSEC validation for delegated zone example.com
2. Set dnssec-validation no for example.com in /etc/nft/nftables.conf
3. Restart nft service with systemctl restart nft
4. Verify resolver cache flush with nslookup -debug example.com

## Post-mortem note
DNSSEC validation failure on delegated zone example.com caused fallback retries to expire the resolver budget. This incident highlights the importance of carefully considering DNSSEC validation settings, especially in environments with complex domain structures. The temporary relief provided by resolver cache flushes was a critical clue that pointed towards a DNS-related issue, ultimately leading to the identification and resolution of the problem.
