## Symptom
The metrics ingestion pipeline experienced a significant disruption, leading to a lack of real-time data for monitoring and alerting purposes. Synthetic probes continued to report healthy statuses, but actual users encountered errors when attempting to access the service. This discrepancy between synthetic and real-user experiences was the primary observable symptom of the incident.

Further investigation revealed that the issue was not related to the service itself, but rather to the metrics pipeline that relied on it. The absence of metrics made it challenging to diagnose the root cause of the errors seen by real users.

The symptom complex was characterized by an empty metrics dashboard, indicating a complete loss of metrics ingestion. This had a cascading effect on the ability to monitor and respond to issues in a timely manner.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential configuration issues or recent changes to the metrics pipeline. However, upon further investigation, it became clear that the root cause was more complex. 
``` 
tsdb-cli inspect /var/lib/tsdb/data --check-integrity
```
This command was used to check the integrity of the metrics storage, which helped to identify inconsistencies in the data retention settings.

## Resolution steps
1. Restart tsdb service with --config.file=/etc/tsdb.conf
2. Set global.retention_period to 30d in /etc/tsdb.conf
3. Run tsdb-cli repair on /var/lib/tsdb/data
4. Verify metric ingestion with promtool query 'rate(metric[1m])'

## Post-mortem note
The metrics ingestion pipeline failed due to outdated retention settings. This incident highlights the importance of regularly reviewing configuration settings to prevent similar issues in the future.
