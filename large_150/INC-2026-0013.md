## Symptom
During a rolling kernel upgrade, a node entered NotReady state, causing concerns about the stability of the container runtime environment. Further investigation revealed that a specific deployment was entering CrashLoopBackOff within 30 seconds of pod start. The pod logs showed a single line and then the container exited with code 137, indicating an out-of-memory (OOM) issue. This pattern suggested that the container was running out of memory, leading to the CrashLoopBackOff.

The symptom was consistent across multiple attempts to restart the pod, pointing towards a configuration or resource allocation issue rather than a transient problem. Given the nature of the error, it seemed likely that the issue was related to the memory limits set for the containers within the deployment.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential misconfigurations in the deployment YAML or issues with the container runtime itself. To investigate, the team used tools like k9s for monitoring and crictl for inspecting container runtimes. A key command used in the diagnosis was:
```
crictl inspect --output json
```
This helped in understanding the container's configuration and runtime state but did not directly point to the root cause. The evidence from these investigations hinted at a memory-related issue but required further exploration of the deployment configurations and container resource limits.

## Resolution steps
1. Raise memory limit to 2 GiB
2. Set -Xmx to 1500m for JVM
3. Update deployment config with new limits
4. Apply updated config with kubectl rollout

## Post-mortem note
Memory limit was reduced causing JVM OOMKill. This incident highlights the importance of regularly reviewing and adjusting resource allocations for deployments, especially after changes in application requirements or during upgrades.
