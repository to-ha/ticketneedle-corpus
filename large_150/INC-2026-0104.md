* **Status:** Resolved

## Symptom
The incident began with reports of PVCs (Persistent Volume Claims) becoming stuck in a "Pending" state after a recent storage class migration. This issue affected multiple pods across various namespaces, leading to service disruptions and timeouts. The symptoms were first observed by the monitoring system, which alerted on an increase in pending PVCs. Upon further investigation, it became clear that the issue was not isolated to a specific namespace or pod, but rather a broader problem affecting the cluster's ability to provision storage.

As the issue persisted, users began to report errors when attempting to deploy new applications or scale existing ones. The error messages typically indicated a failure to bind PVCs to the requested storage class. This led to a significant impact on the development and deployment workflows, as teams were unable to push updates or changes to their applications.

The monitoring system provided valuable insights into the scope of the issue, showing a steady increase in the number of pending PVCs over a short period. This data helped focus the investigation on the storage provisioning pipeline and the potential causes of the bottleneck. The fact that the issue arose after a storage class migration suggested that the problem might be related to changes in the storage configuration or the way PVCs were being handled.

Further analysis of the cluster logs revealed a pattern of repeated DNS queries related to the node-local DNS cache. These queries seemed to be timing out or failing, which could potentially explain the PVC binding issues. However, at this stage, it was still unclear whether the DNS queries were the root cause of the problem or merely a symptom of a deeper issue.

## Diagnosis steps and hypotheses
Initial hypotheses focused on issues related to the storage class migration, such as misconfigured storage classes or insufficient resources. However, as the investigation deepened, attention turned to the node-local DNS cache due to the observed patterns of DNS query failures. One key command used in the diagnosis was:
```
kubectl get pods -n kube-system -l k8s-app=kube-dns
```
This command helped identify any issues with the DNS service itself, but it did not directly point to the root cause. Other hypotheses included network connectivity problems between nodes or issues with etcd consistency, but these were ruled out through additional testing and log analysis.

## Resolution steps
1. Restart node-local DNS cache on each worker node
2. Set dnsCacheSize to 1000 in /etc/kubernetes/dns.conf
3. Run etcdctl get /registry/services/endpoints --prefix=true
4. Verify node-local DNS cache configuration with kustomize build
5. Increase log level for node-local DNS cache to 5

## Post-mortem note
The node-local DNS cache was overloaded due to excessive queries. This overload led to a cascade of failures, including the inability to resolve PVC bindings in a timely manner, which in turn caused the observed symptoms. The resolution steps effectively addressed the root cause by restarting the node-local DNS cache, adjusting its configuration for better performance, and enhancing logging for future diagnostic purposes. These actions not only resolved the immediate incident but also provided a foundation for preventing similar issues in the future.
