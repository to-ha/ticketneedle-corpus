## Symptom
The backup job for the distributed filesystem completed successfully, but the verification step failed, indicating data inconsistencies. This issue was first observed by the monitoring system, which alerted the team to potential problems with data integrity. Further investigation revealed that the verification failure was not due to issues with the backup process itself but rather with how the data was being handled by the metadata server.

Upon closer inspection, it became clear that the metadata server was experiencing difficulties in maintaining a consistent view of the filesystem, leading to the verification failures. The symptom manifested as an inability to correctly verify the integrity of the backed-up data, suggesting underlying issues with the metadata management.

## Diagnosis steps and hypotheses
Initial hypotheses included hardware issues with the storage devices or network connectivity problems. To investigate these possibilities, diagnostic commands such as `smartctl` were used to check the health of the disks. For example:
```
smartctl -H /dev/sda
```
This helped rule out disk failures as a primary cause. Further analysis with tools like `fio` and `iostat` was planned to assess performance and load balancing but was not necessary once the root cause became apparent.

## Resolution steps
1. Restart metadata server on node 3
2. Set replication_factor to 3 in /etc/fs_config
3. Run fio with --numjobs 4 to rebalance load

## Post-mortem note
Metadata server failed due to insufficient replication. This incident highlights the importance of ensuring that the replication factor is adequately set to maintain data consistency and availability, especially in distributed filesystems.
