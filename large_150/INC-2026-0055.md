# Major Incident — INC-2026-0055
- **Ticket ID:** INC-2026-0055
- **Reported:** 2026-01-25 10:48 UTC
- **Priority:** P2
- **Domain:** Containers / Kubernetes
- **Status:** Resolved

## Symptom
The horizontal pod autoscaler (HPA) was observed to scale up pods, but the pods never transitioned to a Ready state. This issue was identified through monitoring tools, which alerted on the abnormal pod status. Further investigation revealed that the HPA was correctly scaling up the number of replicas, but for some reason, the pods were not becoming ready to serve traffic.

The symptom manifested as an increase in the number of pods in the Pending state, with none of them successfully transitioning to Running and then Ready. This led to a decrease in the overall availability of the service, as the load balancer was not able to distribute traffic to the non-Ready pods.

## Escalation timeline
- 10:56 — L1 Platform support: Liu notified the L2 team about the issue.
- 11:33 — L2 Platform engineer: Maya began investigating the HPA configuration and pod logs.

## Diagnosis steps and hypotheses
Initial diagnosis steps involved checking the HPA configuration and verifying that the pods were being created correctly. One hypothesis considered was that the HPA was not properly configured, leading to the pods not becoming Ready. To investigate this, the command ```
kubectl get hpa -o yaml
``` was used to retrieve the HPA configuration in YAML format. However, this did not reveal any obvious issues with the HPA configuration.

## Resolution steps
1. Set minReplicaCount to 3 in hpa.yaml
2. Update deployment with helm upgrade --set maxReplicas=10
3. Verify hpa config with etcdctl get /registry/deployments/hpa
4. Check pod logs with stern -n default -c container-name

## Post-mortem note
The horizontal pod autoscaler was misconfigured with a low minReplicaCount. This issue highlights the importance of regularly reviewing and updating HPA configurations to ensure proper scaling and service availability.
