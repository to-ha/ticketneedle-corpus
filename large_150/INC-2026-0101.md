## Symptom
The incident began with a noticeable increase in the message broker queue depth, which grew unbounded over time. This symptom was first observed by the monitoring system at 11:45 UTC, triggering an alert that was escalated to the L1 Platform support team. As the queue depth continued to rise, it started to impact the feature-flag service's ability to process requests in a timely manner, leading to delays and timeouts for users relying on these features. The user impact was significant, with multiple business-critical applications experiencing errors due to the inability to retrieve or update feature flags.

The monitoring system caught the initial spike in queue depth, but it missed the underlying cause of the issue, which was related to the feature-flag service's cache not being properly updated. The metrics platform showed a steady increase in queue depth over a 10-minute period, with no corresponding increase in request volume or errors from other components. This suggested that the issue was isolated to the feature-flag service.

Further investigation revealed that the feature-flag service was experiencing high latency when trying to retrieve flags from the cache, which was causing the message broker queue to grow. The team suspected that there might be an issue with the cache configuration or the underlying storage, but they needed more data to confirm this hypothesis. The symptom complex was characterized by a single observable pattern: the unbounded growth of the message broker queue depth, which was directly related to the feature-flag service's performance.

As the incident evolved, the team noticed that the feature-flag service was not only experiencing high latency but also returning stale flags to applications. This indicated that the cache was not being updated correctly, which could be due to a misconfiguration or an issue with the cache invalidation mechanism. The user impact continued to grow, with more applications experiencing errors and delays due to the feature-flag service's issues.

The team's initial focus was on understanding the cause of the high latency and stale flags, which led them to investigate the feature-flag service's configuration, cache settings, and storage. They used tools like the vault-style CLI and registry-gc to gather more information about the cache and its contents. The investigation revealed that the cache was not being properly updated, but the root cause of this issue was still unknown.

## Diagnosis steps and hypotheses
The team initially suspected that the issue might be related to a recent change in the cache configuration, which could have caused the feature-flag service to malfunction. They tried to verify this hypothesis by checking the cache settings and running some diagnostic commands. However, after reviewing the configuration files and running some tests, they found no evidence to support this theory.

Another hypothesis was that the issue could be related to a problem with the underlying storage, which might be causing the cache to become corrupted or outdated. The team tried to investigate this further by running some storage-related diagnostic commands, but again, they found no evidence to support this theory.

The team also considered the possibility that the issue might be related to a misconfiguration of the message broker, which could be causing the queue to grow unbounded. They reviewed the message broker configuration and ran some tests, but found no issues with the configuration.

As the team continued to investigate, they started to suspect that the issue might be related to the feature-flag service's cache not being properly updated. They tried to verify this hypothesis by running some cache-related diagnostic commands, including:
```
vault read -format=json /secret/feature/flags
```
This command revealed that the cache was indeed not being updated correctly, which was causing the feature-flag service to return stale flags.

The team then considered the possibility that the issue might be related to a problem with the cache invalidation mechanism, which might be causing the cache to become outdated. They reviewed the cache invalidation settings and ran some tests, but found no evidence to support this theory.

Finally, after ruling out several hypotheses, the team discovered that the root cause of the issue was related to a misconfigured ttl value in the feature-flag service's cache configuration. This was causing the cache to not be properly updated, leading to the feature-flag service returning stale flags and the message broker queue growing unbounded.

## Resolution steps
1. Restart feature-flag service on node 3
2. Set cache ttl to 300 in /etc/flag/config.yaml
3. Run registry-gc with --dry-run flag to identify stale entries
4. Remove outdated flags using vault-style CLI with --purge option
5. Update flag-history retention period to 90 days in /etc/flag/history.conf

## Post-mortem note
The feature-flag service cache was not properly updated due to a misconfigured ttl value. This issue was missed initially because the monitoring system did not have visibility into the cache configuration, and the team did not suspect a cache-related issue until later in the investigation. In the future, we should add more monitoring and logging around the cache configuration to help identify similar issues earlier. Additionally, we should review our incident response process to ensure that we are considering cache-related issues as a potential cause of problems with the feature-flag service.
