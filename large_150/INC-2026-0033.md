## Symptom
The incident began with reports of a DNS resolution latency spike to 5-10 seconds, affecting multiple users across the network. This symptom was first observed by monitoring tools, which triggered an alert due to the unusual increase in response times. Upon further investigation, it became clear that this issue was not isolated to a specific subset of users or geographical locations, suggesting a more widespread problem within the network infrastructure.

As the incident progressed, users began to report difficulties in accessing certain websites and online services, with some experiencing complete loss of connectivity. The impact was significant, affecting not only internal operations but also external communications and services reliant on DNS resolution. The symptom complex revolved around this core issue of delayed or failed DNS resolutions, pointing towards a network-related problem that needed urgent attention.

Initial observations suggested that the problem might be related to routing or network configuration issues, given the nature of DNS resolution and its dependence on stable network connectivity. Tools like `mtr` and `dig` were likely reached for during the initial stages of troubleshooting to understand the path packets were taking and where potential bottlenecks or misconfigurations might exist.

Further analysis of network traffic and logs revealed patterns consistent with routing inefficiencies, possibly tied to the OSPF (Open Shortest Path First) protocol, which is used for dynamic routing within the network. This hinted at a deeper issue within the network's routing configuration that could be causing the DNS resolution latency.

## Diagnosis steps and hypotheses
Diagnosing the issue involved considering several hypotheses related to network configuration and routing. One of the initial hypotheses was that there might be a problem with the OSPF backbone area configuration, which could lead to inefficient routing and thus affect DNS resolution times. To investigate this, the team used various tools to analyze network paths and configurations.

``` 
mtr -r 10.1.1.100
```
This command was particularly useful in tracing the path to a specific router and identifying any potential issues along that path. However, initial results did not immediately point to a single root cause, requiring further investigation into other possible hypotheses, such as issues with interface configurations or metric settings within the OSPF protocol.

Another hypothesis considered was related to the metric settings for path costs in OSPF, which could also influence routing decisions and potentially lead to suboptimal paths being chosen. This would require a detailed review of the OSPF configuration across all relevant routers to identify any inconsistencies or misconfigurations.

## Resolution steps
1. Set OSPF backbone area ID to 0.0.0.1
2. Restart OSPF service on router 10.1.1.100
3. Configure interface eth0 with IP 10.1.1.101/30
4. Update OSPF config with metric 50 for path cost
5. Reload router 10.1.1.102 with new OSPF config

## Post-mortem note
The OSPF backbone area was misconfigured with incorrect area ID. This critical mistake led to the network inefficiencies and DNS resolution latency observed during the incident. Upon reflection, it's clear that regular audits of network configurations, especially for critical protocols like OSPF, are essential to prevent such incidents. Implementing automated checks for configuration consistency across the network could also help in early detection and prevention of similar issues in the future.
