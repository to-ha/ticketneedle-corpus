## Symptom
The incident began with reports of the application's connection pool becoming saturated, leading to blocked application threads. This symptom was first observed by monitoring tools that track database connection utilization and application performance metrics. As the connection pool reached its maximum capacity, the application's ability to serve requests was severely impacted, resulting in a significant increase in error rates and response times. The saturation of the connection pool was identified through alerts generated by the metrics platform, which triggered an initial investigation into the database's performance and configuration.

Further analysis revealed that the primary SQL replica was experiencing an unusually high volume of queries, which was contributing to the connection pool saturation. The database's logs showed a large number of concurrent connections, exceeding the expected baseline. This led to an initial hypothesis that the issue might be related to an unexpected increase in application traffic or a misconfiguration of the database's connection settings.

The impact of the saturated connection pool was widespread, affecting multiple components of the application and resulting in a significant degradation of service. Users reported errors and timeouts when attempting to access the application, and internal teams relying on the database for their operations were also affected. The situation required prompt attention to prevent further escalation and potential data loss.

As the investigation continued, it became clear that the root cause of the issue was related to the primary SQL replica's configuration and its ability to handle the increased query load. The focus shifted towards identifying the specific configuration parameters that were contributing to the issue and determining the appropriate adjustments to restore normal operation.

## Diagnosis steps and hypotheses
Initial hypotheses focused on the possibility of a misconfigured connection pool or an unexpected surge in application traffic. To investigate these hypotheses, the team used tools like `pidstat` to monitor the database's process activity and `pgbouncer` logs to analyze connection patterns. The `iostat` command was also utilized to assess disk I/O performance, which could indicate if the issue was related to storage bottlenecks.

One of the key diagnostic steps involved running the following command to monitor the database's CPU usage and identify any resource-intensive processes:
```
pidstat -p $(pgrep postgres) 10 10
```
This command provided valuable insights into the database's current workload and helped in identifying potential bottlenecks. However, it did not directly point to the root cause of the connection pool saturation.

As the investigation progressed, the team considered several hypotheses, including issues with disk I/O, memory allocation, and network connectivity. Each of these hypotheses was tested through a combination of log analysis, metric inspection, and targeted testing. Although these factors were found to be within normal operating ranges, their examination helped to rule out potential causes and narrow down the focus towards configuration-related issues.

## Resolution steps
1. Restart primary SQL replica with --max-connections=500
2. Set max_wal_senders to 10 in postgresql.conf
3. Adjust pidstat sampling interval to 10 seconds
4. Increase shared_buffers to 4GB in postgresql.conf

## Post-mortem note
The primary SQL replica exceeded its connection limit due to a surge in queries. This incident highlighted the importance of regularly reviewing database configuration parameters to ensure they are appropriately scaled for expected workloads. Following this incident, additional monitoring and alerting have been implemented to provide earlier detection of similar issues, allowing for more timely interventions to prevent service degradation.
