## Symptom
The incident began with reports of feature flag evaluation latency spikes during peak hours, impacting the overall performance of the platform. Users experienced delays in loading pages and slower response times. As the issue persisted, it became clear that the problem was not isolated to a specific service but was rather a platform-wide issue affecting multiple components. The symptoms first appeared around 14:00 UTC, with users starting to report issues on internal chat channels. By 15:00 UTC, the metrics platform indicated a significant increase in latency, prompting the initial investigation.

Further analysis revealed that the latency spikes were correlated with an increase in DNS query times. The runner-logs showed repeated attempts to resolve service discovery queries, suggesting a potential issue with internal DNS resolution. As the incident progressed, the user impact became more pronounced, with several critical services experiencing downtime due to their inability to resolve necessary DNS records.

Monitoring caught the initial latency spikes through alerting rules set up on the metrics platform, which triggered notifications to the on-call team. However, the root cause of the issue—related to internal DNS—was not immediately apparent from the monitoring data alone. It required deeper investigation into the DNS query logs and service discovery mechanisms.

The evolution of symptoms over time indicated a worsening situation, with more services being affected as the DNS resolution issue persisted. This led to a broader impact on the business, affecting both internal tooling and external customer-facing services. The incident highlighted the critical nature of reliable internal DNS for service discovery and the need for more robust monitoring and alerting around this component.

As the investigation continued, it became clear that the issue was not just about latency but also about the reliability of service discovery. Services were failing to start or were experiencing intermittent failures due to unresolved DNS records. This underscored the importance of promptly addressing the root cause of the DNS resolution issue to restore platform stability.

## Diagnosis steps and hypotheses
Initial hypotheses suspected a network congestion issue, given the peak hour correlation. The team attempted to verify this by analyzing network traffic patterns, but evidence from `tcpdump` captures did not support significant congestion. 

A second hypothesis considered a recent change in the service discovery configuration as the potential culprit. However, reviewing the configuration history and comparing it against known good states did not reveal any discrepancies that could account for the DNS resolution failures.

The team also explored the possibility of a DNS server overload, considering the increased query volume during peak hours. To investigate this, they executed the following command to check the DNS server's response time:
```
dig +short dns-server.internal @10.0.1.5
```
This test showed that the DNS server was responsive but did not immediately indicate an overload condition.

Another hypothesis involved issues with the caching layer, potentially causing stale records or failures to update. The team inspected cache logs and found some inconsistencies in update timestamps, but purging the cache did not immediately resolve the issue.

Further investigation led to considering a hypothesis related to the DNS TTL settings, suspecting that an incorrect setting might cause premature expiration of cached records, leading to increased query loads on the DNS servers. This line of inquiry eventually uncovered the root cause.

The actual root cause emerged after a detailed review of the DNS configuration files and query patterns, revealing an incorrect `dns_ttl` setting that was too short, causing cached records to expire too quickly and resulting in a surge of DNS queries during peak hours.

## Resolution steps
1. Restart dns-cache service on node 10.0.1.5
2. Set dns_ttl to 300 in /etc/dns/config.yml
3. Clear cache with vault-cli --purge-cache
4. Update broker-admin with new dns_server_ip 10.0.1.10

## Post-mortem note
The internal DNS cache expired due to incorrect dns_ttl setting. This issue was initially missed because the monitoring focus was more on network and service performance rather than the specifics of DNS resolution times. The incident highlights the need for more granular monitoring of DNS services, especially around peak hours when the platform is under the most stress. Follow-up actions include implementing additional alerting rules for DNS query latency and conducting a review of all configuration settings related to service discovery to prevent similar issues in the future.
