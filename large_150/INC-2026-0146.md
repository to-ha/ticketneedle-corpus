## Symptom
The incident began with reports of asymmetric routing after a config push to the WAN aggregation router. Users noticed that while they could reach external services, return traffic was not being routed correctly, resulting in significant packet loss and timeouts. Initial observations suggested that the issue was intermittent, affecting some users more than others, but as time progressed, it became clear that the problem was widespread and persistent. Monitoring tools caught the issue through increased error rates on the router interfaces and a spike in ICMP destination unreachable messages. However, the monitoring system did not immediately alert on the asymmetric routing itself, requiring manual intervention to identify the root cause.

As the incident evolved, network engineers noticed that certain traffic flows were more affected than others, hinting at a configuration or routing table issue rather than a pure connectivity problem. The user impact was significant, with many external services becoming unreachable or highly unreliable. Business operations were severely impacted, especially those relying on real-time communications or data transfer. The incident highlighted the need for more granular monitoring of routing behavior and the importance of quickly identifying changes in network configuration that could lead to such issues.

Further investigation into the monitoring system's logs revealed that while it did detect anomalies in traffic patterns, it did not have the capability to automatically identify asymmetric routing as the cause. This limitation meant that the issue was not immediately flagged for review, leading to a delay in response. The engineers had to manually analyze traffic captures and routing tables to understand the extent of the problem. Tools like `traceroute` and `nft` were instrumental in diagnosing the issue, providing insights into the path traffic was taking and how firewall rules might be influencing routing decisions.

The asymmetric routing pattern observed during the incident was complex, involving not just the WAN aggregation router but also interactions with other network devices. However, the primary focus remained on the WAN aggregation router, given its central role in the observed symptom. Engineers like Sara and Carlos were involved early on, working to understand the routing behavior and identify potential configuration issues that could be causing the problem.

Given the complexity of the network and the specific nature of the symptom, diagnosing the issue required a deep dive into the router's configuration, routing tables, and traffic patterns. The fact that the issue appeared after a config push suggested that the change might have introduced a misconfiguration or incompatibility that was causing the asymmetric routing. This hypothesis guided the initial diagnostic efforts, with engineers scrutinizing recent changes to the router's configuration for any clues.

## Diagnosis steps and hypotheses
Initially, the team suspected that the issue might be related to a firewall rule misconfiguration, given the asymmetric nature of the routing problem. They attempted to diagnose this by reviewing firewall logs and rules, but found no evidence of blocked traffic that would explain the observed behavior. Next, they considered the possibility of a routing protocol issue, perhaps due to a misconfigured metric or a neighbor relationship problem. However, analysis of routing protocol messages and neighbor tables did not reveal any anomalies.

Another hypothesis was that the issue could be related to MTU size mismatch, which could cause packet fragmentation and lead to asymmetric routing issues. To investigate this, the team used the command ```
traceroute -n 8.8.8.8
``` to trace the path to a known external IP address and observe any MTU-related issues. While this did provide valuable information about the path and potential bottlenecks, it did not directly point to an MTU mismatch as the root cause.

The team also explored the possibility of a hardware failure or a firmware bug in the WAN aggregation router, considering that recent config pushes might have triggered a previously dormant issue. Diagnostic tests were run to assess the health of the router's interfaces and internal components, but no hardware issues were found. Furthermore, reviewing firmware release notes and known issue lists did not reveal any bugs that matched the observed symptom.

As the diagnosis progressed, the team began to focus more closely on configuration-related issues, given the timing of the incident with the recent config push. They carefully reviewed all changes made during the push, looking for any that could potentially cause asymmetric routing. It was during this detailed review that the actual root cause began to emerge, related to a specific configuration parameter that had been altered.

## Resolution steps
1. Restart router with config file /etc/router.cfg
2. Set MTU to 1500 on interface eth0
3. Update routing table with command nft add rule inet filter input tcp dport 22
4. Run traceroute -n 8.8.8.8 to verify path
5. Capture packets with tcpdump -i eth0 -n -vv -s 0 -c 100

## Post-mortem note
The WAN aggregation router was configured with an incorrect MTU size. This critical oversight led to the asymmetric routing issues observed during the incident, highlighting the importance of carefully reviewing configuration changes before implementation. The fact that this issue was missed initially underscores the need for more rigorous testing and validation procedures for config changes, especially those affecting critical network devices like the WAN aggregation router. Follow-up actions include a review of current config management processes to prevent similar incidents in the future and additional training for network engineers on the potential impacts of MTU size mismatches on network routing behavior.
