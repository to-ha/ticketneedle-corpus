## Symptom
The distributed filesystem metadata server began experiencing issues, leading to an increase in object replication lag. This growth past the SLA threshold triggered alerts and notified the on-call team. As the lag continued to rise, it became clear that immediate attention was necessary to prevent further disruption.

The replication lag was observed across multiple nodes, indicating a potential issue with the metadata server's ability to manage and synchronize data. Monitoring tools detected the anomaly, and automated alerts were sent to the L1 Platform support team for initial assessment.

Further investigation revealed that the issue was not limited to a single node or subset of data, suggesting a more systemic problem that required prompt resolution to maintain service integrity.

## Diagnosis steps and hypotheses
Initial hypotheses focused on network connectivity issues or configuration errors within the metadata server. However, as diagnostic efforts progressed, it became apparent that these were not the primary causes. 
``` 
rsync --dry-run -avz /mnt/data/ /mnt/backup/
```
This command was used to test the data synchronization process without actually transferring data, helping to isolate the problem. The output suggested that the issue lay with the metadata server itself rather than the data transfer process.

## Resolution steps
1. Restart metadata server on node 3
2. Set replication factor to 3 in /etc/metadata.conf
3. Run rsync --dry-run -avz /mnt/data/ /mnt/backup/
4. Verify disk health with smartctl -H /dev/sda

## Post-mortem note
The distributed filesystem metadata server experienced data corruption due to a failed disk. This incident highlights the importance of regular disk health checks and the need for robust redundancy in critical system components to prevent single points of failure.
