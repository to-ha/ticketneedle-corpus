## Symptom
The storage team noticed a significant increase in write latency on one of the volumes after a snapshot was taken. This increase in latency was observed through monitoring tools and reported by users attempting to write data to the affected volume. The latency spike was sudden and persistent, indicating a potential issue with the underlying storage infrastructure.

Further investigation revealed that the write latency was specifically impacting the distributed filesystem metadata server, which is responsible for managing file system metadata. This suggested that the issue might be related to the metadata server's ability to handle writes efficiently.

The symptom was consistently observed across multiple writes to the affected volume, ruling out transient issues and pointing towards a more persistent problem that required attention from the storage team.

## Diagnosis steps and hypotheses
Initial hypotheses included issues with disk health and potential misconfigurations in the metadata server. To investigate these possibilities, the team used various diagnostic tools. For instance, they ran 
```
smartctl -H /dev/sda
```
to check the health of the disks involved. Although this revealed some concerns with one of the disks, it did not directly point to the root cause of the write latency issue.

## Resolution steps
1. Restart metadata server on node3
2. Set replication_factor to 3 in /etc/distributed_fs.conf
3. Run rsync --dry-run -avz /mnt/data/ /mnt/backup/
4. Verify multipath -ll output for path redundancy

## Post-mortem note
The distributed filesystem metadata server experienced data inconsistency due to a failed disk. This incident highlights the importance of regularly checking disk health and ensuring that the metadata server is properly configured for redundancy to prevent such issues in the future.
