- **Priority:** P2
- **Domain:** Network
- **Status:** Resolved

## Symptom
The incident began with reports of a DNS resolution latency spike to 5-10 seconds, affecting users trying to access the application. This latency issue was observed across multiple geographic locations, indicating a widespread problem rather than a localized one. Initial observations suggested that the issue was not related to the application itself but rather to how users were being routed to it.

Further investigation revealed that the latency was specifically tied to the edge load balancer's interaction with DNS resolution. It seemed that requests were taking an inordinately long time to resolve, leading to a backlog of unanswered requests and thus perceived latency by the end-users. This symptom complex pointed towards an issue within the network infrastructure, particularly at the point where traffic was being balanced across different nodes.

## Escalation timeline
- 12:30 — L1 Network operations: Olu began reviewing the network logs for any signs of errors or unusual patterns that could explain the latency spike.
- 12:51 — L2 Network engineer: Rafael took over, focusing on the configuration of the edge load balancers to ensure they were properly set up and functioning as expected.
- 13:49 — L3 Network architect: Anya was brought in to assess the overall architecture and identify any potential bottlenecks or misconfigurations that could be causing the issue.

## Diagnosis steps and hypotheses
Initial hypotheses included a potential misconfiguration of the load balancers or an issue with the DNS servers themselves. To investigate, the team used `tcpdump` to capture traffic and analyze the communication between the load balancers and the DNS servers. Specifically, they ran:
```
tcpdump -i eth0 port 80
```
This helped in identifying that the problem was not with the application or the DNS servers but rather how requests were being handled by the edge load balancer. Further analysis of the load balancer logs revealed issues with timeout settings, which seemed to be the root cause of the latency spike.

## Resolution steps
1. Restart edge load balancer on node 1
2. Set timeout to 30 seconds in /etc/loadbalancer.conf
3. Update DNS TTL to 300 seconds using nslookup

## Post-mortem note
The edge load balancer failed to properly distribute traffic due to a misconfigured timeout. This incident highlights the importance of regularly reviewing configuration settings, especially in critical infrastructure components like load balancers, to prevent such issues from arising. Proper monitoring and swift escalation procedures also played a crucial role in mitigating the impact of this incident.
