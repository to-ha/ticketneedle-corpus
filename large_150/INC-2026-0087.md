## Symptom
The network team noticed an asymmetric routing issue after a recent configuration push to the edge load balancer. This resulted in some incoming traffic being routed incorrectly, causing delays and packet loss for a subset of users. The issue was first identified through monitoring tools, which alerted on unusual traffic patterns.

Further investigation revealed that the asymmetric routing was causing problems with session persistence, leading to user complaints about intermittent connectivity issues. The network operations team was initially stumped, as the configuration push had been thoroughly tested in a staging environment before being deployed to production.

The symptom complex was characterized by an increase in latency and packet loss for traffic flowing through the affected load balancer, with some users experiencing complete loss of connectivity. This was observed using tools like MTR and Wireshark, which helped to pinpoint the issue to the edge load balancer.

## Diagnosis steps and hypotheses
Initial hypotheses focused on issues with the load balancer's configuration or the network topology. The team used `iperf3` to test network throughput and identify any bottlenecks. Specifically, they ran the command:
```
iperf3 -c lb.example.com -p 80
```
This helped to rule out some potential causes, such as bandwidth limitations or firewall restrictions. However, it did not immediately reveal the root cause of the asymmetric routing issue.

## Resolution steps
1. Restart load balancer with -c 4 option
2. Set timeout to 30 seconds in /etc/lb/config
3. Increase buffer size to 1024KB
4. Disable keepalive with --no-keepalive flag

## Post-mortem note
The edge load balancer was misconfigured with too low buffer size. This led to the asymmetric routing issue and resulting connectivity problems for users. In the future, the team will ensure that configuration changes are more thoroughly tested and validated before deployment to production.
