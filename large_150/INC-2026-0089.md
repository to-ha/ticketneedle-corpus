## Symptom
The incident began with reports of MFA push notifications being delivered but never accepted, leading to authentication failures for a subset of users. This symptom was first observed by the monitoring team, who noticed a spike in authentication errors around the time the issue started. Further investigation revealed that the affected users were all part of a specific directory group, suggesting a potential issue with directory replication.

As the incident progressed, more users began to report issues with authentication, and the monitoring team observed an increase in error rates for MFA-related transactions. The operations team attempted to troubleshoot the issue using tools like `ldapsearch` and `pam-test`, but were initially unable to identify the root cause. The symptom complex was characterized by a consistent pattern of failed authentications following successful MFA push notifications, indicating a potential problem with the directory service.

The impact of the incident was significant, as affected users were unable to access critical systems and applications. The operations team worked to mitigate the issue by implementing temporary workarounds, such as manual authentication overrides, but these measures were not scalable and did not address the underlying cause. As the incident continued to affect a growing number of users, it became clear that a more comprehensive solution was needed.

The symptom was further analyzed using `session-trace`, which provided insight into the authentication flow and helped to narrow down the possible causes. However, the root cause remained elusive, and the incident required escalation to more senior teams for further diagnosis and resolution.

## Diagnosis steps and hypotheses
The diagnosis process involved several hypotheses, each of which was tested and ruled out based on the available evidence. One initial hypothesis was that the issue was related to a recent change in the MFA configuration, but this was ruled out after reviewing the change history and verifying that the MFA settings were correct.

Another hypothesis was that the problem lay with the directory service itself, potentially due to a software bug or misconfiguration. To investigate this, the team used `ldapsearch` to query the directory and verify its integrity. For example, the following command was used to test the directory connection:
```
ldapsearch -H ldaps://node1:636 -D cn=admin -w password -b dc=example,dc=com
```
However, this hypothesis was also ruled out after verifying that the directory service was functioning correctly and that there were no obvious misconfigurations.

## Resolution steps
1. Stop directory replication service on node 1
2. Set replication interval to 300 seconds in /etc/directory/replication.conf
3. Restart directory replication service on node 1
4. Verify replication status with ldapsearch -H ldaps://node2:636 -D cn=admin -w password

## Post-mortem note
The root cause of the incident was determined to be a misconfigured replication interval, which prevented the directory service from correctly replicating changes. Directory replication failed due to misconfigured interval. This issue was ultimately resolved by adjusting the replication interval and restarting the directory replication service, which restored normal functionality to the authentication system.
