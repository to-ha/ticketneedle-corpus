## Symptom
The incident began with reports of intermittent network connectivity issues, specifically BGP session flapping every few minutes. This pattern was observed across multiple nodes in the recursive DNS resolver cluster, causing concerns about the stability of the network. Further investigation revealed that the BGP sessions would drop and then re-establish themselves after a short period, resulting in temporary losses of connectivity. The impact of this symptom was significant, as it affected the ability of users to access certain resources and caused delays in data transfers.

As the incident progressed, the frequency of the BGP session flapping increased, leading to more prolonged periods of network instability. The operations team noticed that the issue seemed to be related to the DNS resolver cluster, as the flapping sessions were often preceded by spikes in DNS query traffic. To better understand the issue, the team used tools like `iperf3` to measure network performance and `dig` to test DNS resolution.

The `tcpdump` tool was also utilized to capture network traffic and analyze the packets being transmitted. This helped the team to identify patterns in the traffic that might be contributing to the BGP session flapping. Despite these efforts, the root cause of the issue remained elusive, and the team needed to escalate the incident to gather more expertise.

The symptom complex was characterized by a clear correlation between DNS query traffic and BGP session flapping. When DNS query traffic increased, the likelihood of a BGP session flap also increased. This suggested that the issue might be related to the way the DNS resolver cluster was handling queries or the resources available to it.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential network misconfigurations or resource constraints within the DNS resolver cluster. The team considered the possibility of inadequate bandwidth, incorrect routing tables, or insufficient server resources. However, as they delved deeper into the issue, these hypotheses were ruled out based on the evidence gathered.

One key diagnostic step involved testing DNS resolution directly using the command:
```
dig +short example.com @10.0.1.100
```
This test helped to isolate the issue to the DNS resolver cluster and suggested that the problem might be related to how the cluster was handling recursive queries.

Further analysis of the DNS query traffic and server logs revealed patterns that pointed towards the DNS resolver service as the likely source of the issue. The team hypothesized that the service might be experiencing high latency or was unable to handle the volume of queries efficiently, leading to the observed BGP session flapping.

## Resolution steps
1. Restart dns-resolver service on node 10.0.1.100
2. Set max_cache_size to 10000 in /etc/dns/resolver.conf
3. Increase worker_threads to 8 in /etc/dns/resolver.conf
4. Run tcpdump -i eth0 port 53 to verify DNS traffic

## Post-mortem note
The recursive DNS resolver cluster experienced high latency due to insufficient cache size and worker threads. This root cause was identified after a thorough analysis of the DNS query traffic patterns and the performance of the DNS resolver service. The resolution steps effectively addressed the issue by adjusting the cache size, increasing the number of worker threads, and verifying DNS traffic. These changes ensured that the DNS resolver cluster could handle the query load more efficiently, thereby preventing future occurrences of BGP session flapping.
