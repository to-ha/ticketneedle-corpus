## Symptom
The message broker queue depth began to grow unbounded, indicating a potential issue with the feature-flag service. This symptom was first observed by monitoring tools, which alerted the team to the rising queue depth. As the queue continued to grow, it became clear that the issue was causing delays in message processing.

Further investigation revealed that the feature-flag service was not properly filtering messages, resulting in a large number of unnecessary messages being added to the queue. This led to a significant increase in queue depth, causing concerns about the potential for message loss or corruption.

The unbounded growth of the message broker queue depth suggested a problem with the feature-flag service's ability to manage messages effectively. The team's initial focus was on identifying the root cause of this issue and finding a solution to prevent further queue growth.

## Diagnosis steps and hypotheses
Initial hypotheses centered around issues with the message broker itself or the network connectivity between the broker and the feature-flag service. However, after running diagnostic commands such as `vault read -field=value /secret/feature-flag/config`, it became clear that the problem lay within the feature-flag service's configuration or caching mechanism.
``` 
vault read -field=value /secret/feature-flag/config
```
This command helped to rule out issues with the broker or network, focusing attention on the feature-flag service.

## Resolution steps
1. Restart feature-flag service with --reset-cache flag
2. Set cache.ttl to 300 in /etc/feature-flag/config.yaml
3. Run registry-gc --dry-run to identify stale entries
4. Remove outdated flags using broker-admin --delete-flag

## Post-mortem note
The feature-flag service cache was not properly reset after a configuration update. This oversight led to the cache becoming outdated, causing the feature-flag service to malfunction and resulting in the unbounded growth of the message broker queue depth. Steps have been taken to ensure that cache resets are properly handled in the future to prevent similar incidents.
