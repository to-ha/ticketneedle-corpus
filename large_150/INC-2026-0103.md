## Symptom
CI pipelines began stalling on the same stage across all repositories, indicating a potential issue with the shared resources utilized by these pipelines. This symptom was first observed by the development team when they noticed that their builds were not completing as expected. Further investigation revealed that the stall occurred consistently at a specific stage, suggesting a common dependency or resource was causing the issue.

The development team reported this incident, highlighting that the affected stage involved interactions with the shared message broker. This information was crucial as it narrowed down the potential causes to issues related to the message broker or its configuration.

* 12:55 — L2 Platform engineer: Carlos - Carlos took over, focusing on checking the network connectivity and firewall rules that might affect the message broker.

## Diagnosis steps and hypotheses
Initial hypotheses included network connectivity issues, firewall rule misconfigurations, and problems with the message broker's configuration. To diagnose these potential issues, the team used various tools such as `registry-gc` to check for any garbage collection issues, `runner-logs` to inspect the pipeline execution logs, and most importantly, `broker-admin` to manage and inspect the message broker. A key command used in the diagnosis was:
```
broker-admin --check-connections
```
This command provided insight into the current connection status of the message broker, helping to narrow down the root cause of the issue.

## Resolution steps
1. Restart broker with --max-connections=500
2. Set broker.config.max_message_size to 10240
3. Run registry-gc --dry-run --broker=localhost:9092
4. Verify broker-admin --check-connections reports < 400

## Post-mortem note
The shared message broker exceeded its connection limit. This issue was resolved by adjusting the broker's configuration and verifying its connection status, ensuring that CI pipelines could complete without stalling due to broker connectivity issues.
