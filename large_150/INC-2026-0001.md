## Symptom
The incident began with reports of pods stuck in CrashLoopBackOff after a node reboot. This symptom was first observed by monitoring tools, which alerted the on-call team to investigate potential issues with node stability. Upon further inspection, it became clear that the affected node had recently undergone a restart, and since then, several pods had failed to recover, entering a crash loop. The immediate impact was a reduction in service availability, as some critical components were hosted on the affected node. Given the nature of the symptom, the initial focus was on understanding the node's behavior post-reboot and why pods were unable to stabilize.

As the investigation progressed, additional details emerged indicating that the issue was not limited to a single pod or application but was rather a systemic problem affecting multiple workloads running on the node. This suggested that the root cause might be related to a configuration issue, resource allocation problem, or a bug in the node's runtime environment. The on-call team recognized the urgency of resolving the issue quickly to minimize downtime and prevent potential cascading failures.

Further analysis revealed patterns in the pod's crash logs that hinted at resource exhaustion or misconfiguration at the node level. However, without direct access to the node's configuration and runtime data, it was challenging to pinpoint the exact cause. The team decided to escalate the issue to gather more expertise and resources to tackle the problem efficiently.

The symptom complex presented a challenge because it touched on several potential areas of failure, including node configuration, resource management, and application resilience. Each of these areas required careful examination to identify the root cause and apply an effective remedy. The team's approach involved systematically ruling out potential causes through a combination of log analysis, configuration reviews, and targeted testing.

## Diagnosis steps and hypotheses
Initial hypotheses centered around resource allocation issues or potential misconfigurations at the node or pod level. To explore these hypotheses, the team employed various diagnostic tools. One key command used in the diagnosis was:
```
crictl info --output json
```
This helped in gaining insights into the runtime environment of the containers and identifying any discrepancies in resource allocation or configuration.

Another hypothesis considered was that the node's kubelet might be malfunctioning or incorrectly configured, leading to the pods' inability to recover from the crash loop. Evidence from logs and node metrics suggested that while resource usage was within expected limits, there might be an issue with how resources were being allocated to pods. However, detailed analysis of pod configurations and node settings did not reveal any overt misconfigurations that would cause such a widespread issue.

The team also explored the possibility of a bug in the runtime environment or an incompatibility between different components of the Kubernetes setup. Although this seemed less likely given the lack of recent changes to the environment, it remained a consideration until more direct evidence of the root cause could be found.

## Resolution steps
1. Restart kubelet on node-1 with --v=4 flag
2. Set /etc/kubernetes/kubelet.conf max-pods to 110
3. Run crictl logs --since 1h to check for errors
4. Update helm chart values to increase node resources
5. Verify node CPU allocation with stern -n kube-system

## Post-mortem note
The node kubelet crashed due to excessive pod allocation. This incident highlighted the importance of closely monitoring node resource utilization and pod allocation limits to prevent similar crashes in the future. Regular reviews of node configurations and automated scaling policies can help mitigate such risks, ensuring more resilient and efficient operation of Kubernetes clusters.
