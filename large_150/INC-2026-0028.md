## Symptom
The monitoring system began firing alerts that would resolve within seconds, only to re-fire in a flapping pattern. This behavior was observed across multiple probe types, indicating a potential issue with the synthetic-probe runner. The rapid firing and resolution of alerts suggested an instability or misconfiguration in the probe runner's operation.

Further investigation revealed that the flapping pattern was consistent, with alerts being triggered and then cleared in quick succession. This pattern made it challenging to pinpoint the exact cause, as the system would appear to return to normal operation briefly before the issue recurred.

The symptom complex centered around this flapping pattern, which hinted at a deeper issue affecting the probe runner's ability to maintain a stable state.

## Diagnosis steps and hypotheses
Initial hypotheses included a misconfiguration in the probe runner or issues with the underlying metrics database. To investigate these hypotheses, the team used various tools, including `tsdb-cli` to query the database directly. A key command used during diagnosis was:
```
tsdb-cli --query 'probe_runner_status'
```
This helped in understanding the current state of the probe runner and its interaction with the metrics database. However, the root cause remained elusive until further analysis of the logs and configuration files.

## Resolution steps
1. Restart probe runner with --max-retries 3
2. Set scrape_interval to 15s in tsdb config
3. Increase log level to DEBUG at /etc/probe-runner/logging.conf
4. Run promtool to reload tsdb configuration

## Post-mortem note
The synthetic-probe runner failed to restart after a crash. This incident highlighted the importance of ensuring that the probe runner is properly configured for resilience and that monitoring alerts are promptly addressed to prevent similar issues in the future.
