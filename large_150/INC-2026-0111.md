# Major Incident — INC-2026-0111

* **Domain:** Platform infrastructure
* **Status:** Resolved

## Symptom
The incident began with reports of secret rotation breaks in one downstream consumer, which relied on the shared message broker for secure communication. This breakage resulted in failed authentication attempts and subsequent service disruptions. Upon initial observation, it seemed that the issue was isolated to a specific consumer, but as the situation unfolded, it became clear that the problem was more systemic, affecting the message broker's ability to handle connections efficiently.

Further investigation revealed that the affected consumer was experiencing timeouts when attempting to connect to the message broker, indicating a potential issue with the broker's capacity to manage concurrent connections. This symptom was critical because it not only affected the immediate functionality of the downstream service but also had the potential to cascade and impact other services relying on the same message broker.

The monitoring systems in place alerted the team to an unusual spike in connection attempts to the message broker around the time the issue started, suggesting that the broker might have been overwhelmed. This led to a focus on understanding the broker's current configuration and its ability to handle the load.

Given the nature of the symptom—secret rotation breaks in a downstream consumer—it was crucial to consider how changes or issues in the message broker could propagate and affect dependent services. The team recognized that resolving this incident would require a deep dive into the message broker's performance, configuration, and recent changes.

## Diagnosis steps and hypotheses
Initial hypotheses centered around a potential misconfiguration of the message broker or an unexpected surge in traffic. The team considered the possibility that recent changes to the broker's settings might have inadvertently limited its capacity. Another hypothesis was that one or more topics were experiencing unusually high volumes, overwhelming the broker.

To investigate these hypotheses, the team used various tools, including `registry-gc` to inspect topic usage and `vault`-style CLI commands to review configuration settings. A key step in the diagnosis involved running the command:
```
kubectl logs broker -c message-broker | grep 'max connections'
```
This command helped identify if the broker was indeed hitting its maximum connection limit, which could explain the timeouts and failures observed by the downstream consumer.

Despite these efforts, the initial hypotheses did not fully explain the root cause of the issue, leading to a deeper investigation into the message broker's configuration and performance metrics.

## Resolution steps
1. Restart message broker with --max-connections 500
2. Set vault.broker.max-inflight to 2000 in /etc/broker/config
3. Run registry-gc with --dry-run to identify unused topics
4. Remove unused topics with vault topic delete --force
5. Adjust runner-log retention to 30 days with --log-retain 30d

## Post-mortem note
Message broker crashed due to exceeding maximum connections. This incident highlighted the importance of regularly reviewing and adjusting the message broker's configuration to ensure it can handle the evolving needs of dependent services. In the aftermath, the team implemented additional monitoring to track connection usage and automated alerts for when the broker approaches its connection limit, aiming to prevent similar incidents in the future.
