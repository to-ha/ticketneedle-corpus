# Major Incident — INC-2026-0142
* **Ticket ID:** INC-2026-0142
* **Reported:** 2026-03-19 07:52 UTC
* **Priority:** P2
* **Domain:** Database
* **Status:** Resolved

## Symptom
The primary SQL replica experienced a sudden and significant increase in query latency, with the p99 latency jumping from 20ms to 4s. This increase in latency was observed by both users and monitoring tools, causing a noticeable degradation in database performance. Further investigation revealed that this issue was not limited to a specific query or workload, but rather a broad increase in latency across all queries.

The increase in latency was first detected by the monitoring tools, which triggered an alert to the on-call team. Users also reported experiencing slow response times and timeouts when interacting with the database. The symptom was consistent across all users and workloads, indicating a systemic issue with the primary SQL replica.

Initial observations suggested that the issue might be related to resource contention or configuration issues, but further diagnosis was needed to determine the root cause.

## Escalation timeline
* 07:54 — L1 Database operator: Leila: Leila began investigating the issue and gathering initial data on the system's performance and configuration.
* 08:39 — L2 Database engineer: Ahmed: Ahmed took over the investigation, focusing on deeper analysis of the database's configuration and performance metrics.

## Diagnosis steps and hypotheses
Initial hypotheses focused on resource contention, such as CPU or memory limitations, and potential configuration issues. To investigate these hypotheses, the team used tools like `pidstat` to monitor system resource utilization and `psql` equivalent clients to inspect database performance and configuration. A key command used in the diagnosis was:
```
psql -c "SHOW max_connections;"
```
This command helped identify a potential issue with the database's connection limit, which was later confirmed as the root cause.

## Resolution steps
1. Restart primary SQL replica on node 1
2. Set max_connections to 500 in postgresql.conf
3. Run VACUUM on database foo with verbose output
4. Adjust shared_buffers to 2GB in postgresql.conf

## Post-mortem note
The primary SQL replica exceeded its connection limit due to misconfigured max_connections. This incident highlights the importance of regularly reviewing and adjusting database configuration parameters to ensure optimal performance and prevent similar issues in the future.
