## Symptom
The incident began with reports of application threads being blocked due to a saturated connection pool. This symptom first appeared as intermittent errors in the application logs, where threads would timeout waiting for a database connection. As the issue evolved, the frequency and duration of these errors increased, eventually leading to a complete halt in application functionality. The user impact was significant, with all users experiencing errors when attempting to perform any action that required database access. Monitoring caught the issue through alerts on connection pool utilization and application error rates. However, the monitoring did not provide clear insights into the root cause, necessitating further investigation.

Initial observations suggested that the connection pool was being exhausted due to an unusually high volume of incoming requests. However, upon closer inspection, it became apparent that the request volume was within expected parameters, suggesting that the issue lay elsewhere. The database metrics showed a high number of active connections, but no corresponding increase in query execution time or resource utilization, which further complicated the diagnosis.

As the incident progressed, the team focused on understanding the connection pool behavior and its impact on the application. It was noted that the application threads were not only blocked but also that the database was not responding with errors that could explain the connection saturation. This led to a deeper dive into the database configuration and the connection pooling mechanism.

The symptom complex was characterized by a rapid increase in connection pool utilization, followed by application thread blocking, and eventually, a complete application outage. The fact that the database itself did not report any errors or significant performance degradation made it challenging to pinpoint the exact cause. The team had to rely on detailed logs from both the application and the database, as well as metrics on connection pool usage and application performance.

Further analysis of the application logs revealed patterns of connection acquisition and release, which seemed to be in line with expectations. However, the database logs hinted at a potential issue with connection handling, though it was not immediately clear what this meant for the overall system behavior. The team decided to investigate the database configuration more thoroughly, looking for any parameters that could influence connection pool behavior.

## Diagnosis steps and hypotheses
Initially, the team suspected that the issue might be related to an unexpected surge in application traffic, leading to an increased demand for database connections. To investigate this hypothesis, they analyzed the application request logs but found no evidence of unusual traffic patterns.

Next, they considered the possibility of a database performance issue, such as slow queries or locks, that could prevent connections from being released back to the pool. Diagnostic steps included running `EXPLAIN ANALYZE` on recently executed queries and checking for any lock contention, but neither approach yielded conclusive evidence.

Another hypothesis was that the connection pooling mechanism itself was malfunctioning. The team inspected the pgbouncer logs and configuration, looking for any signs of misbehavior or misconfiguration. This led to the execution of the following command to check the current connection limit:
```
psql -h db01 -c "SHOW max_connections;"
```
The result showed that the max connections setting was lower than expected, which could contribute to the connection pool saturation under load. However, this alone did not fully explain the observed behavior, as the application should have been able to manage connections effectively even with this limit.

Further investigation considered the database's ability to handle the current workload, including checking for any resource bottlenecks such as CPU, memory, or disk usage. While some resources were utilized at a higher level than usual, none were at a critical threshold that would explain the connection exhaustion.

The team also explored the possibility of network issues affecting communication between the application and the database, potentially leading to connections being left in an idle state. Network diagnostics, including `tcpdump` and `dig`, did not reveal any issues that could account for the symptoms observed.

As the diagnosis progressed, it became clear that the root cause was more nuanced than initially thought, involving a combination of database configuration, connection pooling settings, and application behavior. The actual root cause emerged after a detailed review of all relevant configurations and logs, pointing towards a misconfiguration in the max connections setting and an inappropriate connection pooling strategy for the given workload.

## Resolution steps
1. Restart primary SQL replica on host db01
2. Set max_connections to 500 in postgresql.conf
3. Adjust pgbouncer.ini to increase max_db_connections to 200
4. Run VACUUM FULL on tables with high bloat factor
5. Analyze query plans using EXPLAIN ANALYZE

## Post-mortem note
The primary SQL replica experienced connection exhaustion due to misconfigured max connections. This issue was initially missed because the monitoring focused more on application-level metrics rather than deep database configuration and performance metrics. In hindsight, a more detailed review of the database settings and connection pooling strategy during the initial deployment could have prevented this incident. Follow-up actions include a thorough audit of all database configurations to ensure that max connections settings are appropriately tuned for each environment, as well as enhancing monitoring to include more detailed database performance and configuration metrics. Additionally, the team will conduct a workshop on database performance tuning and connection pooling best practices to prevent similar incidents in the future.
