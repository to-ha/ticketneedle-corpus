# Major Incident — INC-2026-0021
* **Ticket ID:** INC-2026-0021
* **Reported:** 2026-03-21 21:22 UTC
* **Priority:** P1
* **Domain:** Authentication
* **Status:** Resolved

## Symptom
The incident began with reports of JWT signature validation failures for a subset of tokens. This issue manifested as intermittent authentication errors, where users would be unable to access protected resources despite providing valid credentials. The errors were not consistent across all users, suggesting that the problem was related to a specific subset of authentication tokens. Further investigation revealed that the affected tokens all shared a common characteristic: they had been issued recently, within a narrow time window. This pattern suggested a potential issue with the token issuance process or the underlying directory replication mechanism.

As the incident progressed, the scope of the problem became clearer. The failed authentications were not limited to a specific application or service but were instead widespread, affecting multiple components that relied on the same authentication infrastructure. This broad impact underscored the critical nature of the issue and highlighted the need for a swift resolution. Monitoring systems began to pick up on the increasing error rates, triggering alerts and notifications to the on-call teams.

The symptom complex was characterized by a significant spike in authentication failure rates, which correlated with the issuance of new tokens. This correlation pointed towards a problem in the directory replication or token validation processes. Given the specific nature of the failures—JWT signature validation errors—it was reasonable to suspect an issue related to the cryptographic components of the authentication system or the synchronization of directory data.

The initial observable pattern of JWT signature validation failures for a subset of tokens provided a clear direction for further investigation. The fact that only recently issued tokens were affected suggested a temporal component to the issue, potentially related to changes in the token issuance process, directory replication delays, or cryptographic key management.

## Diagnosis steps and hypotheses
Initial hypotheses focused on potential issues with the cryptographic keys used for token signing, given the nature of the JWT signature validation failures. One possibility considered was that the private key used for signing had been compromised or corrupted, leading to invalid signatures on newly issued tokens. Another hypothesis was that there was a misconfiguration in the token issuance process, perhaps related to the integration with the directory service.

To investigate these hypotheses, several diagnostic steps were taken. The `openssl s_client` command was used to inspect the SSL certificates used by the directory replication service, as issues here could potentially affect the synchronization of user data and, by extension, token validity:
```
openssl s_client -connect dirsync.example.com:636 -showcerts
```
This command provided insight into the certificate chain and helped rule out certain hypotheses related to SSL/TLS configuration. However, it did not directly point to the root cause of the JWT signature validation failures.

Further analysis involved using a jwt.io equivalent decoder to examine the tokens that were failing validation. This tool provided detailed information about the token structure, including the header, payload, and signature. By comparing successful and failed tokens, the team aimed to identify any differences that could explain the validation errors.

Despite these efforts, the initial hypotheses regarding cryptographic key issues or token issuance misconfigurations were not supported by the evidence. It became clear that a deeper issue related to directory replication and synchronization was at play, affecting the consistency of user data across the system.

## Resolution steps
1. Restart directory replication service on node 3
2. Set replication delay to 30 seconds in /etc/dirsync.conf
3. Update pam-test configuration to use the new directory endpoint
4. Verify jwt.io equivalent decoder output for authentication headers

## Post-mortem note
The root cause of the incident was determined to be related to issues with the directory replication mechanism. Specifically, Directory replication failed due to misconfigured SSL certificates. This misconfiguration led to delays and inconsistencies in user data synchronization, which in turn caused the JWT signature validation failures observed during the incident. The swift identification and correction of this issue were crucial in minimizing the impact on users and restoring normal service operations.
