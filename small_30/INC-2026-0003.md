## Symptom

The incident began with reports of intermittent delays in outbound API calls, which were taking 5-10 seconds to complete due to DNS resolution stalls. This slowdown would mysteriously disappear for a few minutes after a resolver cache flush, only to return later. The affected services relied on MPLS L3VPN for connectivity between two sites, and the MTU black hole between these sites was suspected to be the root cause of the issue. Further investigation revealed that the DNS resolution times were indeed erratic, with some queries taking significantly longer than others to resolve.

As the incident progressed, it became clear that the symptom was not limited to a specific set of users or services, but rather was a widespread issue affecting all API calls that relied on DNS resolution. The intermittent nature of the problem made it challenging to diagnose, as the issue would often resolve itself temporarily after a cache flush. However, the fact that the slowdown would return after a few minutes suggested that there was an underlying configuration or infrastructure issue that needed to be addressed.

The observable pattern of MTU black hole between two sites was a key indicator of the problem, and tools like MTR, nslookup, and Wireshark were used to investigate the issue further. These tools helped to identify the erratic DNS resolution times and the impact of the MTU black hole on the API calls. By analyzing the data from these tools, the engineering team was able to narrow down the possible causes of the incident and develop a plan to resolve it.

The impact of the incident was significant, as the delayed API calls were causing disruptions to critical business services. The engineering team worked urgently to resolve the issue, knowing that every minute of downtime was resulting in lost productivity and revenue. As the team worked to identify the root cause of the problem, they remained focused on finding a solution that would prevent similar incidents from occurring in the future.

## Diagnosis steps and hypotheses

The engineering team considered several hypotheses to explain the intermittent delays in outbound API calls. One possibility was that the issue was related to the MPLS L3VPN configuration, specifically the MTU settings between the two sites. To investigate this hypothesis, the team used tools like MTR and nslookup to analyze the DNS resolution times and the impact of the MTU black hole on the API calls.

Another hypothesis was that the problem was caused by a misconfiguration of the DNS resolver. To test this hypothesis, the team ran the following command:
```
dig +edns=4096 example.com
```
The results of this test helped to rule out the DNS resolver misconfiguration hypothesis and pointed towards an issue with the EDNS0 buffer size.

The team also considered the possibility that the issue was related to network congestion or packet loss, but further analysis of the network logs and monitoring data did not support this hypothesis. By systematically testing and ruling out each hypothesis, the team was able to narrow down the possible causes of the incident and develop a plan to resolve it.

## Resolution steps

1. Set edns-buffer-size to 1232 in /etc/resolver/config
2. Restart resolver daemon with systemctl restart resolver
3. Verify new buffer size with dig +edns=1232 example.com
4. Monitor DNS resolution times with mtr --dns example.com
