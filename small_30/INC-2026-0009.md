## Symptom
The incident began with reports of DNS resolution latency spikes, where queries would take 5-10 seconds to resolve. This slowdown was intermittent and seemed to disappear for a few minutes after a resolver cache flush. Users experienced this as outbound API calls stalling for the same duration, directly impacting service responsiveness. The pattern was consistent across multiple observations, suggesting a specific issue rather than a generalized network problem.

Further investigation revealed that the latency spike was not uniform across all DNS queries but was particularly pronounced for certain domains. This hinted at an issue that might be related to the DNS resolution process itself, rather than a broader network connectivity problem.

Monitoring tools picked up on the increased latency, triggering alerts that drew attention to the issue. The symptom complex revolved around this core observation of delayed DNS resolution, which was the primary indicator of the problem.

## Diagnosis steps and hypotheses
Initial hypotheses included issues with network connectivity or problems with the anycast VIP setup. However, these were ruled out through tests like iperf3 and MTR, which showed no significant packet loss or latency outside of DNS queries. 

A key diagnostic step involved running 
```
dig +nssearch example.com
```
to understand the DNS resolution path better. This helped in narrowing down the issue to the DNS resolution process itself.

## Resolution steps
1. Set negative-TTL to 60s in /etc/resolv.conf
2. Add second upstream resolver 8.8.8.8 to /etc/resolv.conf
3. Restart resolver service with systemctl restart resolv
4. Verify failover with dig +trace example.com

## Post-mortem note
Recursive resolver hit upstream rate limit on a single authoritative zone. This root cause was identified through the diagnostic process and addressed by implementing the resolution steps, which effectively mitigated the issue and restored normal DNS resolution times.
