## Symptom
The incident began with a noticeable increase in write latency on one of the object storage volumes, specifically after a snapshot was taken. This latency spike was first observed by the monitoring system, which triggered an alert due to the deviation from the expected baseline performance. Initially, the impact was limited, but as time progressed, the latency increased, affecting the overall performance of the storage system and causing delays in data replication. Users started reporting issues with uploading and accessing files, indicating a significant business impact. The monitoring system caught the initial latency spike but missed the underlying cause, which was related to the object storage bucket replication.

As the incident evolved, the team noticed that the affected volume was experiencing a higher than usual number of write operations, which seemed to exacerbate the latency issue. The metrics platform showed a correlation between the write latency and the number of concurrent writes, suggesting that the storage system was struggling to keep up with the demand. However, this correlation did not immediately point to the root cause of the problem. The team had to dig deeper to understand the relationship between the write latency, snapshot creation, and the object storage bucket replication.

Further analysis revealed that the snapshot creation process was triggering a cascade of events that ultimately led to the increased latency. The snapshot process was causing the storage system to temporarily divert resources, which in turn affected the replication process. This diversion of resources was not immediately apparent and required a detailed examination of the system's logs and metrics. The team used tools like `tcpdump` and `psql` to analyze the network traffic and database queries, respectively, to better understand the system's behavior.

The user impact was significant, with reports of failed uploads and delayed access to files. The business rely on the object storage system for critical operations, and any disruption to this service has a direct impact on their ability to function. The incident highlighted the need for more robust monitoring and alerting mechanisms to detect such issues earlier and minimize the impact on users.

The monitoring system's initial alert was based on a predefined threshold for write latency. However, this threshold did not account for the specific scenario of snapshot creation and its impact on replication. As a result, the alert was triggered only after the latency had already increased significantly, delaying the response to the incident. In retrospect, adjusting the monitoring thresholds and incorporating more nuanced alerting logic could have helped identify the issue sooner.

## Diagnosis steps and hypotheses
The team initially suspected that the issue might be related to a hardware problem, given the sudden increase in latency. They checked the disk health using `smartctl` and found no issues, which ruled out this hypothesis. Next, they considered the possibility of a network congestion problem, but analysis of the network traffic using `tcpdump` did not show any signs of congestion.

Another hypothesis was that the snapshot process itself was causing the latency, perhaps due to the way it was configured or the resources it required. However, reviewing the snapshot configuration and the system resources during the snapshot process did not reveal any obvious issues. The team then considered the possibility of a problem with the replication process, but initial checks of the replication status did not indicate any faults.

To further investigate the storage paths and potential issues with multipathing, the team used the following command:
```
multipath -ll
```
This command provided detailed information about the multipath configuration and helped in identifying if there were any issues with the storage paths. However, the output did not show any problems that could directly explain the latency issue.

The team also explored the hypothesis that the object storage service was malfunctioning or not properly configured. They checked the service logs and configuration files but found no evidence to support this theory. It wasn't until they dug deeper into the replication settings and how they interacted with the snapshot process that they began to understand the root cause of the issue.

## Resolution steps
1. Restart object storage service on node 3 with --force flag
2. Set replication factor to 3 in /etc/objectstorage/config.yaml
3. Run rsync --dry-run -avz /mnt/data/ to test replication sync
4. Verify multipath -ll output for healthy storage paths on all nodes
5. Adjust smartctl -a /dev/sdb settings to optimize disk performance

## Post-mortem note
The object storage bucket replication failed due to a misconfigured replication factor. This issue was missed initially because the monitoring system did not account for the specific scenario of snapshot creation impacting replication. The root cause was only identified after a thorough analysis of the system's behavior and configuration. To prevent similar incidents in the future, adjustments will be made to the monitoring thresholds and alerting logic to better detect anomalies related to snapshot creation and replication. Additionally, the team will review and refine the object storage configuration to ensure that it is optimized for performance and reliability.
