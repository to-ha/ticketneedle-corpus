# Major Incident — INC-2026-0029
* **Ticket ID:** INC-2026-0029
* **Reported:** 2026-02-04 10:06 UTC
* **Priority:** P2
* **Domain:** Containers / Kubernetes
* **Status:** Resolved

## Symptom
The incident began with reports of pods failing to become Ready after being scaled up by the Horizontal Pod Autoscaler (HPA). Despite the HPA successfully scaling up the number of replicas, the pods would remain in a Pending state. Initial observations suggested that this issue was isolated to a single node, node-1, where the pods were being scheduled.

Further investigation revealed that the node's kubelet was experiencing difficulties in pulling the required container images, leading to a backlog of pending pods. This symptom was consistently observed across multiple deployments, pointing towards a node-specific issue rather than an application-level problem.

The monitoring team noticed a spike in pod creation failures around the time the incident started, with error messages indicating that the node was unable to schedule new pods due to resource constraints. However, upon closer inspection, it became clear that the node had sufficient resources to handle the scaled-up workload, suggesting that the issue lay elsewhere.

## Escalation timeline
* 10:18 — L1 Platform support: Kenji notified the L2 team about the escalating issue and provided initial diagnostic data.
* 10:37 — L2 Platform engineer: Eva began reviewing the node's configuration and logs to identify potential causes of the pod scheduling failures.

## Diagnosis steps and hypotheses
Initial hypotheses focused on resource constraints and network connectivity issues. However, after running diagnostic commands such as `kubectl describe node node-1 --v=5`, it became apparent that the node's kubelet was not functioning correctly.
```
kubectl describe node node-1 --v=5
```
This led to a re-evaluation of the node's configuration and the realization that the issue might be related to the kubelet's setup rather than external factors.

## Resolution steps
1. Restart kubelet on node-1 with --pod-infra-container-image flag
2. Set max-pods to 110 in /etc/kubernetes/kubelet.conf
3. Run etcdctl member list to verify cluster health
4. Apply kustomize overlay to update node-1 configuration

## Post-mortem note
The node kubelet was misconfigured with an outdated pod infra container image. This oversight led to a cascade of issues, including the inability to properly schedule and run pods on the affected node. Following the resolution, additional checks were put in place to ensure that all nodes are regularly updated and configured correctly to prevent similar incidents in the future.
