## Symptom
The monitoring system began experiencing a flapping pattern of alerts, where warnings would fire and then resolve within seconds, only to repeat the cycle. This behavior was first observed in the metrics related to the synthetic-probe runner's performance. As the incident progressed, it became clear that the issue was not limited to a single probe or metric but was instead a widespread problem affecting multiple aspects of the monitoring system. The repeated firing and resolution of alerts made it challenging for the on-call team to pinpoint the root cause, as each resolution would temporarily mask the underlying issue.

Further investigation into the symptom revealed that the alerts were primarily related to probe failures and timeouts. The frequency and pattern of these alerts suggested an issue with the probe runner's ability to handle its workload efficiently. Despite the probes themselves appearing to function correctly when tested individually, the collective behavior under load indicated a deeper problem that needed to be addressed.

The impact of this flapping pattern was significant, as it not only generated noise in the alerting system but also led to confusion among the operations team. The constant stream of alerts and resolutions made it difficult to distinguish between actual issues that required immediate attention and the noise generated by this incident. This situation highlighted the need for a swift resolution to prevent further disruption to monitoring capabilities and to restore confidence in the alerting system.

As the on-call engineers delved deeper into the issue, they started examining the logs and metrics more closely, looking for any clues that might explain the erratic behavior of the synthetic-probe runner. The focus was on identifying patterns or anomalies that could point towards the root cause of the problem. Tools like log-tail and tsdb-cli were utilized to inspect the logs and time-series data for any hints of what might be going wrong.

## Diagnosis steps and hypotheses
The diagnosis process involved considering several hypotheses about the cause of the flapping alerts. Initially, it was thought that the issue might be related to network connectivity problems or probe configuration errors. However, as these hypotheses were tested and ruled out, the focus shifted towards the synthetic-probe runner itself and its interaction with the time-series database (tsdb).

One of the key commands used during the diagnosis was:
```
tsdb-cli --query='probe_errors > 0' --start=-1h
```
This command helped in identifying if there were any probe-related errors within the last hour, which could have been contributing to the alerts. The results from this query, along with log analysis, pointed towards issues with how the probe runner was handling its load and interacting with the tsdb.

Other hypotheses considered included problems with the metrics platform, issues with the SIEM integration, and even potential bugs in the synthetic-probe runner software itself. Each of these was investigated through a combination of log analysis, metric inspection, and targeted testing. However, as the evidence mounted, it became clear that the root cause was more closely related to the configuration and operation of the synthetic-probe runner in conjunction with the tsdb.

## Resolution steps
1. Restart synthetic-probe runner with --log-level=debug flag
2. Set tsdb.retention-period to 30d in /etc/tsdb.conf
3. Run promtool to reload tsdb configuration
4. Verify probe-runner.log contains no errors after restart

## Post-mortem note
The synthetic-probe runner was not properly configured to handle increased load. This oversight led to a series of cascading issues, including the flapping pattern of alerts that were observed during the incident. In retrospect, regular reviews of the probe runner's configuration and performance metrics could have helped identify this issue before it became critical. The experience gained from this incident will be used to improve monitoring and alerting processes, ensuring that similar issues can be caught and addressed more proactively in the future.
